## 一句话结论

**局域网同步在四端都做得到,而且不破「零后端 / 不接三方 SDK」两条约束** ——
四端都有系统级 mDNS + TCP + 现代加密 API,不需要账号,数据不出局域网。
现在很多 App 能做得顺,是因为传输层早就不是难点;**真正的难点是两件与传输无关的事**:

1. **多设备同时改同一份数据时的合并语义**(删掉的订阅会不会被另一台带回来、进度谁覆盖谁);
2. **手机端的后台限制**(iOS / 鸿蒙在暂停播放后进程会被挂起,「永远在线」的同步不存在)。

至于「像 Spotify 那样」:**Spotify Connect 本身是账号 + 云端架构**,局域网只负责最后一跳。
零后端方案可以做到**同网段内的一键交接**,做不到**跨网络、锁屏后台的自动接力**。
这不是实现水平问题,是约束一的直接结果。若哪天接受「用户自己的云盘」,跨网络可以走另一条线
(见 `2026-10-18-cloud-backup.md`),但仍然不是 Spotify 那种「无感」体验。

## 用户要的两件事,先拆开

| 说法 | 真实含义 | 零后端 + 局域网能不能满足 | 主要卡点 |
|---|---|---|---|
| 「数据同步更顺滑」 | 订阅 / 收藏 / 历史 / 批注 / 印章在几台设备间一致,不要再导出 JSON、再导入 | **能**,一次配对后一键或自动合并 | 删除语义、冲突覆盖、首次全量大小 |
| 「播放进度跨设备,像 Spotify」 | A 在放,B 接着从同一秒放;甚至 B 能控制 A | **同网段、双方都在前台(或正在出声)时能**;跨网络/长期后台不能 | iOS/鸿蒙后台挂起、双设备同时出声、时钟偏差 |

**先把「同网段交接」和「跨网络接力」分开立项**。前者是 1~2 个版本能做完的功能;
后者要么破约束一,要么只能做「用户手动放一份文件到自己的云盘」,两者是不同的产品。

## 先划清一个参照:Spotify Connect 不是局域网方案

Spotify Connect 的工作方式是:**手机与播放设备都登录同一账号,通过 Spotify 的云端交换状态**;
同一 Wi-Fi 下的本地发现只用于最后一跳。开源实现 librespot 也必须连 Spotify 的 access point
做认证与取密钥,不是「两台设备自己谈」。所以:

- **能复制的部分**:本地发现、状态信令、一键把播放交给另一台设备;
- **不能复制的部分**:跨网络自动发现、锁屏后仍持续同步、无感切换 —— 这些依赖云端账号。

本文推荐的方案是「**局域网内的显式配对 + 状态信令**」,不是「重造 Spotify Connect」。
把它写清楚,是为了避免后面拿「Spotify 能跨网」当验收标准,做出一个永远不达标的承诺。

## 方案对比(先排除,再选)

| 方案 | 四端可用 | 守约束 | 适用 | 结论 |
|---|---|---|---|---|
| **mDNS/DNS-SD 发现 + TCP 长连接** | ✅ 系统能力 | ✅ | 同网段发现、全量/增量同步、播放信令 | **推荐主线** |
| 手动 IP:端口 + 配对码 | ✅ | ✅ | mDNS 被路由器挡住时的兜底 | **必做兜底** |
| UDP 广播发现 | ✅ 但代价高 | ✅ | 比 mDNS 更原始 | 不选:iOS 收广播要 multicast entitlement;Android 17 也要本地网络权限;没有额外收益 |
| Wi-Fi Aware(NAN) | ❌ 四端不齐 | ✅ | 无路由器直连 | 不选:平台支持不对称,不能当四端方案 |
| BLE | ✅ | ✅ | 极低带宽信令 | 不选:v1 不值得为它加一套配对/MTU/后台复杂度;播放信令走 TCP 已够 |
| MultipeerConnectivity | ❌ 仅 Apple | ✅ | Apple 端之间 | 不选:跨端即废,且最多 8 台 |
| Google Nearby Connections | ❌ 依赖 GMS | ❌ 三方 SDK | 海外 Android | 不选:大陆华为设备没有 GMS,且违反约束二 |
| WebRTC | ✅ 但重 | ⚠️ 通常要信令服务 | 跨网络 P2P | 不选:要么引三方库,要么自建信令(破约束一) |
| 用户自有云盘 / 系统云(iCloud Drive、SAF、鸿蒙 Cloud Kit) | 部分 | ✅ / ⚠️ | 跨网络、异步 | **另一条线**,见 `2026-10-18-cloud-backup.md`;不是本文的实时方案 |
| 鸿蒙「分布式数据对象」 | ❌ 仅鸿蒙 | ✅ | 鸿蒙设备间 | 不选:只覆盖鸿蒙;多端协同单对象上限约 500 KB,实例数与设备数也有硬上限,跨端即废 |
| 自建账号云同步(Spotify 式) | ✅ | ❌ 破约束一 | 跨网络无感 | **不做**(与项目性格直接冲突) |

**为什么主线是 mDNS + TCP,而不是 HTTPS/WebSocket:**
四端都有 TCP socket 系统 API(Apple `NWConnection`、Android `Socket`/`ServerSocket`、鸿蒙 `TCPSocket`/`TCPSocketServer`),
而 WebSocket 在 Android/鸿蒙上通常要引库或自己实现握手;**多引一个库就多一条「三方 SDK」的审查面**。
TCP 上跑「4 字节大端长度 + UTF-8 JSON」足够,协议自己定、四端各写一百来行,反而最可控。
TLS 也不必要:自签证书在四端的信任链与提示行为不一致,不如用「ECDH + AES-GCM + 六位配对码」
这一套**不依赖平台证书体系**的方案(见下)。

## 推荐架构(如果拍板做)

### 1. 设备身份与配对

- 每次安装生成一个**安装级设备 ID**(16 位十六进制)和一对**长期 P-256 密钥**。
  私钥进 Android Keystore / Apple Keychain / 鸿蒙 HUKS;设备 ID 只用于区分记录,不用于身份认证。
- 首次连接必须**显式配对**,不做「同一 Wi-Fi 自动信任」:
  1. 双方各自发起「附近设备」,通过 mDNS 看到对方;
  2. 建立临时 ECDH,双方用共享密钥派生一个**六位配对码**(SAS),一台显示、另一台输入/核对;
  3. 码一致才把对方公钥与名称存进「已配对设备」。
- 为什么不用「第一次见到就信任」(TOFU):局域网里任何一台设备都能冒充「附近的一台」;
  TOFU 在第一次就被中间人利用时没有任何提示。六位码是唯一能让**人**参与判断的一步。
- 配对窗口 2 分钟,过期作废;已配对设备后续连接用长期密钥做挑战应答,不再输码。
- 重装 App 等于换身份:旧设备记录要能手动删除,避免「幽灵设备」永久留在列表里。

### 2. 发现

- 服务类型:`_reverb._tcp`(Apple 需写进 `NSBonjourServices`;Android 用 `NsdManager`;
  鸿蒙用 `@ohos.net.mdns`)。
- 服务实例名用 ASCII:`Reverb-<设备ID前8位>`;显示名在认证后交换,不塞进 mDNS
  —— 鸿蒙的 mDNS 属性键名**必须小于 9 个字符**、值必须是 `Array<number>`,
  不适合放任意文本;四端都只广播最小字段:`v`(协议版本)、`id`(短 ID)、`pk`(公钥字节)。
- 发现超时 5 秒仍为空 → 提示「路由器可能开了 AP 隔离/访客网络」,并给**手动 IP:端口**入口。
  这不是体验瑕疵,是家庭网络的常见真实情况(尤其是运营商光猫的访客 Wi-Fi)。

### 3. 传输

- 监听一个固定端口(如 47820),失败则退回系统分配端口并在 mDNS 里广播实际端口。
- 帧格式:4 字节大端长度 + UTF-8 JSON;**单帧上限 8 MiB**,超过就分页(每页 200 条记录)。
- 连接保持:30 秒心跳;空闲 5 分钟关闭。同步与播放信令复用同一条连接,不各开一套。
- 消息类型:`hello` / `auth` / `snapshot_request` / `snapshot` / `delta` / `ack` /
  `ping` / `pong` / `playback_state` / `playback_take`。
- 所有消息带 `protocolVersion`;不认识的版本直接拒绝并提示升级,不做「尽力兼容」。

### 4. 加密

- ECDH P-256 → HKDF-SHA256 → AES-256-GCM;每条消息带 nonce 与序号,防重放。
- 不做自签 TLS:四端 TLS 栈对自签证书的处理不同,鸿蒙侧服务端 TLS 的可用性还要另验;
  自定义 ECDH 只用各端系统 Crypto API,行为可预期。
- 连接建立后先验证对方公钥是否在「已配对设备」里;不在就只允许进入配对流程,不传数据。
- 握手 transcript(版本号 + 双方 nonce + 双方公钥)用长期密钥签名;防止中间人替换公钥或降级协议。

### 5. 数据范围与合并语义(这是最容易做错的部分)

**复用现有「完整备份」的 v1 JSON 形状与分区**,不另造一套格式 —— 这样 LAN 同步、文件备份、
换机恢复三条路径共用同一套编解码,也不会再出现 H259 那种「新字段在某个 DTO 里被静默丢掉」。

| 分区 | 现有形态 | 建议合并规则 | 是否同步 | 理由 |
|---|---|---|---|---|
| `subscriptions` | Podcast 列表(整条 feed 元数据) | **按 `feedUrl` 取并集**;两端都有时保留本地那条(标题/封面差异只是抓取时间不同) | ✅ | 订阅是用户最在意的集合 |
| `favorites` | Episode 列表 | **按 `Episode.id` 取并集**,新在前 | ✅ | 纯集合,天然幂等 |
| `stamps` | 印章(episodeId + seal + createdAt) | **按 `episodeId` 取并集**;同集保留已有那条,删除走墓碑 | ✅ | 印章可撤销(`StampStore.remove`),不能只做并集 |
| `notes` | 批注(noteId + positionMs + text + createdAt + episode) | **按 `noteId` 取并集**;同 id 不覆盖,删除走墓碑 | ✅ | 批注不可编辑但可删除(`NoteStore.remove`),不能只做并集 |
| `history` | 每集 positionMs / durationMs / updatedAt / played | **按 `updatedAt` 取较新**(LWW);跨端时间戳统一到毫秒 | ✅ | 现有备份恢复已是这条规则,不要另立一套 |
| `listenStats` | 每频道 perDevice 分账 | **按设备取 max**(G-Counter 语义) | ✅ | 现有 `merge` 已幂等,直接复用 |
| `downloads` | 已下载单集 | **不传文件**;最多传「下载清单」让对端自行决定 | ❌ v1 | 体积大、网络与存储代价不可控 |
| `settings` | 主题/下载/播放等 | **默认不同步**;只允许少数「内容型」偏好以后单独列 | ❌ v1 | 设备形状不同(手机/桌面),整段同步会互相打架 |
| 逐字稿缓存 / 章节缓存 | 本机生成或拉取 | **不同步** | ❌ | 可重建;章节很小但也没必要,避免缓存格式耦合 |

**必须补的一层:删除墓碑(tombstone)。** 现有备份恢复是「并集」,因此**删掉的订阅会在恢复时复活** ——
换机场景下这是可接受的(旧备份里本来就有),但「多设备日常同步」下这是硬伤:
你在手机上退订一个节目,桌上那份同步时又把它加回来,而且永远删不掉。
所以同步协议里的**所有可删除的集合**(订阅 / 收藏 / 印章 / 批注)都要带 `{id, deletedAt, rev}` 墓碑,
保留 90 天;全量快照也要带墓碑,否则新设备从快照恢复后仍会复活旧条目。
**这一条如果不做,宁可先不做集合同步** —— 它比传输难,也比传输重要。
> **落地状态(2026-11-12)**:上一句里的墓碑已经做了,但只做了**墙钟版**:
> `kind + id → deletedAt(毫秒)`,90 天,快照带 `tombstones` 段,订阅键用归一化 feedUrl
> (Android `SyncTombstones.kt` / Apple `LanSyncTombstones.swift`)。**HLC 没做** ——
> 于是"两台时钟差几分钟"和"A 删 / B 重新订阅"仍按墓碑优先裁决;
> 这一层要等真正出现"同一条目两边来回改"的多设备用法再升级。

**排序用 HLC(Hybrid Logical Clock),不直接用墙钟。** 每台设备的系统时间可能差几分钟,
单纯比较毫秒时间戳会让「时钟快的那台」永远赢。HLC = 物理毫秒 + 逻辑计数 + 节点 ID:
收到对方更大的时间戳时,把本地物理时间抬到对方之上再 +1,因此即使两台差 5 分钟,
所有设备仍能得到**同一个确定的全序**;物理时间只用于播放进度的外推,不用于冲突裁决。
实现上每条记录带一个可排序字符串(如 `0000018f3c2a1b40-03-a1b2c3d4`),比较按字典序即可。

**冲突不要静默覆盖。** 历史进度用 LWW 是合理的,但当两台设备对同一集的 `updatedAt` 相差不到几分钟、
位置却差很多(比如一台刚听完、另一台停在开头),更稳的做法是**保留较新那条,同时在界面上提示**
「另一台设备停在 12:34」,让用户自己决定。播客不是协作文档,静默回退进度比多一次提示更恼人。

**Podcast 元数据没有 `updatedAt`。** 当前 `Podcast` 只有标题/作者/封面等字段,没有「这条记录何时被改过」。
v1 同步按 `feedUrl` 并集、保留本地即可;如果以后要做「封面/标题以较新抓取为准」,
需要给订阅存一份抓取时间 —— 那是持久化格式变更,按硬规矩 11 处理,不要顺手加。

### 6. 播放进度交接

**先做「交接」(handoff),不做「遥控」(remote control)。**
交接是「A 暂停、B 从同一位置接着放」;遥控是「B 当 A 的遥控器」。后者要处理命令归属、
双方同时操作、A 被来电打断等状态机,复杂度高一个量级,第一版不值得。

- **信令频率**:只在「正在播放」时发,1 秒 1 次;暂停/跳转/切集时立即补一条。
  不在后台常驻,不为了同步把播放器变成 1 Hz 的网络进程。
- **时钟偏差**:用 ping-pong 四时间戳估 offset(取 5 次中位数,RTT/2 补偿);
  绝对时间不用于排序(排序用 HLC),只用于「A 说 12:34 时,B 现在应该到哪」的外推。
  偏差超过 2 秒就只显示「约 12:34」,不自动 seek。
- **交接流程**:
  1. B 在前台看到「iPhone 正在播放 · 12:34」;
  2. 用户点「在此设备继续」;
  3. B 发 `playback_take`,A **先暂停**并回 `ack`(带最终位置);
  4. B 用 `ack` 位置 + 往返时间 × 速率 seek,再开始播放。
  **不自动接管、不自动播放** —— 两个设备同时出声是这类功能最典型的翻车方式。
- **后台现实**:
  - Android:播放期间有 `mediaPlayback` 前台服务,进程能维持 socket;暂停后不保证。
  - iOS:开了后台音频,播放期间可维持;暂停后会被挂起,信令随之停止。
  - 鸿蒙:只有 `audioPlayback` 长时任务在**真的出声**时能维持;`dataTransfer` 不是为长连接设计的
    (连续 10 分钟无进度会被取消),不能拿来常驻。
  - macOS:没有手机那种挂起,但 macOS 15+ 有本地网络权限提示。
  ⇒ 产品上要接受:**「正在放」时能交接,「停了一会儿」时只能等下次前台同步**。
  这不是缺陷,是三个手机系统的共同边界;把它写进文案,比做一个「有时灵有时不灵」的承诺好。

### 7. 与「零后端」的关系

局域网直连**不破约束一**:没有服务器、没有账号、数据只在用户自己的设备之间走;
它也不违反「不接三方 SDK」:mDNS、TCP、Crypto 都是系统能力。
但有两处口径要提前想清楚:

1. **「包里没有任何上传数据的代码路径」这句话要改成更准确的表述** ——
   同步会在**用户主动配对后**向局域网内的另一台设备发送数据,这不是上传到服务器。
   隐私政策与同意页要写明「仅在同一局域网、仅向已配对设备、不经过任何服务器」。
2. **解包 grep 的判据要能区分「外网域名」与「局域网地址」**:同步代码不应新增任何外部主机名;
   验收时按硬规矩 1 扫 `classes.dex` / 鸿蒙 `modules.abc` / Apple 二进制里的 URL 与 host,
   **新增的外部域名应为 0**,而不是笼统地说「没有网络代码」(播客本身当然要联网)。

## 四端能力矩阵(本轮核到的官方口径)

| 能力 | Android | iOS | macOS | HarmonyOS |
|---|---|---|---|---|
| 发现 | `NsdManager`(DNS-SD) | `NWBrowser` / Bonjour | `NWBrowser` / Bonjour | `@ohos.net.mdns`(API 10+) |
| 监听入站 TCP | `ServerSocket` | `NWListener` / BSD socket | 同 iOS | `TCPSocketServer`(API 10+) |
| 入站是否要本地网络权限 | Android 17 / targetSdk 37+ **要**;≤36 由 `INTERNET` 隐式授予 | **不要**(TN3179 明确:listen/accept 不需要) | 同 iOS(macOS 15+ 有本地网络隐私) | 官方文档只要求 `ohos.permission.INTERNET`;**是否有本地网络门未见** |
| 出站 TCP / mDNS | 要(Android 17) | **要**(出站 TCP 与全部 Bonjour 操作) | 要(macOS 15+) | 未见独立门 |
| 原始组播/广播 | 要本地网络权限 | **要 multicast entitlement**(普通 Bonjour 不用;通配浏览/任意服务类型才要) | 不要 multicast entitlement | 未见独立门 |
| 后台常驻 | `mediaPlayback` 前台服务播放期间可维持 | 播放期间可维持,暂停即挂起 | 基本不受手机式挂起 | `audioPlayback` 出声时可维持;暂停挂起 |
| 加密 | Keystore + `javax.crypto` | Keychain + CryptoKit / Security | 同 iOS | HUKS + `@ohos.security.cryptoFramework` |
| 已知坑 | 解析到的地址可能是 IPv6;`resolveService` 在 API 34 弃用,改用 `registerServiceInfoCallback`;部分机型 mDNS 需 MulticastLock | 模拟器不支持本地网络隐私,必须真机验;后台且权限未定时**静默拒绝且不弹窗**;不要硬编码 `en0` | ad-hoc 签名下本地网络隐私的身份跟踪不可靠(升级后可能重新弹窗/重置);防火墙会弹入站允许 | mDNS 属性键名 <9 字符、值为 `Array<number>`;mDNS 与 Android/Apple 的互通**未实测** |

⚠️ **本仓库 Android 当前 `targetSdk 34`** —— 按官方口径,targetSdk ≤36 时本地网络由 `INTERNET` 隐式授予,
所以**现在做同步不会被权限门挡住**;但一旦把 targetSdk 提到 37,所有 LAN 访问会立刻变成「要运行时权限」。
设计与文案现在就要按「将来会弹权限」准备,别等提 targetSdk 时才发现整条链路不可用。
**这张表里最重要的三行,决定了产品形态:**

- **iOS 的后台静默拒绝**:配对与首次发现必须在**前台**完成。不要在启动时偷偷扫,
  用户会看到一个没有上下文的「本地网络」弹窗,拒绝率很高。
- **macOS 的 ad-hoc 签名**:本项目 macOS 是 ad-hoc 签名,而 TN3179 明确说本地网络隐私
  用代码签名跟踪身份、ad-hoc 不可靠。**这是 macOS 侧的真实风险**,不是实现细节;
  要么接受「每次换构建可能重新授权」,要么以后换正式签名 —— 由维护者拍。
- **鸿蒙 mDNS 互通未验**:API 存在不等于能和 Android/Apple 的 mDNS 互相看见。
  这是本项目最应该先做的一次**真机对照实验**(鸿蒙广播、Android 浏览;再反过来),
  验过之前不要把鸿蒙写进「四端同步」的承诺里。

## 失败模式与规避(按发生概率排序)

| 失败形状 | 真实原因 | 规避 |
|---|---|---|
| 两台设备互相看不见 | 路由器开了 AP 隔离/访客网络;或 mDNS 被挡 | 手动 IP 兜底 + 明确提示;不要在 UI 上说「网络有问题」 |
| 首次连接弹「本地网络」被拒 | iOS/Android 17 的权限门 | 在用户点「连接设备」后再触发;弹窗前先解释用途 |
| 连接超时,没有报错 | Android 17 无权限时 TCP 表现为 **timeout**、UDP 为 **EPERM** | 按平台错误码分流提示,不要统一报「连接失败」 |
| 删掉的订阅又回来了 | 集合型数据没有墓碑 | 墓碑 + 全量快照也带墓碑(见 §5) |
| 两台同时出声 | 自动接管 | 必须用户点按;A 先暂停并 ack,B 再播 |
| 进度跳回开头/超出时长 | 秒/毫秒混用,或 LWW 取到旧记录 | 所有时间戳统一毫秒;跨端按 `updatedAt` 比较;沿用 H86 的归一口径 |
| 重复同步把批注翻倍 | 恢复/合并用随机 id | 现有 `noteId` 确定性兜底已解决;同步协议必须按 id 幂等 |
| 大历史撑爆一帧 | 全部记录塞进一个 JSON | 8 MiB 上限 + 每页 200 条 + 分页 ack |
| 升级后设备身份变了 | 重装/换签名导致密钥丢失 | 新设备重新配对;旧记录可手动删;不要用系统设备名当身份 |
| mDNS 广播泄露隐私 | 服务名/属性带了用户名或真实设备名 | 只广播 `v`/`id`/`pk`,显示名认证后再交换 |

## 分阶段计划(拍板后才开工)

**P0 — 局域网「一键同步」(最小可用,先解决用户现在的痛点)**
- 手动 IP + 六位配对码 + ECDH/AES-GCM;
- 复用现有备份 v1 JSON,**整份全量**双向合并(先不做增量、不做墓碑,只做「两台设备之间同步一次」);
- **P0 的已知限制:删除不会传播** —— 在对端删掉的条目,下一次同步可能被这边带回来。
  文案只承诺「把两台设备的内容合到一起」,不承诺「删除也会同步」;这条限制写进设置页的说明。
- 明确提示「这是合并,不是覆盖」;同步前自动在本地留一份快照,失败可回退。
- 自证:先做 Android↔iOS、Android↔macOS、iOS↔macOS 三对(鸿蒙并入时再补 Android↔鸿蒙),
  同步两次结果不变(幂等),断网/AP 隔离有可读提示。

**P1 — 发现与增量**
- mDNS 自动发现 + 手动兜底;
- 墓碑、HLC、增量 delta、分页;
- 设置仍不同步,下载仍不传。
- 自证:删订阅/删批注在两端都不复活;在 ±5 分钟人为时钟偏差下合并不乱序;
  重复同步/交错同步收敛到同一状态。

**P2 — 播放交接**
- `playback_state` 信令 + ping-pong 时钟估计 + 一键接管;
- 先 Android ↔ iOS/macOS,再验鸿蒙;
- 不做遥控、不做自动播放。
- 自证:两台真机同 Wi-Fi,A 播到 10:00,B 点接管,B 从 10:00±1s 开始,A 已暂停;
  锁屏/后台/暂停后打开 App 的行为符合文案。

**P3 — 可选**
- 遥控(B 控制 A 的播放/暂停/跳转);
- 下载清单转交;
- 跨网络:走 `2026-10-18-cloud-backup.md` 的用户自有云盘线,不是本文的 LAN 协议。

**明确不做**:账号、云端中继、Spotify 式跨网络无感同步、第三方发现/传输 SDK。

## 做完才算数的验收(全局)

- **解包 grep**:同步代码新增的外部域名 = 0;Android / 鸿蒙 / Apple 三份产物各扫一遍(硬规矩 1)。
- **五语同步**:新增的配对/同步/交接界面文案、隐私政策、同意页、关于页,按硬规矩 5 一次改齐;
  Android 的 `\'` 与鸿蒙 JSON 的直接 `'` 不要写混(H191)。
- **权限说明**:iOS `NSLocalNetworkUsageDescription` + `NSBonjourServices`;Android 17 起
  `ACCESS_LOCAL_NETWORK`;鸿蒙只加 `ohos.permission.INTERNET`(如后续文档出现新门再补)。
- **真机矩阵**:每对设备至少跑「配对 → 同步 → 第二次同步幂等 → 删一条 → 对端不复活 → 断网提示」;
  播放交接另跑「接管 → 暂停 → 锁屏 → 回前台」。
- **时钟偏差注入**:把一台设备时间调快/调慢 5 分钟,验证 HLC 排序与进度外推不崩。
- **电池**:播放期间 1 Hz 信令的耗电要实测,不能只靠「应该不高」。
- **不要用模拟器验本地网络隐私**:iOS 模拟器不支持,必须真机(TN3179)。

## 核实记录(原文摘录 + 出处 + 读取日期)

以下只列**会改变方案选择**的原文,不是全文。读取日期均为 2026-11-11。

### Apple TN3179《Understanding local network privacy》

- 入站 TCP **不需要**本地网络权限,出站 TCP **需要**(原文表格行,逐行摘录):
  > "Making an outgoing TCP connection | yes"
  > "Listening for and accepting incoming TCP connections | no"
- 所有 Bonjour 操作(注册/浏览/解析)**都需要**本地网络权限:
  > "All Bonjour operations require local network access."
  > "Registering a service with Bonjour | yes"
  > "Browsing for Bonjour services | yes"
  > "Resolving a Bonjour service | yes"
- multicast entitlement 只在 iOS 上、且只对「原始组播/广播」与「通配浏览/任意服务类型」要求;
  **普通 Bonjour 不需要**,**macOS 不需要**:
  > "The multicast entitlement isn’t required on macOS."
  > "Some uncommon Bonjour operations also require the multicast entitlement: Working with arbitrary Bonjour service types | yes; Browsing for all advertised service types | yes"
- iOS 在后台且权限未定时,**静默拒绝且不弹窗**:
  > "If an iOS app is in the background and performs a local network operation while its Local Network privilege is undetermined, the system denies that operation without presenting the local network alert."
- 模拟器不支持本地网络隐私:
  > "The simulator doesn’t support local network privacy. Test your local network privacy behavior on a real device."
- **ad-hoc 签名的身份跟踪不可靠**(macOS):
  > "Local network privacy tracks the identity of your program using its code signature. This presents a challenge on macOS, which allows for unsigned code and ad hoc signed code ... To ensure that local network privacy reliably tracks the identity of your macOS program, sign it with an Apple-issued code-signing identity."
- 不要硬编码 `en0`:
  > "BSD interface names, like `en0`, aren’t considered API on any Apple platform."
- 出处:<https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy>

### Android《Local network permission》

- Android 17(API 37)起,targetSdk ≥37 的应用访问局域网必须申请 `ACCESS_LOCAL_NETWORK`;
  targetSdk ≤36 由 `INTERNET` **隐式授予**:
  > "Starting in Android 17 (API level 37), local network protections are enforced for apps targeting Android 17 or higher."
  > "If your app targets SDK 36 or lower, local network access is implicitly granted using the INTERNET permission."
- 门覆盖**所有** TCP/UDP 与 mDNS、`NsdManager`,且在协议栈深处生效(原文表格行,逐行摘录):
  > "Making an outgoing TCP connection | yes"
  > "Accepting an incoming TCP connection | yes"
  > "Sending a UDP unicast, multicast, broadcast | yes"
  > "Receiving a incoming UDP unicast, multicast, broadcast | yes"
  > "These restrictions are implemented deep in the networking stack, and thus they apply to all networking APIs."
- 无权限时 **TCP 表现为 timeout、UDP 为 EPERM**:
  > "TCP Connections will typically result in a timeout error."
  > "UDP errors and general permission denials will typically result in an EPERM error code"
- 有系统选择器路径可避免宽权限(mDNS 的 `FLAG_SHOW_PICKER`),但只适合「用户选一台设备」的场景;
  四端自动发现仍需要宽权限或手动地址。
- 出处:<https://developer.android.com/privacy-and-security/local-network-permission>

### 鸿蒙 `@ohos.net.mdns` / `TCPSocketServer` / 长时任务

- mDNS 与 TCP Server 均从 **API 10** 起提供;mDNS 服务属性:
  > "mDNS服务属性键值,键值长度应该小于9个字符。" / "value: Array<number>"
- 仅需 `ohos.permission.INTERNET`(系统授权,normal 级):
  > "ohos.permission.INTERNET 允许使用Internet网络。"
- 长时任务:API 21 起一个 UIAbility 可同时申请多个,最多 10 个:
  > "从API version 21开始，支持一个UIAbility同一时刻申请多个长时任务，最多可申请10个"
- `dataTransfer` 连续无进度会被取消、`audioPlayback` 不发声会被挂起 ——
  这两条是「不能拿长时任务做常驻同步」的直接依据,官方页面为 JS 渲染,本轮由子代理读取正文核对。
- 出处:
  - <https://developer.huawei.com/consumer/cn/doc/harmonyos-references/js-apis-net-mdns>
  - <https://developer.huawei.com/consumer/cn/doc/harmonyos-references/js-apis-socket>
  - <https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/continuous-task>
  - <https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/permissions-for-all>

### Spotify Connect / librespot(只用于说明「为什么不能照抄」)

- Spotify 官方页面要点(转述,非逐字):Spotify Connect 需要 Spotify 账号;首次设置要求设备在同一 Wi-Fi,
  **登录后可以跨网络工作**;需要兼容设备。
- librespot(开源 Connect 接收端)仍依赖 Spotify 的 access point 做认证与密钥交付;mDNS 只用于发现
  (README 与源码结构要点的转述,非逐字)。
- 出处:
  - <https://support.spotify.com/us/article/spotify-connect/>
  - <https://github.com/librespot-org/librespot>

### 同类产品的既有做法(旁证,不直接采用)

- LocalSend:组播 UDP 发现,默认端口 53317,优先 HTTPS,用证书 SHA-256 指纹校验;
  HTTP 回退不校验指纹。说明「局域网发现 + 加密传输」是成熟组合,也说明**指纹/配对提示是必要的一步**。
  <https://github.com/localsend/protocol>
- 这些实现大多是**文件传输**,不是**多设备状态合并**;它们能证明传输层不难,
  证明不了本文 §5 的合并语义。真正的返工风险在后者。
- 鸿蒙分布式数据对象的规模上限(仅用于说明它不能当四端方案):
  <https://developer.huawei.com/consumer/cn/forum/topic/0204229376797726028>
  —— 多端协同单对象不超过 500 KB、单应用最多 16 个实例;且只覆盖鸿蒙设备。

| **跨端 mDNS(复验)** | Mac 侧 `dns-sd -B _reverb._tcp local` 先登记一个临时 `TestPositive` 当阳性对照,8 秒内它出现了;**同一窗口里没有 Android 的 `Reverb-841efc1b`**。两端仍分别在 `192.168.6.153` / `192.168.50.210`,组播不跨段 —— 「同一 Wi-Fi 自动发现」仍然没有证据 |
| Bonjour 注册 | Apple 侧自己的 `NWBrowser` 在 12 秒内发现 `ReverbProbe-…._reverb._tcp.local.`;Android 日志有「已广播 Reverb-df92b2fc 端口=47820」「开始发现 _reverb._tcp.」 |
| **未测** | 跨端 mDNS(两台设备无法落到同一广播域)、iOS/macOS **App 面板**的点击与运行(Apple 侧跑的是探针) |

**结论**:协议、加密、分块、合并与去重、双方角色都已在 Android 与 Apple 共享层之间真机跑通,
并有一次**真实 Wi-Fi(手动地址)单向**的端到端读数;
**「同一 Wi-Fi 下自动发现」这句话还没有实测证据** —— 它需要两台设备进了同一广播域再跑一次,
方法同上(把手动地址换成发现列表里点对方即可)。

## 同一网段的自动发现与双向直连(2026-11-12,已补)

Android 换到 H3C(`192.168.6.228/24`),与本机 Mac(`192.168.6.153`)同段,两块拼图都补上了:

| 项 | 读数 |
|---|---|
| 系统 NSD(对照组) | 面板打开 3 秒内 `SERVICE_FOUND` **0 条**;Mac 侧 `dns-sd -B` 却能看见手机的 `Reverb-841efc1b`。抓包确认 Mac 的组播应答确实发了 —— **AP 只放行一个方向的组播**(重连 Wi-Fi 能好一阵,几分钟后又坏) |
| QU 发现(新增的兜底路) | 同一次面板打开后 3 秒:日志 `QU 发现 1 台:cxyxl的Mac Mini@192.168.6.153:47820`;列表里可点 |
| Android 发起 | 两屏配对码 `199763`;手机 `restore` 3 160 B,探针 `APPLY … bytes=3160`(`subscriptions 1 / history 2 / listenStats 2`);两端 `added …=0`(内容一致) |
| Apple 发起 | 探针连手机**实际广播端口** `39937`(默认端口被残留占用的那一轮),配对码同为 `199763`,探针 `SENT 2488 B` |
| Mac 端解析 | `dns-sd -L` → `Android.local.:39937`,`nm=Pixel\ 3` |

所以「同一 Wi-Fi 下自动发现」在 H3C 这种**只丢一个方向组播**的网络上成立,
但成立的路径是新增的 QU 单播通道,不是系统 NSD —— 机制与踩坑见
`docs/TROUBLESHOOTING.md` H265。**仍未做**:iOS/macOS **App 面板**的运行与点击
(这一轮 Apple 侧仍是直接编译共享层的探针 + `dns-sd`),以及健康的双向组播网络上的
NSD 路径回归(本机没有那样的网络;代码保留它是因为在别处它更省电更省事)。

**鸿蒙那一台同段但不参与(同日晚复核)**:Mate 60(`9CN0224A08003297`,应用 `com.yuyin.reverb` 1.0.8)
在 `192.168.6.196/24`,与手机 `192.168.6.228`、Mac `192.168.6.153` 同段,双向 `ping` 3/3 收(0% 丢包)。
但它没有这套能力,三条独立读数一致:

| 项 | 读数 |
|---|---|
| TCP 监听 | 从 Mac `nc -vz 192.168.6.196 47820` → **Connection refused**;同一时刻 `192.168.6.228:47820` **succeeded**(对照组;`192.168.6.228:47821` 也 refused,证明探针认得出"有监听"与"没监听"两种形状) |
| mDNS 广播 | Mac `dns-sd -B _reverb._tcp local` 8 秒只有 `Reverb-841efc1b`(Android,`nm=Pixel\ 3`,`Android.local.:47820`),没有鸿蒙实例 |
| 界面入口 | 设置页从顶翻到底(内容 / 外观 / 播放与下载 / 逐字稿 / 提醒 / 存储 / 备份 / 日志 / 关于)没有「局域网」一项 |
| 源码 | `harmony/entry/src/main` 的 111 个 `.ets/.ts/.json/.json5` 里 `局域网\|LanSync\|_reverb\._tcp\|mdns` **0 命中**;阳性对照:同一扫描器同批文件「设置」命中 33 个 |

结论:Android ↔ 鸿蒙的**数据同步目前是产品范围外的"没有"**,不是信号、权限或配对问题;
鸿蒙接入要等 `@ohos.net.mdns` 侧实现(能力面见本文「鸿蒙 `@ohos.net.mdns` / `TCPSocketServer` / 长时任务」一节
与 `docs/FEATURES.md` 十四的端范围表)。
