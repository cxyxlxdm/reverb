> 三端(Android / macOS / HarmonyOS)从零到发布前的完整过程记录。
> **2026-08-01 ~ 08-25,198 次提交**,Android 11.4k 行 Kotlin、鸿蒙 11.8k 行 ArkTS、
> macOS 6.0k 行 Swift,外加 767 行 C/C++(两端各一个 native 模块)。
>

> 具体的坑与修法在 `TROUBLESHOOTING.md`(66 条);功能全貌见 `PRODUCT.md` / `FEATURES.md`;
> 实现细节见 `ARCHITECTURE.md`。

## 阶段一 · Android 首版(08-01 ~ 08-02)

从一个明确的产品判断出发:**做一个没有推荐流、不要账号、零后端的播客客户端**。
技术上的连带结论是「全链路免费免鉴权」——取源只用公开接口,播放一律回落发布方 RSS 里的
原始直链。这一条后来成了很多设计的边界条件(也成了合规叙事的基础)。

两天内成型的东西:发现(分类热门榜 + 搜索 + RSS 直接导入)、音阁(订阅/最新/收藏/下载/历史)、
播放(后台 + 锁屏 + 倍速 + 睡眠定时 + 续播)、订阅与更新提醒、下载离线、备份与 OPML。

紧接着一批「让听过的东西留下痕迹」的功能,它们后来成了这个 App 的性格:
**随机 / 情境电台**、**剪藏此刻**(把当下这一句做成卡片)、**听觉印记**(3×3 水墨情绪印章)。

这一阶段的两次小返工已经预示了后面的节奏:
- 电台从「两个按钮」改成「单按钮 + 设置切模式 + 长按显名」——两个按钮会同时转圈,状态说不清;
- 盖章面板去掉「取消」与「撤章」按钮,改成**再点同一枚即取消**——两个额外按钮解释成本高于它们的价值。

## 阶段二 · macOS 移植与「原生化」(08-02 ~ 08-10)

### 不是把 Android 界面搬过去

第一版 macOS 是照 Android 的布局搭的,能跑,但**不像 mac 应用**。随后整体重做:
顶部分段切换代替底部导航、设置走 `⌘,` 标准设置窗口、发现页改网格卡片、详情大留白。
这次重做定下了一条贯穿全程的原则:**功能对齐,交互各自原生**。

同期把仓库按平台拆成 `android/` 与 `macos/`,共享物料(图标、种子清单、引导音频)放 `shared/`
并用脚本分发——避免「改了一边忘了另一边」。

### macOS 特有的一串视觉与稳定性问题

刘海屏全屏时顶部菜单栏发黑、首屏封面偶发空白、播放条换集不刷新、首启动时控件带键盘焦点蓝框……
这些都不是逻辑 bug 而是平台细节,逐个查完之后**催生了 `TROUBLESHOOTING.md`**:
每条记「现象 / 根因 / 修法 / 可复用的规律」。事后看这是这个项目最有价值的一份文档。

### 转录:第一次做「跟读」

macOS 26 的 `SpeechAnalyzer` / `SpeechTranscriber` 是设备端识别,**而且给词级时间戳**——
于是播放页多出第三页:逐句显示、跟播放高亮、点一句跳到那一刻。
词级时间戳让「逐字卡拉OK」成为可能,又因为进度采样只有 0.5 秒一次,
补了**逐帧外推**(记住采样值与采样时刻,两次之间按真实流逝时间推)。
这套外推手法后来被 Android 与鸿蒙原样搬用。

### 性能:播放页每秒重渲两次的代价

外部反馈里有「CPU 长期高位」「偶发卡死」。根因很朴素:播放页观察播放器,
而播放中 500ms 一次 tick 就重渲一遍,**每次重渲都把几十 KB 的 shownotes HTML 重跑十道正则**。
修法是把解析移出渲染路径 + 按段懒排版 + 按当前页门控高频动画。
留下的规律:**渲染路径里不做解析**,以及「每秒会跑两次的代码要按每秒两次来估成本」。

### 收听时长:一个分布式计数问题

「按频道累计实际听过的时长」听着简单,难点在**备份恢复不能重复计数**。
最终按设备分账(设备 ID → 毫秒),展示值取各设备之和,合并规则是**按设备取 max**
——等价于一个 G-Counter CRDT。于是同一份备份重复恢复不会翻倍,跨设备恢复会正确汇总,
各设备自己新听的也不会被抹掉。

## 阶段三 · 鸿蒙端(08-11 ~ 08-15)

鸿蒙是第三端,也是**唯一只经商店分发**的一端(不支持自由侧载),这决定了它后面所有的合规取舍。

按里程碑推进,每个里程碑真机验证:M1 骨架与主题 → M2 数据层 → M3 发现与订阅 →
M4 播放层(AVPlayer + AVSession + 后台保活)→ M5 音阁与设置与 i18n,
随后 F1 收听时长与队列 → F2 电台 → F3 下载离线 → F4 印记与足迹与剪藏。

ArkTS/ArkUI 与 Compose 的差异比预想大,几个必须知道的:
- **`@Builder` 的值参数是一次性的**,状态变化不会重算——设置页的行标题因此不能用值参;
- 图标体系:`sys.media.*` 只有 66 个、缺齿轮/柱状图/心形/月亮等,不足以对齐 Material,
  最终改用系统 Symbol 字体(`SymbolGlyph`)逐个映射;
- `navDestination` 与并列 `if` 会白屏——这类问题只能真机撞出来。

## 阶段四 · 两轮厂商复核未通过(08-17 ~ 08-19)

这是整个项目最关键的转折点,因为它把「合规」从事后检查变成了设计输入。

**第一轮(鸿蒙)**:卡死、CPU 高、功能异常。与 macOS 那一轮性能问题同源——渲染路径里做重活。

**第二轮(Android)**:**隐私合规**。判定是「同意隐私政策前获取 SSID」。
根因不在我们的代码:Android 用的媒体播放库与后台任务库在判断网络类型时会调用系统接口,
该接口在 Wi-Fi 下返回的对象**顺带**携带 SSID。我们既不读也不存,但**调用发生在同意之前**。

修法有两层:
1. 首启**隐私同意门**——同意之前**一个会联网或读系统网络信息的组件都不装配**;
2. 隐私政策里为 SSID 写**专项说明**,把「系统接口顺带返回」这件事讲清楚。

鸿蒙端随即**提前对齐**同意门,没等它也被驳一次。
留下的规律:**"我们没读"不等于"没发生调用"**;合规看的是行为发生的时间点。

## 阶段五 · 登记与渠道隔离(08-20 ~ 08-23)

大陆应用商店要求 APP登记。合规口径把「内置内容目录 / 分类浏览 / 内容推荐」判定为
提供视听节目服务,需《相应内容分发许可资质》——个人主体拿不到;
而「用户自行添加 RSS 源」的纯工具不需要。

于是有了**渠道差异**:大陆商店渠道去掉分类热门榜、关键词检索、电台、内置精选清单,
首屏改为「导入推荐订阅 + 粘贴 RSS」。Android 用 flavor(`default` / `store`),
鸿蒙只有一个渠道、直接用编译期常量。

### 返工:两次证明「界面上点不到」不等于「包里没有」

- **Android**:靠 R8 折叠编译期常量把整套目录代码与数据剔除,**验收方式定为解包 grep**
  ——不是点界面。这条后来成了硬规矩。
- **鸿蒙**:同样的写法**不成立**。ArkTS **没有 DCE**,`Features.CATALOG ? A : B` 两支都会进包,
  release hap 里照样能 grep 到 iTunes/fyyd/gpodder 的类与 URL。
  最终把那四路取源**整体移出编译树**(挪到 `harmony/shelved/`)。

留下的规律:**编译期开关能不能真的删代码,取决于工具链有没有 DCE,不能类推。**

同期把域名切到 `cxyxl.cn`、写 `BEIAN.md`(登记所需信息、决策依据、流程顺序全量归档)、
按渠道拆分隐私披露(长文共用,差异那两段各渠道一份)。

### 截图返工了四轮

发布截图重截了不止一次:误拍成另一个页面、图标配色修好后整套重截、
按提交包重截、补足印记数据后重截受影响的 6 张,还撤掉过误提交的中途截图与两张含真实收听数据的图。
留下的规律:**截图要按"实际提交的那个包"拍**,而且任何 UI/文案改动都会让它过期。

## 阶段六 · 逐字稿三端落地(08-23 ~ 08-25)

macOS 早就有了,这一阶段把它推到另外两端。三端**功能形状一致、取字方式完全不同**,
因为可用的系统能力与渠道口径不同。详见 `TRANSCRIPT.md`。

### Android:官方稿 + 内置 whisper.cpp

先做发布方提供的稿(RSS 的 `podcast:transcript`),再做本机识别。
本机识别只随自分发渠道走——**大陆商店渠道完全不含引擎与模型**,靠 source set 隔离
(R8 删不掉 `.so` 与 assets,只能让那个渠道压根没有这些文件)。

一个先量后定的决定:模型在真机上用真实中文单集实测过再选,而不是凭感觉
——`tiny` 快一倍但中文错得明显,`base-q5_1` 的错基本只剩同音词。

### 返工:词级时间戳换了一次来源

中文逐字高亮最初用 whisper 的 **DTW** 对齐。上线后用户报「高亮跟语音完全对不上,而且根本不跟着走」。
查出来是**三个互不相干的缺陷叠在一起**:

1. **自动滚动把自己判成了「用户在滚」**——`animateScrollToItem` 自己也会让
   `isScrollInProgress` 为真,于是触发了「手指一碰就停 4 秒」的抑制,净效果是每 4 秒才跳一下;
2. **DTW 用错了**:实测整体偏晚 0.4~0.9 秒,而且库里那段赋值有**一格错位**;
3. **首块 120 秒**⇒首字要等二十多秒,而那段等待还是一片空白。

为了不再靠猜,专门写了**主机端探针**(`android/tools/asr-probe/`,与 JNI 同参数,
把每个 token 的时刻打出来),真相用**切片法**定(把音频截到 1.0 / 1.3 秒分别识别,
看第几个字还在里面)。结论:改用 whisper 自带的 `token_timestamps`——
准到 ±150 ms、**快 43%**,还能让 flash attention 常开,于是**逐字高亮不再有额外耗时**。

留下的规律:**一个现象可能是多个缺陷的和**;以及**时间轴这类看不见中间值的问题,
必须先造出能看见的工具**。

### 鸿蒙:实现了,然后按实测结论关掉

鸿蒙 ArkTS 层**没有解封装/解码 API**,所以先写了 native 模块(`cpp/reverb_pcm.cpp`)
把音频解成 16k 单声道 PCM,再喂系统的 Core Speech Kit。接线上连撞四个坑(见 H62),
修完能出字、不崩。

**但质量不够用**:默认(短语音)档一次会话只认第一句,10 分钟的中文单集只出 14 行、
多是「。」「能力。」这类碎片;试传「长语音」档的参数(参数名能从系统库里 `strings` 抓到、
取值抓不到)反而变成 0 行。结论:**Core Speech Kit 的离线档是给短语音输入设计的,
不是给长音频转写的——接口形状对得上,适用场景对不上。**

于是鸿蒙定型为**只走官方稿**(`Features.LOCAL_ASR = false`),识别代码保留、开关关着。
native 解码链真机验过能用,是后续接 whisper.cpp 的现成基础。

留下的规律:**"系统有这个 API"不等于"这个 API 能干这件事"**,这种判断只能靠真机跑真实素材。

## 阶段七 · 发布物料的准确性审计(08-24 ~ 08-25)

拿到 APP 备案号(`浙ICP备2026068045号-1A`)之后做了一轮系统审计,
查出来的**全是「文案与实际不符」这一类**,而且不止一处在 App 内部:

| 发现 | 为什么要紧 |
|---|---|
| 两端**发布文案**都写着「分类榜单、节目与单集搜索」 | 国内渠道没有这两个功能。不只是描述不实——砍掉内容目录正是为了不被判定为提供视听节目服务,文案里却写着有,等于自己推翻合规口径 |
| 两端**关于页**(App 内)同样写着「按地区与分类浏览每日热门」「按名字搜索」 | 比商店文案更要紧,复核人员一定会读到 |
| 隐私正文「不申请……**麦克风**」 | 对自分发完整版是**假的**——它为「真实频谱」声明了 `RECORD_AUDIO`,而同意门两个渠道都出 |
| 隐私正文的**权限清单只列 4 项** | 实际还有唤醒锁、开机广播、Android ≤9 的外存写入;商店平台复核会拿清单与政策对照 |
| **繁体那条隐私正文其实是简体** | 两端都栽在同一条串上(272 / 5 条里就这一条),孤立漏项但正好是法务文本 |
| **es / fr 的隐私正文整段还是英文** | 两端都是;而「五种语言」是文案里的卖点 |
| 政策说「保存图片……**不申请**相册写入类敏感权限」 | minSdk 26,Android 9 及以下确实要申请 |
| `FEATURES.md` 写「首启隐私同意门:默认渠道 无」 | 实际是无条件的,两个渠道都有——而这条错误直接导致了上面那条麦克风问题没被发现 |

留下的规律:**功能一改,自述就过期**。App 内的功能自述、商店文案、隐私政策、
功能文档这四处会同时失真,而且**最容易漏的是 App 内那一处**。

## 阶段八 · 鸿蒙端的性能返工(08-25)

用户报的是一句很小的话:「下拉刷新 loading 非常卡」。查下来是**两件互不相干的事**,
而且都不在下拉刷新本身。

### 返工一:高频状态挂在了被观察对象上

`PlayerController` 加了 `@Observed`,而 **ArkUI V1 的观察粒度是整个对象** ——
任何字段被赋值,所有 `@ObjectLink` 持有者都重跑 `build()`。而 AVPlayer 的 `timeUpdate`
约每 100ms 一次,回调里就一句 `this.positionMs = t`。于是**播放中整个页面每秒重建约十次**,
连搜索框与两个列表一起重建。下拉刷新只是最看得出来的那一刻。

这一轮没有靠手感,而是先找到**系统自带的两把尺**:`hilog` 里的 `ProcessJank` 事件数,
以及每次重建都会打一行的 `AceTextField` 日志。基线:播放中静置 10 秒 = 62 jank / 45 次重建,
**暂停后同一窗口 = 0 / 0**。

修法是把高频量搬进普通对象(`PlaybackClock`)、`positionMs` 保留成 getter、
需要连续进度的界面各自轮询,并把进度条拆成独立组件 `SeekBar` ——
让高频刷新只重渲那一小块。顺带把 ticker 的 `notify()` 与每半秒一次的 AVSession 推送都停掉。

**中途栽了一次**:挪走 `positionMs` 后重建只从 10Hz 降到 2Hz。剩下的是 ticker 里两行
毫不起眼的记账(`tickCount += 1`、`lastCountedPosMs = …`)和 `ListenStatsStore` 的
未落盘累计量 —— **ArkUI V1 不区分 private**,私有字段赋值一样通知。
于是判据从"界面用不用它"改成"**它多久变一次**"。

### 返工二:解析占住 UI 线程近两秒,而 jank 计数看不出来

第一轮改完,用户回了一句关键的话:**「即便暂停播放,下拉刷新还是很卡」**。
而我手上的 `ProcessJank` 计数只有 5,差点据此认为"刷新本身不卡" ——
**那个计数记的是 jank 事件,不是掉帧数,一次 1.8 秒的停顿也只记一条。**

改成往已有日志里加一个 `Date.now()` 差之后,话立刻说清了:一个 8.5 MB / 1026 集的订阅源
解析 **1833ms**,一轮 15 源刷新**约 4.5 秒是纯解析**,全在 UI 线程上。
根因是 ArkTS 没有协程:`Http` 的等待是异步的,但 `XmlPullParser` 的逐 token 回调、
每集一遍的 `htmlToText`、上千个对象的构造**全是同步 JS,谁调用就占谁的线程**。

修法是 `@Concurrent` + `taskpool`(`net/FeedTask.ets`),连网络一起搬进子线程,
并保留回落本线程的降级;另外把"整份写回"的缓存序列化也纳入去抖
(`writeJsonDebouncedLazy` 传取值函数而不是值,一轮刷新从 15 次全量 `stringify` 降到 1 次)。

复测:边播边下拉刷新 **124 jank → 0**、整页重建 131 → 4;暂停下拉刷新 jank 0。

留下的规律有三条,都写进了硬规矩:**观察粒度是对象不是字段**、
**"异步"不等于"不占线程"**、**别信粗计数器,要量绝对耗时**(第三条与逐字稿那次同源)。

### 三端扫查:同一类毛病,各端各犯一种

修完鸿蒙那两处之后顺着问了一句「**还有没有别的**」,于是按五类(同步文件 IO / 大对象序列化 /
解析与正则 / 图像编解码 / 渲染路径里的重循环)把三端扫了一遍。扫出四族(详见 H66):

- **鸿蒙独有、也最重**:下载把一集几十 MB 整块读进 JS 堆再 `writeSync`;
  逐字稿缓存(全应用最大的一份 JSON)读写解析全在 UI 线程;设置页 O(N) 同步 stat;
  备份的 stringify/parse 在 UI 线程,而且导入时把同一个大 JSON 解析了两遍。
- **三端共有**:播放中每约 5 秒整份写回 history / listen_stats。
- **macOS**:逐字稿缓存在主 actor 上同步解码。
- **冷启动**:三端都在启动时同步读一堆 JSON —— 但**实测之后决定不改**
  (Android `am start -W` 219ms、macOS store 合计约 53ms),并行化要动装配顺序,风险大于收益。

这一段最值得记的不是修法,而是两条判断:**报障的那一端不等于唯一有问题的那一端**
(鸿蒙报"下拉刷新卡",但同族问题另两端各有一份;而鸿蒙最重的那处另两端压根不存在——
因为那两端的框架天然把它放在后台);以及**"扫出来"不等于"该修"** ——
族四看着最像问题,量完发现改它是白担风险。

Android 侧的复测用 `dumpsys gfxinfo`(比鸿蒙的 jank 计数准得多):
边播边连续滚动 30 秒,**2 帧 jank → 0 帧**,`Number Slow UI thread` 2 → 0;
落盘 round-trip 也验了(播到 45:00 → 再播 1 分钟 → Home → force-stop → 重启续播到 46:46)。

## 三端对照:同一个产品,三套取舍

| | Android | macOS | HarmonyOS |
|---|---|---|---|
| 语言 / UI | Kotlin / Compose | Swift / SwiftUI | ArkTS / ArkUI |
| 规模 | 11.4k 行 / 67 文件 | 6.0k 行 / 38 文件 | 11.8k 行 / 58 文件 |
| 分发 | 自分发 + 大陆商店(两个渠道) | dmg 自分发 | **只有应用市场** |
| 逐字稿取字 | 官方稿 + 内置 whisper.cpp(仅自分发) | 系统 `SpeechAnalyzer`(词级) | **只有官方稿** |
| 词级高亮 | 有(whisper `token_timestamps`) | 有(系统给) | 仅当官方稿自带词级时间 |
| 真实频谱 | 有(可选,仅自分发) | 无(平台无等价能力) | 无 |
| 后台更新检查 | WorkManager 每 6 小时 | 无(手动刷新) | workScheduler 周期任务 |
| 合规门控 | 首启同意门(两渠道) | 不涉及商店 | 首启同意门 |

**为什么 macOS 代码只有另两端一半**:它不需要渠道隔离、不需要合规口径的功能删减、
SwiftUI 的声明式写法也更紧凑;而鸿蒙那 11.8k 行里有一部分是「ArkTS 没有等价能力
只能自己写」的补偿代码(比如 native 解码模块与图标映射表)。
