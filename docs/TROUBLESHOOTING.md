# 余音 · Reverb 踩坑与性能优化记录

> 开发过程中遇到的 **bug** 与 **性能问题** 全量归档,含**现场 / 根因 / 解法 / 涉及文件 / 教训**。
> 供日后查阅与复盘,避免重复踩坑。

## 维护约定(重要)

- **何时更新**:每解决一个 bug 或性能问题,**提交前把它补进本文件**(和代码改动同一次提交)。
- **写什么**:
  - **现场**——可复现的表现(用户看到 / 触发条件)。
  - **根因**——真正的原因,而非表面症状。
  - **解法**——关键改动、涉及文件与行为;有取舍要写清。
  - **教训 / 规律**——可迁移到别处的经验(能写就写)。
- **分平台**:分 `通用`、`Android`、`macOS`、`鸿蒙` 四节。**日后再新增平台(如 iOS / Windows),照此追加一节**,并把跨端共性问题沉淀到「通用」。
- **编号**:每节内递增编号(G/A/M…),新问题**追加到对应小节末尾**,不复用旧号。
- **不虚构**:只记真实发生并已定位的问题;假 bug(误操作 / 环境问题)也值得记,但要标注清楚。

## 通用(跨端共性)

### G1. 列表无谓闪动:不稳定排序触发 diff 重排

- **现场**:「最新」列表每次刷新后条目上下跳动 / 闪烁,内容其实没变。
- **根因**:按 `pubDate` 排序,但**相同日期的条目相对次序不定**(unstable sort)。上层用「内容相等」去重驱动 UI(Kotlin `StateFlow` 的 `distinctUntilChanged`、SwiftUI 的列表 diff)。内容一样但**顺序抖动**,被判定为「变了」→ 重新发射 / 重排 → 肉眼可见的闪动。
- **解法**:排序追加**稳定次级键**(`id`),形成全序:
  - Android:`sortedWith(compareByDescending<Episode> { parsePubMillis(it.pubDate) }.thenBy { it.id })`(`InboxStore.kt`)
  - macOS:同理,主键日期、次键 id。
- **教训 / 规律**:凡是驱动 diff 的列表,排序必须是**确定的全序**。别让「看不见的次序抖动」变成「看得见的闪动」。

### G2. 收件箱刷新范式:原子替换 + 失败不清空

- **现场**:多源增量刷新时列表反复重排;某个源抓取失败会把**已有内容清空**成白屏。
- **根因**:逐源「边拉边发」导致中间态频繁变动;失败分支直接写入空列表。
- **解法**(Android / macOS 的 `InboxStore` 同一套思路):
  - 有缓存时**不逐源刷 UI**,全部合并完成后**一次原子替换**:`if (latest.isNotEmpty() || !hasCache) value = latest`。
  - **失败不写空**——保留旧内容,宁可陈旧也不白屏。
  - **冷启动(无缓存)才逐源刷**,让用户尽快看到第一批内容。
- **教训 / 规律**:异步聚合多个数据源时,把「过程」和「结果」分开——过程别频繁抖动 UI,结果一次性落定;失败是「保持现状」,不是「清空」。

### G3. 累计计数器 + 备份「合并」= 重复统计(设计缺陷)

- **现场**:新增「按频道累计收听时长」后,备份/恢复走的是全局「合并语义」。若把累计时长也按合并=**相加**处理:第一次跨设备恢复能正确把两台时长加起来,但**同一份备份重复恢复就会反复累加**,数字越滚越大。
- **根因**:**累计计数器天生不满足幂等**。`订阅/收藏/印记` 是集合(按 id 去重,合并幂等),`历史` 是按 `updatedAt` 取新者(幂等),但「累计时长」是个单调增长的标量——两个标量无论取和还是取新,都无法同时满足「跨设备要汇总」与「重复恢复不重复计」这两个要求。取和会重复计;取 max 又会把另一台**自己新听的内容丢掉**。
- **解法**:改为**按设备分账**(等价 **G-Counter CRDT**)。
  - 每个频道不再存一个总数,而存 `perDevice: {设备ID → 毫秒}`;设备ID 是首次生成后固定的安装标识(macOS 存 `UserDefaults["device_id"]`,Android 存 `reverb_settings` 的 `device_id`)。
  - **本机只累加自己名下那一格**;展示值 `listenedMs` = **各设备之和**。
  - 备份恢复的合并规则 = **按设备逐格取 max**(`ListenStatsStore.merge`),**绝不跨设备相加**。
  - 旧格式(扁平 `listenedMs`)兼容:本地文件迁移时归入本机名下;来自旧备份的扁平值归入稳定的伪设备键 `legacy:<频道键>`,避免与本机数相加出错。
- **为什么同时满足三条**:不同设备是不同的格子,故跨设备恢复**自然汇总**;同一设备的两个数值只是**同一个单调计数器的两次读数**,取 max = 取较新读数,既**不重复计**也**不丢数据**——某台自己新听的时长记在它自己的格子里,别人的备份里那格更旧,max 会保留本地较大值。
- **验证**(推演已跑通,六例全过):A=10h、B 全新 → 恢复得 15h(B 又听 5h 新内容)→ **重复恢复仍 15h** → A 再听 3h 后恢复得 18h → 反向恢复两机均 18h → 再双向重复恢复稳定不变。
- **教训 / 规律**:**要合并的数据,先问它是不是幂等的**。集合用「按 id 并集」、状态用「按时间戳取新」、**计数器必须按来源分账再求和(CRDT 思路)**——把一个全局标量拆成「每来源一格」,合并就从「危险的相加」变成「安全的逐格取 max」。同理适用于任何未来要跨设备同步的累计量(播放次数、下载流量等)。

### G4. 分账下的「历史估算种子」仍会跨设备翻倍

- **现场**:G3 的分账修好后仍有一个漏洞——首启用历史估算的种子若**记在本机格**:A、B 两台都从**同一份历史**(历史本身也在备份里、会被合并)各自种子 10h,互相恢复后按设备相加 = **20h**,而真实只有 10h。选择性恢复(只勾「历史」不勾「收听时长」)会稳定触发。
- **根因**:种子不是「本设备的独立贡献」,而是**对同一份共享数据的估算**。把估算记进"本设备"这一格,就被 G3 的「不同设备相加」规则当成了独立贡献。
- **解法**:种子改记到**所有设备共用的固定格** `seed`(macOS `ListenStatsStore.seedKey` / Android `SEED_KEY`),合并时对该格取 max ⇒ 取较大的估算值,不再翻倍;真实播放仍各记在自己设备格里,该加的照加。
- **验证**:修复前两机种子互相恢复 = 20h(✗);修复后 = 10h(✓);且「种子 10h + B 新听 5h + A 新听 3h = 18h」、重复恢复稳定 18h。
- **取舍**:两台设备在启用本功能**之前**听的是**完全不同**的旧内容时,取 max 会偏保守(少算)。宁可少算估算值,也不虚增。
- **教训 / 规律**:分账 CRDT 里,**"格子"的语义必须是"独立贡献源"**。任何"对共享数据的推算/估算"都该放进一个共享格并用 max 收敛,而不是伪装成某个设备的贡献。

## Android

### A1. 下拉刷新灰色圆圈常驻不消失 / 上滑后无法再下拉

- **现场**:「最新」tab 下拉刷新,灰色 loading 圆圈**不消失、常驻**在顶部;而且**先往上滑一下,就再也拉不动**。
- **根因**:
  1. 刷新容器最外层 `Box` **缺 `.clipToBounds()`**——静止态的 `PullToRefreshContainer` 指示器越界露在顶部(同项目「发现」页 `DiscoverScreen` 有这层裁剪,`InboxScreen` 漏了)。**这是圆圈常驻的根因。**
  2. 指示器结束依赖 `fetch.await()`,要等**整套多源刷新(~8s)全部完成**才 `endRefresh()`,期间圆圈一直转。
  3. 增量发布时列表 collapse 会**推动下拉偏移量**,导致上滑后手势状态错乱。
- **解法**(`ui/screens/InboxScreen.kt`、`data/local/InboxStore.kt`):
  - `Box` 加 `.clipToBounds()`(裁掉静止态越界露出的指示器)。
  - **刷新与指示器解耦**:`rememberCoroutineScope` 里 `launch` 后台刷新,**不等全量完成**;`delay(600)` 后立即 `pullState.endRefresh()` 收起圆圈。
  - 增量发布加 `hasCache` 守卫,有缓存就不再逐源 collapse。
- **教训 / 规律**:遇到「同一交互在别处正常、这里不对」,**优先照抄本项目已工作的实现**(这里就是「发现」页的下拉刷新),比从头调快得多。指示器的显隐**不该和数据加载时长强耦合**。

### A2. 「改了却连最新都没了」——debug/release 双包混淆(假 bug)

- **现场**:装上新 release 包后,「最新」列表空了,一度以为是回归 bug。
- **根因**:手机上**同时并存**旧的 `com.yuyin.reverb.debug`(debug 带 `.debug` 后缀)与 release `com.yuyin.reverb`——**它们是两个独立可安装的应用**。用户打开的是**旧的 debug 包**,自然看不到新改动。
- **解法**:确认「正在装 / 正在打开」的是同一个 `applicationId`;用 `adb` 明确重装 release 包并打开它。
- **教训 / 规律**:排障第一步先确认**「在测的就是刚构建的那个包」**。Android 的 `applicationId` 后缀(debug/release)会造成同机多个同名图标,极易张冠李戴。

### A3. 想做「无外框图标」在某国产定制 ROM 上三条路都走不通(实测记录)

- **目标**:去掉图标外层的圆角矩形,让水墨声波徽标直接落在壁纸上。
- **实测环境**:某国产定制 ROM,Android 16,densityDpi 560(机型与 ROM 身份见本地 `docs/STORE-OPS.md` 第九节)。
- **三次尝试与结果**:
  1. `adaptive-icon` + 背景用「填了 `#00000000` 的 vector」→ 启动器把它合成成**纯黑圆角方块**,比自带的水墨渐变底更难看。
  2. `adaptive-icon` + 背景用 `@android:color/transparent`(真正的透明色)→ **同样是纯黑圆角方块**。
  3. 去掉 adaptive、改走 **legacy 透明 PNG**(mipmap-*/ic_launcher.png)→ 确实**无框了**,但启动器对 legacy 图标施加了固定内缩(legacy icon treatment),把图案压进内圈;即使把内容铺满画布 98%、并把像素尺寸翻倍到 384px,**仍明显小于同屏其它图标**,且放大后偏软。
- **结论**:该启动器环境下拿不到"既无框又与别人等大"的效果,**保留深色水墨底版**(也与 macOS / 鸿蒙三端统一)。无外框素材保留在 `ic_launcher_foreground_nobg.xml`,原生 Pixel 启动器一类环境可用,`ic_launcher.xml` 注释里写了切换方法。
- **一处判断失误(记下来提醒自己)**:我一度断言"这套 ROM 会给所有图标强加底色",并想拿 Play 商店/微信/X 当证据。**这是错的** —— 微信与 X 本身就是不透明方形图标,判断不了;而同屏的 **Google 图标是完全无框的彩色 G**,直接推翻了该断言。为什么 Google 能无框、我们不能,我**没有查清**(可能与系统内置图标包或它的图标资源形态有关),不做猜测。
- **教训 / 规律**:拿"看起来正常"的样本当反例前,先确认**该样本本身是否具备区分力**(不透明方形图标对"是否强加底色"这个问题零信息量)。以及:平台观感类结论必须落到具体机型 + 启动器,不能一概而论。

> 备注:A1 之外,「最新」在覆盖安装后的「长时间 loading + 闪动」由 A1(指示器解耦)+ G1(稳定排序)共同解决,非独立问题。

### A4. 频道详情页下拉灰圆常驻页首:标准容器 + clipToBounds 就够,别急着另起炉灶

- **现场**:频道详情页(PodcastDetailScreen)加下拉刷新后,页首常驻一枚灰圆,刷新结束也不消失。「发现」页同样的容器却没有残留,收件箱页(A1)加裁剪就能治。
- **根因**:material3 1.2 的 `PullToRefreshContainer` 把 48dp 的指示器圆**无条件常驻合成**,静止态仅靠 `graphicsLayer.translationY = verticalOffset - 容器高度` 把圆挪到**内容 Box 顶边之上**。它没有隐藏动画(`endRefresh()` 是瞬间归零,容器里也没有任何 LaunchedEffect/Animatable,这一点是反编译 aar 确认的)。详情页内容 Box 之上是顶栏(返回/分享按钮),越界部分直接画进顶栏区域,Box 没有裁剪 → 常驻。
- **走过的弯路**:当时断言「详情页残留在界内裁不掉」(**未验证的误判**),据此自绘了一套指示器——「不拖不刷就不挂进树」,derivedStateOf/graphicsLayer/Canvas 延迟读取做到拖动全程零重组。残留确实没了,但观感与系统组件不一致,真机一验即被否。
- **解法**(真机验证):与发现页/收件箱完全同款——标准 `PullToRefreshContainer` + 内容 Box 加 `clipToBounds()`。残留在 Box 顶边**之外**,裁剪即消失;越界画进顶栏这件事本身就是可裁的,当初想复杂了。
- **教训 / 规律**:
  1. A1 写过「同一交互别处正常、这里不对,先照抄已工作的实现」——这次没照抄,多走了一圈返工。
  2. 「能不能裁」是个几何问题:残留画在参照 Box 顶边之外,就一定能被 `clipToBounds` 裁掉。**未验证的论断(「界内裁不掉」)写进方案,是这次返工的直接根因。**
  3. 自绘系统组件之前先问一句:观感要不要跟系统一致?要,就别自绘——复刻官方组件的动效细节(箭头跟手、缓动)成本远高于套一次裁剪。
  4. 反编译 aar 看实现(`javap` 即可)仍然值得:无条件常驻合成、无隐藏动画这两个事实后来都派上了用场,错的不是排查,是排查完的选择。

## macOS

### 一、Bug

#### M1. 「最新」tab 每次切换都重载 + 条目跳动

- **现场**:每次切到「最新」分段都**重新加载**,列表条目上下跳。
- **根因**:切换即无条件重拉;叠加 G1 的不稳定排序。
- **解法**(`Data/InboxStore.swift`):加 `refreshIfStale` + `loadedSignature`(内容签名相同则不重新发射),避免切走切回反复重拉;配合 G1 稳定排序、G2 原子替换 / 不清空。

#### M2. 冷启动封面空白

- **现场**:冷启动时部分封面加载不出来,留白。
- **根因**:`AsyncImage` **偶发加载失败且不重试**(冷启动网络栈未热)。
- **解法**(`UI/Theme.swift`):自建 `RemoteImage`——走 `URLSession.shared` 的内存 / 磁盘缓存(重开即命中),失败按 **0.4s 退避重试至多 3 次**;`.task(id: url)` 换集时**先清空旧图**,避免残留上一集封面。
- **教训 / 规律**:系统 `AsyncImage` 没有重试策略,对弱网 / 冷启动不友好;需要稳态封面就自建带缓存+重试的加载器。

#### M3. 首次启动出现蓝色焦点环

- **现场**:首启时某控件被自动聚焦,出现一圈蓝色键盘焦点环。
- **根因**:macOS 默认给首个可聚焦控件加焦点环。
- **解法**(`UI/Theme.swift`):`.focusEffectDisabled()`(macOS 14+)封装为 `noFocusRing()`,按需施加。

#### M4. 睡眠唤醒后播放加载失败、静默卡死

- **现场**:合盖唤醒后点播放,加载失败且**无任何反馈**,一直卡住。
- **根因**:唤醒后网络栈短暂异常,`AVPlayerItem` 进入 `.failed` 状态却无处理,静默卡死。
- **解法**(`Playback/PlayerController.swift`):观察 `item.publisher(for: \.status)`,`.failed` 时**自动重试 3 次(退避 0.8s)**;仍失败给出**可见提示 + 手动「重试」按钮**。
- **教训 / 规律**:网络类加载一定要观察失败态并给用户出口,别让失败变成「转圈到天荒地老」。

#### M5. shownote 简介丢失换行、糊成一坨

- **现场**:播放页「简介」把所有换行 / 段落丢掉,连成一大段。
- **根因**:`Fmt.plainText` 把**所有 `\s+`(含 `\n`)collapse 成单个空格**,连段落结构一起抹平。
- **解法**(`UI/Theme.swift` 的 `Fmt.plainText`):**先**把 `<br>` 与块级标签(`p/div/li/ul/ol/h1-6/tr/blockquote/section`)转成 `\n`,**再**去其余标签;之后只压缩行内空白 `[ \t]+`、`" *\n *"→"\n"`、`\n{3,}→\n\n`,**保留换行结构**。
- **教训 / 规律**:清洗 HTML 文本时,「去标签」和「压空白」的**顺序**很关键——先把结构性标签转成换行,再压空白,别一上来 `\s+→空格` 把段落也吃掉。

#### M6. 播放页不出现「转录」页

- **现场**:播放页轮播里没有「转录」页。
- **根因**:`transcriptionEnabled` 设置项默认 `false`,用户没手动开。
- **解法**(`Data/Stores.swift` `SettingsStore`):默认值改为 `true`(init 读取 + didSet 落 UserDefaults 一并配好)。

#### M7. 中/英手动切换导致缓存失效、反复重转

- **现场**:转录页带「中文 / English」手动切换;**中→英→中**每次都重新下载语言模型、重跑转录,**完全没缓存**。
- **根因**:手动 toggle 改变 `localeId` → **改变缓存 key** → 每次都 miss;而一段音频通常**只有一种语言**,本就不该让用户手动切。
- **解法**(`UI/TranscriptPage.swift`、`Data/TranscriptStore.swift`):**去掉手动切换**,转录语言**固定按应用界面语言映射**(`zh-Hans→zh-CN` 等),缓存 key 稳定;每单集 × 每语言一份 JSON 缓存,命中**秒显**、不重转。
- **教训 / 规律**:缓存 key 要绑定**稳定、语义正确**的维度。别把「本不该由用户频繁改的东西」做成开关,既是坏设计也毁缓存。

#### M8. Swift 6 并发告警(NSLock / 捕获可变 buffer)

- **现场**:`TranscriptStore` 用 `NSLock` + 闭包捕获可变 buffer,触发 Swift 6 并发告警。
- **根因**:跨并发闭包共享可变状态。
- **解法**:`Transcriber` 改为 **`AsyncThrowingStream`**,在 **MainActor 上顺序消费**事件,天然无锁、顺序有保证,告警消失。
- **教训 / 规律**:Swift 6 下,与其用锁保护共享可变状态,不如用 `AsyncStream` + 单一 actor 顺序消费,把并发「串行化」掉。

#### M9. `onChange(of:initial:_:)` 在旧系统不可用

- **现场**:编译报新版 `onChange` 签名不可用。
- **根因**:该签名要求 macOS 14+。
- **解法**:用 `@available(macOS 14, *)` 门控 `TranscriptPage`(其容器本就从 14+ 实例化)。

#### M10. 新增 `@Published` 属性忘了在 `init` 初始化

- **现场**:编译错误——存储属性未初始化。
- **根因**:`SettingsStore` 加了 `transcriptionEnabled` 但 `init` 里漏了赋值。
- **解法**:`init` 补 `transcriptionEnabled = d.object(forKey: "transcription_enabled") as? Bool ?? true`。
- **教训 / 规律**:给非可选存储属性的 class 加成员,**别忘了 init 里配一行**;Swift 不会自动给非可选属性兜默认值。

#### M11. SourceKit 跨文件「Cannot find type」误报

- **现场**:编辑器 / 诊断持续报 `AppEnvironment` / `Episode` / `TranscribedSegment` 等**找不到类型**,跨文件飘红,但实际能编译。
- **根因**:SwiftPM 单 target 下 **SourceKit 索引的假阳性**(同 target 内跨文件类型解析偶发失效)。
- **解法**:**以 `swift build -c release` 为准**——只要 `Build complete!` 且 0 error / 0 warning,就是真没问题,忽略这类飘红。
- **教训 / 规律**:编辑器诊断 ≠ 编译结果。命令行构建才是唯一事实来源,别被 IDE 飘红带偏去「修」不存在的问题。

#### M12. 词级卡拉OK仍「一段一段」高亮

- **现场**:开启词级同步后,播放时高亮**还是整句一起亮**,没有逐字推进的打字机感。
- **根因**:
  1. 播放进度 `positionMs` 由 `AVPlayer` 的 periodic time observer **每 0.5s 才更新一次**(`PlayerController.swift:60`)——天然「半秒一跳」。
  2. 词级高亮**只作用于当前整句**;而**中文一句常是单个 run**(无空格分词),导致 `words` 为 `nil` 或整句是一坨,视觉上=整句高亮。
- **解法**(`UI/TranscriptPage.swift` 的 `KaraokeLine`):
  - 用 `TimelineView(.animation)` 在两次进度采样间**逐帧外推**平滑毫秒(`anchorMs + 已过时间 × 倍速`,**封顶到本句 `endMs`** 防抢跑)。
  - 预铺**「每字符时间线」**:有词级时间→按每个词的 `[start,end]` 线性分摊到词内字符;**无词级时间(老缓存 / 整句)→整句 `[start,end]` 均分到字符**——因此老缓存也能逐字亮。
  - **只有当前一行**逐帧刷新,其余行静态;暂停时按锚点静态显示。
- **取舍**:逐字节奏是**按时间线性推**,非逐音素对齐;整句均分时匀速铺字,语速起伏处会略快略慢,但整体跟随对。
- **教训 / 规律**:粗粒度的时间源(0.5s 采样)可以在客户端**逐帧外推**成平滑动画;缺细粒度数据(词级时间)时,用**线性插值兜底**也能得到连续观感。

### 二、性能

#### P1. 进入播放详情页卡 + 横滑卡:高频 TimelineView 常驻叠加

- **现场**:点进播放详情页明显卡顿,左右横滑也卡。
- **根因**:两个高频 `TimelineView` **同时常驻**——
  - `InkWave` 水墨波纹(`Canvas` + `.blur(radius:6)`,30fps;**blur 每帧强制离屏合成**,很贵);
  - `KaraokeLine` 当前句(60fps),而且**转录页在后台不可见时仍在空跑**;
  - 三页轮播常驻,**横滑时三页一起渲染**;
  - 剪藏 PNG(`ImageRenderer` 主线程同步)在 `.task` 里**阻塞开场动画**。
- **解法**(`UI/PlayerView.swift`、`UI/TranscriptPage.swift`):
  - **按当前页门控高频动画**:波纹仅在**第 0 页可见且播放时**流动(帧率 30→24fps);卡拉OK逐帧刷新仅在**转录页 `active` 且播放时**启用,否则静态显示。
  - 剪藏 PNG 渲染**延后 0.35s**,让开场 / 横滑动画先跑完再渲染。
- **教训 / 规律**:**不可见的动画必须停**;同一时刻尽量**只跑一个高频 `TimelineView`**;**动画层上叠 blur 极贵**(每帧离屏合成),能避则避、能降频则降频;主线程同步渲染(`ImageRenderer`)要延后,别挡首帧。

#### P2. 横滑仍卡 + 开场卡一两秒:shownote 长文本全量布局

- **现场**:P1 之后横滑仍有顿挫;点进详情页要**卡一两秒**才弹出。
- **根因**:
  1. `Fmt.plainText(ep.description)` 那串**正则写在 `body` 里,每次渲染都重跑**,横滑反复触发。
  2. `.fixedSize(horizontal:false, vertical:true)` 迫使**整段长简介一次性全量布局**(TextKit 同步排完所有行);分页 `LazyHStack` **预建相邻的简介页**时就触发这次全量排版 → 开场 1-2s 卡顿。
- **解法**(`UI/PlayerView.swift` 的 `showNotePage`):
  - 解析移到 `.task(id: ep.id)` **按集缓存**(`noteParagraphs`/`noteForEpisode`),不随横滑重跑正则。
  - 长文**按段落拆进 `LazyVStack`**,**只对可见段落布局**,去掉 `fixedSize`。
- **取舍**:跨段落的连续框选会**断在段边界**(段内正常),换来长文流畅滚动与秒开。
- **教训 / 规律**:**昂贵的纯计算(正则 / 解析)别放在 `body`**,移到 `.task`/`onChange` 按 key 缓存;**超长文本用 `Lazy` 容器分块**,避免 `fixedSize` 触发一次性全量布局。

## 鸿蒙(HarmonyOS NEXT / ArkTS)

> 环境:DevEco Studio 6.0.2、SDK HarmonyOS 6.0.2(API 22);真机 BRA-AL00 / HarmonyOS 6.1.0.135(API 24)。

### H1. hvigor 报「工程结构与配置需升级」

- **现场**:全新手写的工程,`hvigorw assembleHap` 直接失败:`00303024 The project structure and configuration need to be upgraded before use.`,提示用 DevEco 的迁移工具。
- **根因**:`ValidateUtil.modelVersionCheck()` 要求 **`modelVersion` 同时出现在 `hvigor/hvigor-config.json5` 与根 `oh-package.json5` 两处且完全相等**;缺任意一处即报此错(错误信息完全没提这点)。版本还必须落在 `[MINIMUM_MODEL_VERSION, CURRENT_MODEL_VERSION]`(本机为 5.0.0 ~ 6.0.2)。
- **解法**:两处都写 `"modelVersion": "6.0.2"`。
- **教训 / 规律**:遇到语义含糊的工具链报错,**直接去插件里搜错误码**(`hvigor-logger/res/error/*.json` 拿到符号名,再全局搜该符号名找到校验函数),比照文档猜快得多。

### H2. ArkTS 只编译「可达」文件,未引用的模块完全不参与类型检查

- **现场**:写完整个数据层(RSS 解析、四路取源、Repository、6 个 Store)后 `hvigorw assembleHap` **构建成功、0 错 0 警**——但这些文件当时还没被任何页面 import。
- **根因**:ArkTS 编译器从入口页面出发按依赖图编译,**未被引用的 .ets 根本不进编译单元**,自然也不做类型检查。于是"构建通过"是假的。
- **解法**:建立引用点(接入 `AppContainer` 并被 `Index.ets` import)后再构建;并用 `strings entry/build/default/intermediates/loader_out/default/ets/modules.abc | grep <符号>` **验证目标模块确实被编进字节码**。
- **教训 / 规律**:分层开发时别攒着一大堆未接入的文件——**每写完一层就接上引用点再构建**,否则错误会积压到最后集中爆发。

### H3. 页头压住状态栏(全屏布局下安全区避让失效)

- **现场**:M1 时页头正常;M3 把外层换成 `Navigation` 后,「发现」标题直接压在状态栏时间上。
- **根因**:`EntryAbility` 里设了 `setWindowLayoutFullScreen(true)`,内容延伸到状态栏下;原先靠内层 `Column` 的 `.expandSafeArea(...)` 生效,套上 `Navigation` 后该修饰符不再作用于最外层。
- **解法**:主动读避让区并作内边距——`window.getLastWindow()` → `getWindowAvoidArea(TYPE_SYSTEM / TYPE_NAVIGATION_INDICATOR)`,用 `UIContext.px2vp()` 换算后 `padding({top, bottom})`;tab 外壳与每个 `NavDestination` 都要加。实测 top≈32.9vp、bottom=28vp。
- **注意**:`getContext()` 已废弃,API 12+ 用 `this.getUIContext().getHostContext()`;`px2vp` 不要用 `.bind()`(会产生隐式 any,触发 `arkts-no-any-unknown`)。

### H4. 长时任务报 9800005「bgMode is invalid」,后台播放会被回收

- **现场**:播放正常,但 `backgroundTaskManager.startBackgroundRunning(...)` 持续失败:`9800005 Continuous Task verification failed. The bgMode is invalid.`,且因每 0.5s 同步一次状态而**刷屏重试**。
- **根因**:两点——(1) 必须在 `module.json5` 的 ability 里声明 `"backgroundModes": ["audioPlayback"]`(合法值见 SDK `toolchains/modulecheck/module.json` 的枚举),仅代码申请无效;(2) 用枚举版 `BackgroundMode.AUDIO_PLAYBACK` 与新版校验不匹配。
- **解法**:module.json5 补 `backgroundModes`,并改用**字符串模式版** `startBackgroundRunning(ctx, ['audioPlayback'], wantAgent)`;同时加 `bgFailed` 守卫,失败后不再每 tick 重试。
- **教训 / 规律**:鸿蒙的后台能力是「清单声明 + 运行时申请」双重门,少一半就失败。另外**任何放在 0.5s tick 链路上的失败分支都要加"只试一次"守卫**,否则日志与耗电一起失控。

### H5. 迷你播放条在全屏详情页消失

- **现场**:开始播放后回到频道详情页,底部迷你条不见了。
- **根因**:迷你条只挂在 tab 外壳里,而频道详情是覆盖其上的 `NavDestination`,外壳被整体遮住。
- **解法**:详情页的 `NavDestination` 内部也挂一份迷你条(与 Android「全屏详情页保留迷你条、隐藏 tab 栏」的设计一致)。

### H6. `@Builder` 的值参数是一次性的,状态变化后不重新求值

- **现场**:设置页切成「深色 · 水墨」,主题**确实即时生效**(整页变色),但「主题」那一行右侧显示的值仍是「跟随系统」。
- **根因**:`@Builder choiceRow(title, options, selected: number, ...)` 里 `selected` 是**按值传入**的参数;ArkUI 的 @Builder 值参数**不参与状态追踪**,组件重渲时不会重新求值,于是显示值定格在首次渲染。
- **解法**:改为传**闭包** `selectedOf: () => number`,在 builder 内部调用求值(闭包每次重渲都会重新执行)。
- **教训 / 规律**:ArkUI 里 `@Builder` 想拿到会变的值,要么**传闭包/按引用 `$$`**,要么在 builder 内部直接读状态——**不要按值传**。同类坑:`@Prop` 会更新(组件属性),`@Builder` 值参数不会,两者容易混淆。

### H7. 被重入拒绝的刷新把 loading 提前关掉

- **现场**:进音阁时「最新」聚合被触发两次,第二次被重入守卫拒绝,却把转圈标志置为 false——下拉刷新的圈提前消失,而真正的刷新还在跑。
- **根因**:loading 标志放在**页面**的本地状态里,由调用方设置;而"是否真的在刷"只有 store 自己知道。
- **解法**:让 store 自己持有 `refreshing` 标志(`InboxStore.refreshing`),UI 只读不写。
- **教训 / 规律**:**异步任务的进行态应由持有该任务的一方拥有**,调用方只订阅。与 Android 侧「指示器不该和数据加载时长强耦合」(A1)是同一个道理的另一面。

### H8. 频道详情页白屏:navDestination builder 里写了多个并列 `if`

- **现场**:M3 时点任何频道都能进详情页;M4/M5 之后**点任何频道都是白屏**(只剩一个返回箭头)。日志里 RSS 解析压根没触发。
- **根因**:`Navigation` 的 `.navDestination(builder)` 要求该 builder **只产出一个 `NavDestination`**。M3 时里面只有一个 `if (name === 'podcast')` 所以正常;M4/M5 追加 `player`、`settings` 后变成**三个并列的独立 `if`**,框架无法正确解析,后面的分支退化成空页面。
- **解法**:改成 **`if / else if` 链**(互斥且只产出一个 NavDestination)。
- **教训 / 规律**:声明式 UI 里"看起来等价"的 `if` 与 `else if` 在框架层并不等价——**路由/分支型 builder 一定要写成互斥链**。另外:我一度把这个白屏误判为"误触",是排查失误;**页面级异常要先复现两次再下结论**,别急着归因于操作。

### H9. 锁屏卡片进度显示 `--:--`(部分修复)

- **现场**:锁屏媒体卡片的封面/标题/频道/上一集-暂停-下一集**全部正常且暂停键真能控制播放**,但左右两端的时间数字一直是 `--:--`。
- **根因(已确认的一半)**:元信息只在**换集时**写一次,而此刻 `durationMs` 还是 0(时长要等 `durationUpdate` 或 `prepared` 后才拿到)⇒ 系统收到 `duration=0`。
- **解法**:`sync()` 里在**首次拿到时长后补写一次元信息**(记 `lastDuration`,变化即重写)。修复后日志确认 `duration=602592` 已送达,**进度条也确实随播放推进**。
- **仍未解决**:两端的**数字标签**依旧 `--:--`。进度条能动说明 position/duration 已被系统接受,故推测是该机型锁屏卡片自身的渲染行为(或还需额外声明某项会话能力),暂未找到解法。功能不受影响,**如实标记为未解决**。

### H10. AVPlayer 不接受普通文件路径,本地播放必须走 `fdSrc`

- **现场**:离线下载成功(文件确实在 `files/downloads/dl_xxx.m4a`),但播放已下载单集立刻报
  `Invalid Parameter: invalid parameters, The input parameter is not fd:// or network address`。
- **根因**:`AVPlayer.url` 只接受 **`fd://` 形式或网络地址**,**不接受文件系统路径**。
  Android 的 `Uri.fromFile(...)` / macOS 的 `URL(fileURLWithPath:)` 都能直接用,鸿蒙不行。
- **解法**:本地播放改用 `p.fdSrc = { fd: file.fd }`,文件用 `fs.openSync(path, READ_ONLY)` 打开;
  并在**换源与 release 时关闭上一个 fd**(`closeLocalFile()`),否则 fd 泄漏。
- **教训 / 规律**:跨端移植"传一个音频源"这种看似平凡的动作时,**每个平台接受的源形态都要单独确认**;
  同时凡是拿到系统句柄(fd/handle)就必须配一条明确的释放路径。

### H11. 下载失败会残留半截可播文件(顺手修掉的既有缺陷)

- **现场**:Android 版下载是直接写目标文件,中断/失败后**残留一个不完整但看起来能播的文件**。
- **解法**(鸿蒙侧一开始就按正确做法写):**先写 `<target>.part`,成功后 `renameSync` 成目标名**;
  失败路径统一 `cleanup(part)`。
- **教训 / 规律**:凡"下载/导出到最终路径"的写入,一律 **临时名 + 原子 rename**,别让失败留下伪成品。

### H12. 存相册:`createAsset` 要受限权限;`showAssetsCreationDialog` 的 uri 必须用 `fileUri` 转

- **现场**:剪藏 PNG 生成成功,存相册先报 `Permission denied`,换接口后又报 `Internal system error`。
- **根因(两层)**:
  1. `photoAccessHelper.createAsset` 需要 `ohos.permission.WRITE_IMAGEVIDEO` 这类**受限权限**,普通应用申请不到 ⇒ Permission denied。
  2. 改用免权限的 `showAssetsCreationDialog(srcFileUris, configs)` 后仍失败,是因为我**手拼了 `file://` + 路径**;该接口要求传**沙箱 uri**。
- **解法**:用 `fileUri.getUriFromPath(path)` 得到合规 uri 再传入。修好后系统会弹「允许"余音"保存 1 张图片?」(带图片预览),用户点允许即写入相册,日志确认「已存入相册」。
- **教训 / 规律**:鸿蒙里「写系统媒体库」的正道是**受控接口 + 系统确认弹窗**,而不是申请权限;并且**凡是跨进程传文件,一律用 `fileUri` 生成 uri,不要手拼字符串**。

### H13. 缓存命中后忘了继续后台刷新(注释与代码不一致)

- **现场**:发现页分类榜第一次拉到后写入磁盘缓存;**此后无论何时进入,永远显示旧榜单**,只有手动下拉刷新才更新。
- **根因**:`loadCategory` 里缓存命中就 `return` 了,而**注释却写着"后台刷新在下面继续"** —— 注释描述的是意图,代码没实现。Android/macOS 都是「缓存秒开 + 后台刷新」两步都做。
- **解法**:命中缓存只做「先展示」并置 `hadCache=true`,**继续往下执行 refreshPopular**;仅在无缓存时才显示转圈(有缓存时静默刷新,不打扰用户)。
- **教训 / 规律**:**注释声称的行为要和代码对得上**——这类"注释比代码更正确"的地方极难靠肉眼发现,写完一段带注释的分支后应回读一遍确认。

### H14. 两个已废弃 API 与 5 处未处理异常(0 警告收尾)

- `xml.XmlPullParser.parse` 自 API 14 废弃 → 改用 **`parseXml`**(同签名)。
- 全局 `componentSnapshot.get` 自 API 18 废弃 → 改用 **`UIContext.getComponentSnapshot().get`**。
- `AVPlayer` 的 `createAVPlayer/play/pause/seek/setPlaybackRate` **均可能抛异常**(状态机不允许时),
  ArkTS 会给 "Function may throw exceptions" 警告;统一包 try/catch(倍速集中到 `applyRate` 兜住)。
- **教训 / 规律**:另两端都是 0 警告构建,鸿蒙端也应保持;**警告里混着真实健壮性问题**(播放器状态机随时可能拒绝调用),不能只当噪音。

### H15. i18n 的求值时机:模块级常量会在 `L.init()` 之前求值

- **现场**:把界面文案抽到 `string.json` 后,分类 chips / 地区名 / 印章标签显示成**键名**(如 `genre_news`),而同页其它文案正常。
- **根因**:`DISCOVER_CATEGORIES` / `REGIONS` / `SEALS` 是**模块级常量**,在模块被 import 的那一刻就求值了 —— 那时 `L.init(ctx)` 还没执行,`resourceManager` 为空,`L.s()` 走了兜底分支返回键名。
- **解法**:标签改为**惰性求值** —— `categoryLabel(c)`、`regionLabel(r)`、`sealOptions()`;页面里的 `themeLabels`/`fontLabels`/`langLabels`/`segments` 也从常量字段改成方法。
- **勘误**:本条最初还写了「并把 `L.init(ctx)` 放在 `AppContainer.boot` 最前」——**这一步当时并没有真的做**,见 H18。
- **教训 / 规律**:**凡依赖运行时上下文(context/资源/配置)的值,都不能放在模块级常量里**。这类 bug 只在真机跑起来才看得见——编译永远通过,兜底分支让它"看起来能用"。

### H16. workScheduler 周期任务需要配套的 ExtensionAbility

- **现场**:`workScheduler.startWork(...)` 注册看似成功,但后台检查从不执行。
- **根因**:`WorkInfo.abilityName` 必须指向一个**已在 `module.json5` 声明的 `type: "workScheduler"` 扩展**(`WorkSchedulerExtensionAbility` 子类)。只写 ability 名不建扩展,任务没有落点。
- **解法**:新建 `FeedUpdateExtension`(实现 `onWorkStart/onWorkStop`)并在 `module.json5` 的 `extensionAbilities` 里声明。
- **注意**:扩展跑在**独立上下文**里,拿不到 UI 侧的 `AppContainer` 单例,须自行最小化装配(`L`/`Prefs`/`JsonFile`/订阅/repository);且它的 `context` 是 `ExtensionContext` 而非 `UIAbilityContext` —— 相关初始化接口的形参应放宽到 `common.Context`,别强转(强转会被 ArkTS 直接拒绝)。
- **另外**:`notificationManager.requestEnableNotification()` 的无参重载自 API 12 废弃,要传 `UIAbilityContext`(授权弹窗需挂在具体界面上)。

### H17. 锁屏时间数字 `--:--`:`updateTime` 要 epoch 毫秒(**本条曾给出错误结论,已重测改写**)

- **现场**:见 H9 —— 锁屏卡片封面/标题/控制键都对、**进度条随播放推进**,但两端时间数字显示 `--:--`。
- **本条的曲折,如实记录**:
  1. 先修了「元信息写太早导致 duration=0」——**这一步是对的且必要的**,但当时看仍是 `--:--`。
  2. 我据此推断 `AVPlaybackState.position.updateTime` 要的是**开机 uptime**,改成 `systemDateTime.getUptime(STARTUP)`,看到锁屏出现了时间数字,就**判定修好并写进了本文档**。
  3. 真机复验时发现:那个"时间数字"是 **`45:47 / 45:47`,两端相同、进度条满格** —— 明明才播了十几分钟。**它不是修好了,是换了一种错法。**
- **根因(实测数据)**:系统按 `elapsedTime + (系统now − updateTime)` 外推当前位置,而它的「now」是 **epoch 毫秒**。同一时刻实测三个时钟:`epoch = 1786507526089`(1.79e12)、`uptime STARTUP = 78567991`(7.86e7)、`uptime ACTIVE = 21358911`(2.14e7)。传 uptime 时外推量 ≈ 1.79e12,**位置溢出后被钳到时长** ⇒ 两端都显示总时长、进度条满格。
- **解法**:`updateTime: new Date().getTime()`(epoch 毫秒)。改回后实测锁屏显示 `14:48 / 45:47`、`18:10 → 18:46`(34s 后,差 36s)、`21:24 → 21:39`(15s 后,差 15s),**数字正确且按真实速度推进**。
- **那么最初的 `--:--` 是什么?** 是 **①duration=0(第 1 步已修)** 与 **②息屏低功耗态** 两件事。第 ② 点单独记为 H21 —— 它不是 bug。
- **诊断手段(这台机器上第三方应用取不到 hilog)**:`hdc shell hilog` 拿不到本应用的日志,`avSession.createController` 读回系统状态又需要系统级权限 `MANAGE_MEDIA_RESOURCES`。最后用**写沙箱文件 + `hdc file recv`** 取数:把 `epoch / uptime(STARTUP) / uptime(ACTIVE) / 发出的 elapsed / duration` 每 2s 写进 `avs_probe.json`,再把 `updateTime` 的时钟做成一个常量开关逐个试。**这套"沙箱文件当日志 + 常量开关做 A/B"在鸿蒙上很好用,值得复用。**
- **教训 / 规律**(这条比技术结论更值钱):
  1. **"改完现象变了"不等于"修好了"**。从 `--:--` 变成有数字,我就收工了 —— 而真实情况是从"不显示"变成了"显示一个错的值"。**验收要核对数值本身对不对,不能只看"有没有东西显示"。**
  2. **别把推断写成结论**。当时 H17 里我把"要 uptime"写得斩钉截铁,还专门总结了一条"system time 常指单调时钟"的规律 —— 那条规律在这里是**错的**,并且它作为"已归档的经验"会持续误导后来的自己。**文档里的因果结论,必须标注是实测还是推断。**
  3. 上一版还写了一条"部分生效比全坏更容易误诊"—— 这个教训本身是对的,但我**当时就在犯它**:进度条会动让我以为数据被正确消费了。

### H18. i18n 全界面显示键名:主进程从未调用 `L.init()`(H15 的遗留)

- **现场**:真机启动,发现页整屏都是键名 —— 标题 `nav_discover`、副标题 `app_slogan`、搜索框 `search_placeholder`、分类 chips `genre_recommend / genre_news / genre_business`、`continue_listening`、`discover_daily_hot`。**但底部 tab「发现 / 音阁」显示正常**,更新通知的文案也正常。
- **根因**:`L.init(ctx)` **只在 `FeedUpdateExtension`(workScheduler 扩展)里调过**,主进程的 `AppContainer.boot()` 里漏了。`L.rm` 为 null ⇒ `L.s(name)` 走兜底分支**原样返回键名**。底部 tab 正常是因为那两处走的是 `$r('app.string.…')` 而非 `L.s()`,不经过这条通路。
- **解法**:`AppContainer.boot()` 里 `Prefs.init` / `JsonFile.init` 之后立刻 `L.init(ctx)`(早于所有 `store.load()`)。
- **两点值得记的**:
  1. **兜底返回键名这个设计,是双刃剑**。它让「漏配某一条文案」一眼可见(好),但也让「整套资源管理器没装配」**不报错、不崩溃**地混过了编译与冒烟(坏)。若 `L.rm === null` 时打一条 error 日志,这个问题在第一次启动就会暴露。
  2. **同一份初始化逻辑存在两个入口(主 Ability 与 Extension)时,极易只补其中一个**。H16 里为扩展补 `L.init` 时,我误以为主进程早已有 —— 而 H15 的记录里也写着"已把 `L.init` 放到 `boot` 最前",**那句是错的**(已在 H15 加勘误)。**文档写了不等于代码做了**;涉及"某处必须调用某初始化"的结论,应以 grep 调用点为准,不以记忆或旧文档为准。

### H19. 语言切换只有小半个界面变:`@Builder` 值参数一次性(H6)+ 页面不观察语言

- **现场**:H18 修好后,在设置页把语言切成 English,只有**三处**变了 —— 页面标题 `Settings`、配色行 `Accent`、语言行的当前值 `English`;其余(`外观 / 主题 / 字号 / 地区 / 电台模式 / 默认倍速 / 快退 / 快进 / 备份 / 导出完整备份 …`)全都还是中文。冷启动进来则完全正常(全英文)。
- **根因**:两个原因叠加,恰好解释了"为什么偏偏是那三处变了"。
  1. **`@Builder` 的值参数是一次性的**(与 H6 同一个坑的新发作)。设置页的行标题都走值参:`sectionLabel(L.s('sec_appearance'))`、`choiceRow(L.s('set_theme'), …)`、`actionRow(L.s('backup_export'), …)` —— 状态变化后**不重新求值**。而变了的那三处恰好都不是值参:`accentRow()` 在 builder **内部**调 `L.s()`;`choiceRow` 的当前值走的是**闭包** `selectedOf()`(这个闭包写法当初就是为 H6 加的,注释还在);页面标题是传给 `ScreenHeader` 的**对象参数**。
  2. 即便修掉值参,**其它已挂载页面(发现/音阁)也不会重建** —— 它们把 `L.s()` 写在 `build()` 里没问题,但**语言不是它们观察的状态**,没有任何信号会触发重建。
- **解法**:与 Android「切换语言重建界面」同策略 —— **整棵界面树重建**。`EntryAbility` 持有 `windowStage`,把重建入口注入 `SettingsStore.onLanguageChanged`;`setLanguage()` 里 `setTimeout(…, 150)` 延后一帧调用(此刻还在下拉菜单的点击回调里,立刻销毁整棵树会连带销毁正在收起的菜单),然后再 `loadContent('pages/Index')`。
  - 一次性覆盖两个原因,不必逐个页面审计 `L.s()` 的调用位置。
  - 播放层(`PlayerController` / `AvSessionBridge`)是**树外单例**,重建不打断播放。
  - **代价**:导航栈随之重置,切完语言会回到「发现」页。
- **顺带确认**:`setAppPreferredLanguage()` 之后,**已持有的 `resourceManager` 实例会按新语言解析**,不需要重新取 rm(那三处能变就是证据)。
- **教训 / 规律**:
  1. **"只有一部分生效"是高信息量的现象,别急着当成"没生效"**。这里"哪三处变了"直接指认了根因 —— 变的都不是 `@Builder` 值参。和 H17 的教训互为镜像:那次是"部分生效"骗我以为已修好,这次是"部分生效"帮我定位。
  2. **同一个坑修过一次,不等于全局都对**。H6 当时只修了"当前值"这一类参数,标题类值参原封不动 —— 因为标题在当时的场景里确实不会变。**"这个值不会变"是随需求会过期的假设**,i18n 一来就过期了。
  3. 涉及全局性显示参数(语言/字号/主题),与其逐点做成响应式,**整树重建往往更省事也更可靠**。

### H20. 设置项弹出菜单贴着屏幕左侧,选项越多位置越离谱

- **现场**:设置页每一项(主题/字号/语言/地区/电台模式/倍速/快退快进)点开后,下拉菜单都弹在**屏幕左侧**,离用户点的「当前值」(在行右侧)很远;**「地区」最离谱** —— 12 项的菜单被丢在屏幕中间偏左,还纵向盖住了好几行。
- **根因**:`bindMenu` 挂在**整行**上,而行是 `width('100%')` 的满宽容器 —— 菜单的锚点矩形就是整屏宽的那一条,不给 `placement` 时按左上对齐,于是贴着屏幕左边缘弹出。
- **修一半的过程(值得记)**:先加 `{ placement: Placement.BottomRight }`,**6 项的语言菜单立刻正常**(贴着当前值下方弹出),但**12 项的地区菜单依旧歪** —— 因为它太高、在锚点下方放不下,ArkUI 转而自动选别的 placement;而锚点是满宽的一条,换成左/右侧摆放时就被挤回屏幕中间。**锚点尺寸不对,单靠 placement 治不好。**
- **解法**:改成**居中单选对话框**,与 Android 的 `ChoiceDialog` 同形态(标题 + 单选圈列表 + 可滚动 + 取消),自绘在页面的 `Stack` 顶层:
  - 没有锚点 ⇒ 选项多少都不影响位置;`constraintSize({ maxHeight: 360 })` + `Scroll` 让长列表滚动(地区 12 项);
  - 遮罩 `withAlpha('#000000', 0.45)`,点空白处关闭;
  - `@State picker: PickerSpec | null`,`null → 非 null` 时 `if` 分支整体重建,故 `@Builder` 的值参数拿到的是最新 spec(避开 H6/H19 那个坑)。
- **一处自我纠正**:我看截图觉得"遮罩没生效/太弱"。**是错的** —— 取弹层外同一区域(「备份」小标题那一带)测像素:最亮 186→106、均值 77.4→42.2,压暗到约 55%,与 0.45 黑遮罩吻合。深色主题下遮罩本来就不显眼。**观感判断要用可测的量去证伪,别凭印象改代码。**
- **教训 / 规律**:**弹层位置的第一嫌疑是锚点,不是 placement**。把浮层挂在满宽/满高容器上,任何对齐参数都会失去意义;要么把浮层挂在**真正的视觉锚点**(那个小控件)上,要么干脆改用**无锚点的居中对话框**。选项数量会放大这个错误——短列表恰好"看着还行"极易掩盖问题。

### H21. 息屏低功耗态下锁屏卡片显示 `--:--`(不是 bug)

- **现场**:`updateTime` 修正为 epoch 后,锁屏时间数字正确;但**放一会儿再截图又变成 `--:--`**,进度条却仍在推进 —— 看着像时好时坏。
- **实测**:同一次播放里连拍,规律稳定可复现:
  - 亮屏:`17:10` → 7 秒后 `17:17` → 正确推进;
  - 转暗约 30s 后:`--:--`,且**卡片整体位置上移、配色变暗**(是另一套 UI 状态);
  - 再唤醒:`18:46`,与真实时间吻合(34s 前是 `18:10`)。
  同时用沙箱探针确认:**息屏期间我们的 500ms ticker 一直在跑**(`epochMs` 与 `sentElapsed` 持续推进,增量与真实时间一致),所以不是推送停了。
- **结论**:这是**系统息屏/低功耗锁屏界面自己的渲染状态**,不显示两端时间数字(只保留进度条),应用侧无从干预。**不是缺陷,不需要"修"。**
- **教训 / 规律**:**排查"时好时坏"的显示问题,先把设备/系统的状态维度当成变量**(亮屏 vs 转暗 vs 息屏、前台 vs 后台)。我前后几次截图分别落在不同的屏幕状态上,同一份正确数据于是呈现出矛盾结果,白绕了一圈。判断"卡片位置/配色变了"⇒ 换了 UI 状态,是最直接的线索。

### H22. 自家导出的 OPML 自家导不回来:字符串抠属性漏了反转义与单引号

- **现象(离线自查发现,非用户报告)**:真机断开期间给 OPML 往返写了个纯逻辑回归,当场挂了 ——
  导出订阅 `https://x.com/rss?id=7&format=rss`,再导入回来变成 `https://x.com/rss?id=7&amp;format=rss`,
  拿这个地址去拉 feed 必然失败。另有一类整份识别不到:属性写成 `xmlUrl='...'`(单引号)时,一个源都抽不出来。
- **原因**:`BackupManager.extractFeedUrls` 当初用正则抄近路 `/xmlurl\s*=\s*"([^"]+)"/gi`,漏了两件事:
  1. **导出端 `xmlEscape` 把 `&` 转成了 `&amp;`,导入端却不反转义** —— 一条自相矛盾的往返。带查询参数的播客源很常见,不是边角情况;
  2. XML 属性值**单引号同样合法**,部分导出器(尤其手写/脚本生成的)就这么写。
- **为什么只有鸿蒙有**:Android 走 `XmlPullParser.getAttributeValue`、macOS 走 `XMLParser` 的 `attributeDict`,
  **实体反转义和引号风格是系统解析器的职责**,两端白拿。鸿蒙这边是自己抠字符串,解析器替别人做的事就得自己补。
- **解法**:`util/HtmlText.ets` 新增 `xmlUnescape()`(命名/数字实体都管),正则改为 `(?:"([^"]*)"|'([^']*)')` 两种引号都收,抽出后反转义。
  顺带纠正 `htmlToText` 里同一类顺序错误。**`&amp;` 必须最后替换**:先解 `&lt;` 再解 `&amp;`,会把
  `&amp;lt;`(转义过的字面量 `&lt;`)错解成 `<`,丢掉一层转义。
- **教训 / 规律**:
  1. **凡是「导出 + 导入」成对的功能,必须写往返测试**,且样本要含转义字符。单看导出正确、单看导入正确,合起来可以是错的;
  2. **用正则代替解析器时,要显式列出"解析器本来替我做了什么"**(反转义、引号风格、大小写、命名空间)并逐条补齐 —— 这类缺口不会在编译期暴露,只会在真实数据上暴露;
  3. **设备不在场时,纯逻辑层照样可以验**。把 ArkTS 的函数照搬成 JS 用 node 跑断言,几分钟就能定位这类缺陷,不必等真机。本条与备份幂等性都是这么查出来的。

### H23. 恢复备份后被踢回发现页、「已恢复」提示看不见:同值 setter 也触发了整树重建

- **现象**(真机验证 H22 的备份幂等性时顺手撞见):设置页点「从备份恢复」→ 选中文件 → 恢复确实生效
  (统计/订阅/历史都对),但**界面瞬间跳回发现页**,底部那行「已从备份恢复(合并,不覆盖)」提示
  随设置页一起被销毁。用户看不到任何成功反馈,只看到自己被莫名踢走,极易以为恢复失败而再点一次。
- **原因**:`BackupManager.apply()` 恢复设置段时是**逐键无条件调 setter** 的
  (`if (o['language'] !== undefined) st.setLanguage(...)`),而 `setLanguage` 挂着 H19 的整树重建钩子
  (`onLanguageChanged` → `loadContent`)。备份里的 `language` 与当前值**通常完全相同**(自己导出的备份尤其如此),
  于是「语言没有任何变化」却走完了整套重建。全工程只有这一个 `loadContent` 调用点,定位很快。
- **解法**:`setLanguage` 里先比值,同值直接 return,不碰重建钩子(落盘与 `applyLanguage` 保留,幂等无害)。
  真机复验两个方向都对:恢复后**留在设置页并显示提示**;把语言真切成 English 时整树照旧重建、全英文无键名泄漏。
- **教训 / 规律**:
  1. **带副作用的 setter 必须自己做同值短路**,不能指望调用方先比较 —— 恢复备份、同步、初始化这类
     「批量灌值」的调用方**天然会把当前值再写一遍**,副作用越重(重建界面/重连/重下载)代价越突出;
  2. **改动的波及面要顺着调用方向找一遍**。H19 给 `setLanguage` 加重建钩子时,只想着「用户在设置页选语言」
     这一个入口,漏了 `BackupManager` 也在调它。加钩子/加副作用时,先 grep 一遍谁在调;
  3. **"功能生效了"和"用户看得见它生效了"是两件事**。这次数据层全对,反馈却被自己的重建吃掉 —— 验收要
     连提示一起看,否则这种缺陷只有用户会遇到。

### H24. 导出的日志时间戳是 UTC 且不带日期,和用户手机上的时间差 8 小时

- **现象**(真机验收「导出日志」时发现):导出的 `reverb-log.txt` 首行写 `09:11:42 I/App: 启动`,
  可设备当时是 **17:11**(`hdc shell date` 为 `17:17 CST`,文件 mtime 也是 17:xx)。整份日志比本地时间**慢 8 小时**,
  且**只有时间没有日期**。
- **原因**:`Logger.remember` 用 `new Date().toISOString().substring(11, 23)`。`toISOString()`
  **固定输出 UTC**,东八区就差 8 小时;`substring(11, 23)` 又把日期部分切掉了。
- **为什么这很要命(而不只是"不好看")**:日志的唯一用途是**用户把它发过来、开发者按"我大概几点几分遇到的"去比对**。
  时间对不上,这份日志基本失去作用;跨天的日志没有日期,更分不清是哪一天的记录。
  三端还因此不一致 —— Android 用 `SimpleDateFormat("yyyy-MM-dd HH:mm:ss.SSS")`(默认本地时区)、
  macOS 显式 `f.timeZone = TimeZone.current`,**两端本来都是本地时间且带日期**,只有鸿蒙跑偏。
- **解法**:自己拼 `yyyy-MM-dd HH:mm:ss.SSS`。`Date` 的 `getFullYear/getMonth/getDate/getHours/...`
  **取的就是本地时区**,不要碰 `toISOString()`。真机复验:`2026-08-12 17:17:43.252 I/App: 启动`,与 `date` 吻合。
- **教训 / 规律**:
  1. **`toISOString()` 不是"格式化时间"的通用手段,它是"序列化成 UTC"**。凡是给人看的时间戳(日志、导出文件、界面),
     都要显式走本地时区;只有机器间传输才该用 UTC;
  2. **诊断类功能要按"它被使用的那个场景"验收**,而不是只看"有没有导出成功"。文件生成了、能打开、有内容,
     依然可能整份不可用 —— 这次就是导出、行数、分级、tag 全对,唯独时间是错的;
  3. 三端同名设施要**逐字段比对**,不能只对齐"有这个功能"。时区/精度/字段顺序这类差异,不比对就发现不了。

### H25. 单选圆圈左边被削掉一道直边:`Circle().stroke()` 的描边越界后被裁

- **现象**(用户报告):设置项对话框里的单选圆圈,**左侧被盖掉一点点**,放大看是一道竖直的平边,不是圆弧。
  配色行的选中环同理。
- **原因**:ArkUI 的 shape 描边是**跨路径居中**的 —— `Circle().width(18).height(18).strokeWidth(1.5)`
  会把线宽的**外侧 0.75vp 画到 18×18 布局盒之外**,而组件按自身边界裁剪,超出的部分直接没了。
  左侧最明显是盒左边界的亚像素取整所致;把圆缩小塞进更大的 Stack 也没用,因为裁剪发生在 **Circle 自己**的边界上。
- **解法**:圆环不要用 shape 描边,改用**盒模型的 border**:`Column().width(20).height(20).borderRadius(10).borderWidth(1.5)`。
  border 画在盒子**内部**,任何线宽都不会越界,也就无从被裁。项目里 `PodcastDetailPage` 的订阅按钮早就是这么画的。
- **教训 / 规律**:**"描边画在路径中心"是矢量绘制的默认约定,不是 ArkUI 的怪癖** —— CSS/SVG/Canvas 都一样。
  凡是给 shape 加 stroke,就要记得组件盒必须比图形大出至少半个线宽,否则一定被裁。
  需要严丝合缝的圆环/圆角框,优先用 border 而不是 stroke。

### H26. 「配色点了没反应」:页面读的是未被观察的裸对象,主题/字号看着正常纯属偶然

- **现象**(用户报告):设置里点配色色块**毫无反应**,环不动、颜色不变。而同一页的主题/字号却即时生效。
- **排查**:先用 `hdc` 把 `preferences/reverb_settings` 拉下来 —— `accent_index` 已经是 `1`。
  **写入成功、落盘成功,只是界面不刷新**;退出设置页再进来,环就在新位置上了。
  接着分别试主题与字号:两者都即时生效 ⇒ 不是全局失效,只有配色行不行。
- **原因**:`SettingsPage` 通过 `private app = AppContainer.get()` 读 `this.app.settings.accentIndex`,
  拿到的是**未被 ArkUI 观察**的裸对象;改它的字段不会触发本页重渲。
  主题/字号"正常"是**偶然**的:它们走对话框,选完会置 `this.picker = null` —— 这个 `@State` 变化顺带让本页重渲了一次,
  于是新的 `@Prop scheme` 也一并同步进来。配色行是直接 `onClick`,没有任何本地状态变化,自然原地不动。
- **解法**:把设置对象作为 `@ObjectLink settings: SettingsStore` 传入(该类已 `@Observed`),页内一律读 `this.settings`。
  这样字段变化本身就是刷新信号,不再依赖对话框的副作用。
- **教训 / 规律**:
  1. **"能用"和"因为正确的原因能用"是两件事**。主题/字号一直是靠对话框关闭的副作用刷新的 —— 这种偶然正确最坏:
     它掩盖了缺陷,直到有个不走对话框的入口(配色)出现才暴露。看到"一部分能用一部分不能",要先怀疑**能用的那部分是不是也错着**;
  2. **单例/容器里取到的对象天然不在响应式体系内**。`AppContainer.get().xxx` 这类写法读值方便,但绕过了 `@Observed/@ObjectLink`
     的观察链;凡是**要驱动界面**的状态,必须顺着 `@State → @ObjectLink/@Prop` 传下来;
  3. **"点了没反应"要先分清是没写进去还是没刷新**。直接去看落盘数据(本例 `preferences` 文件)一步就能定性,比盯着界面猜快得多。

### H27. 全 App 排查「改了不刷新」:四处真缺陷 + 两处「偶然正确」

- **起因**:用户报「配色点了没反应」(H26)后要求确认全 App 是否还有同类问题。逐页核查渲染的数据来源,
  凡是读 `AppContainer.get().xxx` 的都是**未被观察的裸对象**,再看该次交互有没有任何本地 `@State` 变化 ——
  没有就一定不刷新。结果:
  | 位置 | 交互 | 症状 |
  |---|---|---|
  | `LibraryPage` | 订阅段「行/宫格」切换 | 点了布局不变 |
  | `LibraryPage` | 历史段「清空」 | 列表不消失 |
  | `LibraryPage` | 删除下载 | 行不消失 |
  | `LibraryPage` | 「最新」刷新完成 | 结果不上屏 |
- **另两处「看着正常」的,同属偶然,一并纠正**:
  - `PodcastDetailPage` 的 `@State dlTick` **只写从不读**。ArkUI 按依赖刷新,没有任何元素依赖它,
    `dlTick++` 触发不了重渲 —— 下载态能变是蹭了别的重渲。**一个从不被读的 @State 等于没有。**
  - `DiscoverPage` 的电台按钮读 `app.radio.*`,靠播放状态 tick 顺带刷新;设置改了配色/字号后,
    发现页也一直停在旧配色(用户看到的「chips 还是青瓷」)。
- **解法**:外壳 `Index` 以 `@State` 持有全部 store,页面一律用 `@ObjectLink` 接收。
  前提已满足:各 store 都是 `@Observed`,且改数据一律「复制后整体赋值」(`this.x = next`),
  正是 ArkUI 能观察到的形式 —— 若有 store 是原地 `push/splice`,`@ObjectLink` 同样不会触发,得先改成整体赋值。
- **真机验证(关键:必须在「没有播放」时验)**:播放中每 500ms 的 tick 会让整棵树重渲,
  **把所有这类缺陷全都掩盖掉**。停止播放后逐项验:宫格切换当场变、删除下载该行当场消失、
  冷启进音阁「最新」自动上屏、点下载即刻变进度圈再变「已存」、改配色后返回发现页整页跟着变色。
- **教训 / 规律**:
  1. **「一部分能用一部分不能」时,先怀疑能用的那部分也是错的**。本轮六处里有两处一直"正常",
     实际都靠副作用吊着;只修不能用的那四处,等于把定时炸弹留在原地;
  2. **审计这类问题有确定的两步判据**:①渲染读的对象在不在观察链上(`@State/@Prop/@ObjectLink`);
     ②这次交互有没有任何被 build 读到的状态发生变化。两条都不满足即为缺陷,不必靠试;
  3. **验证响应式问题要先关掉所有"背景重渲源"**(播放 tick、定时器、轮询),否则测不出真相;
  4. 只写不读的 `@State`(计数器/tick)是**假信号**,写的时候以为在驱动刷新,实际什么也没做。

### H28. 两个进程写同一份 preferences:后写的整份盖掉先写的(预防性修复)

- **背景**:真机上曾出现 `accent_index` 从 2 自行变回 0(设置无故复原)。**该现象未能复现** ——
  实测写入立即落盘、`aa force-stop` 后重启仍在,故不下"就是它"的结论。
  但排查中发现一个确实成立的隐患,按预防处理。
- **隐患**:`Prefs` 用 `getPreferencesSync` 拿实例,`put` 后 `flush()` 是**整份写回**;
  而 `FeedUpdateExtension`(workScheduler 落点)跑在**独立进程**,也会 `Prefs.put('seen_*')`。
  鸿蒙 preferences **并非多进程安全**:两个进程各持一份快照,谁 flush 谁的整份内容落盘,
  另一进程之后改的键会被静默盖回旧值。
- **解法**:`seen_*` 迁到独立文件 `reverb_updates`(`Prefs.seenGet/seenPut`),两个进程不再写同一份。
  验证:跑一次「立即检查更新」后,`reverb_updates` 新建且含 `seen_*`,而 `reverb_settings`
  的 mtime 停在上一次改设置的时刻、`accent_index` 未变。
- **教训 / 规律**:**跨进程共享的键值存储要按「谁写」分文件,而不是按「是什么」分文件**。
  只要有两个进程会写同一个 preferences/SharedPreferences 文件,就存在整份覆盖的风险;
  扩展/Service/Widget 这类独立进程尤其容易被忽略 —— 它们往往只写一两个键,却会连带整份落盘。

### H29. `@Builder` 一次性值参数,把动态文本"往下挪一层"照样失效

- **现象**(S4 重构设置页时踩两次):设置页「清除缓存」的副标题要显示实时占用。点确认后
  缓存文件**确实被删了**(`hdc shell ls` 报 No such file),可副标题照旧显示旧的「257 KB」。
- **第一次修错**:以为是 `@State cacheBytes` 没触发重渲。实际是把副标题当**字符串**传给
  `@Builder actionRow(title, sub, action)` —— `@Builder` 的值参数是一次性的(H6/H19/H27 同族)。
- **第二次修错(关键教训)**:改成闭包 `subOf: () => string` 了,但在 `actionRow` 里
  写的是 `this.rowText(title, subOf())` —— **先求值,再把字符串传给下一层 @Builder**。
  等于把那个一次性值参数**往下挪了一层**,毛病一模一样,现象也一模一样。
- **正解**:闭包要**一路传到真正渲染那一层**再调用:`rowText(title, subOf: () => string)`,
  在 `rowText` 体内 `subOf()`。闭包之所以有效,不是因为"闭包是特殊参数",而是因为
  **它在 builder 体执行时才去读状态** —— 只要中途有人替它求了值,这个性质就没了。
- **教训 / 规律**:
  1. **修这类问题要顺着数据一路看到 `Text()` 那一行**,中间每一次 `@Builder` 传参都是一道
     可能冻结的关卡。只把最外层改成闭包,等于没改;
  2. **验证要用"能独立证伪"的观测点**。这次是靠 `hdc shell ls` 确认文件真删了,才能断定
     "逻辑对、显示错";只看界面会误判成"清除没生效",方向直接跑偏;
  3. 三次踩同一族问题(H6 值参数、H27 未观察对象、本条向下传值)说明:ArkUI 里
     **凡是"显示的值会变"的地方,都要先问一句「这个值是在哪一层求的」**。

### H30. 从 Android `strings.xml` 搬文案:XML 实体与 Android 转义会原样带进 JSON

- **现象**(S5 多语言实机验收时发现,两处):
  - 英文「Clear cache」副标题显示 `Charts &amp; image cache · 10 KB` —— 实体没解开;
  - 法语「Empreinte d\'écoute」多一个**字面反斜杠**,另有 8 条同类。
- **原因**:文案是从 Android `res/values*/strings.xml` 批量搬到鸿蒙 `element/string.json` 的。
  两种载体的转义约定不同:
  - XML 里 `&` 必须写成 `&amp;`(还有 `&lt;` `&gt;` `&quot;`);
  - **Android XML 还要求撇号/引号加反斜杠**(`d\'écoute`),换行写 `\n`;
  - JSON **两套都不需要** —— 直接照抄,这些转义字符就成了正文的一部分。
  中文文案没有 `&` 和撇号,所以 base/zh_TW 一条没中,**只在英文和法语暴露**。
- **解法**:搬运时统一做一次反转义:`&lt; &gt; &quot; &apos; &#39;` 各自还原、`&amp;` **放最后**
  (同 H22 的道理),再把 `\'` `\"` 去掉反斜杠、字面 `\n` 还原成真换行。
- **教训 / 规律**:
  1. **跨载体搬文案必须过一次"转义翻译"**,不能当纯文本拷贝。XML→JSON、JSON→XML、
     CSV→任何格式都同理;
  2. **中文文案会掩盖这类问题**:它不含 `&` 和 `'`,基准语言全绿会让人以为搬运没问题。
     多语言资源的验收**必须逐语言上机看**,至少覆盖一个含撇号的拉丁语言;
  3. 与 H22 是同一个根:**"谁负责反转义"这件事,在换载体时最容易掉在地上。**

### H31. 静态"未使用资源"分析会漏掉拼 key 的动态取串(差点删掉 31 个在用的键)

- **背景**:S5 收尾想清理无用字符串。用正则抓 `L.s('xxx')` / `$r('app.string.xxx')`,
  算出 50 个"没人用"的键,准备删。
- **险情**:其中 31 个是 `genre_*` 与 `region_*` —— 它们实际是**拼出来的**:
  `L.s(\`genre_${c.key}\`)`、`L.s(r.labelKey)`(key 存在数据表里)。删掉会让
  **发现页 19 个分类 chips 和 12 个地区名全部变空**,而且编译期一声不响。
- **处置**:核对后确认只有 19 个是真过时(被图标取代的 `layout_grid`/`downloaded`/`action_remove`、
  被新行名取代的 `backup_export`/`sec_other` 等)。考虑到收益只是"整洁"、而误删代价是静默
  功能损坏,**决定一个都不删**,把结论记在这里备查。
- **教训 / 规律**:
  1. **"没有引用"≠"没被使用"**。凡是支持 `L.s(变量)` / 反射 / 字符串拼接的取值方式,
     静态扫描一律不可信 —— 清理前必须先搜一遍**动态取串的入口**(模板字符串、labelKey 之类字段);
  2. **删除类改动要按"误删代价"定夺,而不是按"看起来没用"**。这次误删不会编译失败、
     只会让界面静默变空,属于最难发现的一类;
  3. 死资源的运行时成本是零。**收益为零、风险非零的清理,不做才是对的。**

### H32. 迷你播放条跑到底部 tab 栏**下面**:它是 `Tabs` 的兄弟节点,而 `Tabs` 自带的 bar 在自己底边

- **现象**(用户报告):迷你播放条显示在底部「发现 / 音阁」tab 栏的**下方**;Android 是在 tab 栏**上方**。
- **原因**:外壳写成
  ```
  Column() {
    Tabs({ barPosition: BarPosition.End }) { ... }.layoutWeight(1)
    if (player.current !== null) { MiniPlayerBar(...) }   // ← 排在 Tabs 之后
  }
  ```
  `Tabs` 自带的 bar **属于 Tabs 组件本身**,固定在它的底边;任何作为 Tabs **兄弟节点**排在其后的东西,
  只能落到那条 bar 的下面。想插到 bar 之上,在这个结构里没有位置可用。
- **解法**:`.barHeight(0)` 把自带 bar 收掉,底部栏自绘,顺序按 Android 的 bottomBar 排:
  内容(layoutWeight 1)→ 迷你条 → 分隔线(仅迷你条出现时)→ 自绘 tab 栏。
  自绘的 tab 项要自己接 `onClick` 改 `this.tab`,并把 `.width('100%')` 换成 `.layoutWeight(1)` 平分宽度。
- **教训 / 规律**:**"自带容器"的部件(Tabs / Navigation / 各种带 bar 的组件)会把自己的附属条钉在自身边界上**,
  外面无法往它内部插层。凡是"要和它的附属条形成特定上下关系"的需求,先问一句:**这条 bar 归谁所有?**
  归它所有,就只能关掉自带的、自己画 —— 而不是试图靠调整兄弟节点顺序去挤。

### H33. 半模态的 `onClick(置 true)` 与 `bindSheet($$state)` 挂同一节点 ⇒ 关闭时抖一下又弹回来

- **现象**(用户报告,偶发):点「章」从底部弹出印章面板,点空白处收起,**又自己弹出来一次**,再点才最终收起。
  复现不稳定。
- **原因**:同一个节点上写了
  ```
  .onClick(() => { this.showSeals = true; })
  .bindSheet($$this.showSeals, this.sealSheet(), { height: 330 })
  ```
  `$$` 是**双向绑定**:点空白处关闭时 ArkUI 自己把 `showSeals` 置 false。而该节点的 `onClick`
  会把它置回 true —— 关闭动作与"再次置真"在同一节点上竞争,命中时序就出现「收起 → 回弹 → 再收起」。
  偶发性正来自这个时序竞争。
- **解法**:让**触发者与 sheet 宿主不是同一个节点**。本次顺着 Android 把盖章收进「更多」溢出菜单,
  由 `MenuItem` 的 onClick 置位、sheet 绑在菜单按钮上,冲突自然消失。
- **教训 / 规律**:
  1. **`$$` 双向绑定的状态,不要在同一节点上再写一个"单向置真"的手势** —— 框架的自动回写与你的
     手动置位会互相踩。要么用单向 `bindSheet(this.x)` 自己管开关,要么把触发挪到别的节点;
  2. **"偶发、复现不了"的交互抖动,优先去找同一状态的多个写入方**。这类 bug 靠反复点很难抓,
     但把"谁会写这个状态"列出来,往往一眼就看出竞争。

### H34. 分享私有目录里的文件必须用 `fileUri.getUriFromPath()`,拼裸 `file://` 路径面板压根不弹

- **现象**:足迹海报的「分享」点了**毫无反应** —— 没有面板、没有报错、没有异常日志。
- **排查关键**:先去看**中间产物**。`hdc shell ls` 确认 `reverb-footprint.png` 已经生成(74 KB),
  拉下来看图也完全正确 ⇒ 离屏渲染没问题,问题只在"交给分享"这一步。
  若只盯界面,很容易误判成"离屏渲染失败"或"分享 API 在本机不可用",方向就跑偏了。
- **原因**:`SharedData` 的 `uri` 我写成了 `file://${沙箱绝对路径}`。图片在**应用私有目录**里,
  别的应用没有读权限;分享框架拿不到可授权的 URI 就静默不弹面板。
- **解法**:`fileUri.getUriFromPath(path)`(`@ohos.file.fileuri`)生成带 bundle 归属的应用文件 URI,
  分享框架据此做临时授权。改完面板正常弹出,还带海报预览。
- **教训 / 规律**:
  1. **"点了没反应"要先确认链路走到哪一步断的**。这类跨应用交互失败常常是静默的,
     日志里什么都没有 —— 去找中间产物(临时文件、缓存、落盘数据)最快;
  2. **跨应用传文件,路径和 URI 不是一回事**。凡是把自己目录里的文件交给别的应用/系统组件,
     都要走平台提供的 URI 生成 + 授权机制(鸿蒙 `fileUri`、Android `FileProvider`),
     手拼 `file://` 在两个平台上都会失败,且都倾向于静默失败。

### H35. 可滚动内容导不出完整长图:按 id 截屏只能拿到一屏,要用离屏渲染

- **现象/需求**:足迹海报要把**全部**印章导出成一张图,而印章网格是可滚动的、通常比视口高。
  沿用剪藏那套 `componentSnapshot.get(id)` 只会得到当前可见的那一屏。
- **解法**:`UIContext.getComponentSnapshot().createFromBuilder(builder, delay, checkImageStatus)`
  —— 把一棵**不在界面上**的子树按其自然尺寸离屏渲染成 PixelMap。
  为此把海报单独写成一个 `@Builder`(标题 + 全量三列网格 + 页脚),尺寸写死不受视口约束。
  Android 侧是用 Canvas 程序化合成位图(`ShareCards.footprintPoster`),两端手段不同、语义一致。
- **教训 / 规律**:**"截屏"和"渲染出一张图"是两件事**。凡是导出内容可能超出一屏(长列表、报表、海报),
  就不要用截屏 API —— 找平台的离屏渲染入口,或自己用 Canvas 合成。

### H36. 沉浸式全屏下状态栏图标不跟主题:深色底上一片黑,几乎看不见

- **现象**(用户报告):深色「水墨」主题下,状态栏的时间/WiFi/电量全是**深色**,压在深色底上糊成一团。
- **原因**:应用调了 `setWindowLayoutFullScreen(true)`,内容铺到状态栏底下;但**系统栏图标的颜色
  不会跟着应用背景自动变** —— 默认那套是给浅色背景准备的深色图标。项目从头到尾没设过这个属性。
- **解法**:`window.setWindowSystemBarProperties({ statusBarContentColor, navigationBarContentColor })`,
  深色主题给 `#FFFFFF`、浅色给 `#000000`。主题可在设置里随时改,所以**启动时设一次不够**,
  设置页的 `onChanged` 里要再设一次。
- **验证覆盖到全部四档主题**:深色·水墨(白)、浅色·宣纸(黑)、纯白(黑)、跟随系统(跟 `scheme.isDark`)。
- **教训 / 规律**:
  1. **开了沉浸式,就接管了系统栏的可读性**。凡是把内容铺到系统栏底下的应用,状态栏/导航条的
     内容色都必须自己声明,并且**跟着主题变**;
  2. **"我只看了深色"是个危险的验收范围**。这次是用户主动提醒"亮色你也确认一下" —— 主题类改动
     必须把所有档位都过一遍,浅色/纯白/跟随系统各有可能踩不同的默认值。

### H37. 顶栏图标间距看着不齐:字形墨迹 ≠ 字形盒,且图标等比缩放会同步放大内部留白

- **现象**(用户两次报告):播放页顶栏先是"太挤",加了 40×40 触摸盒后变成"倍速和睡眠之间明显更小、
  其他明显更大"。
- **原因分两层**:
  1. 顶栏里混了两类元素 —— **纯图标**(透明背景)和**药丸**(有背景色)。给图标套 40 宽透明盒后,
     可见间距变成三种:图标↔图标 = space + 两侧各约 9.5 的透明内缩、药丸↔药丸 = space、
     图标↔药丸 = 居中值。实测 27 vs 8,差 3 倍;
  2. 去掉透明盒、间距统一交给 `Row space` 后仍有残差:**字形墨迹比字形盒窄**
     (实测 队列 19.7 / 更多 16.0,盒均为 21),这两处两侧各多出 1–2.5vp 空白。
- **走错的一步**:我先想"把偏窄的图标放大让墨迹填满盒子" —— 方向错了。图标是**等比缩放**的,
  放大时内部留白同比例变大;把「更多」从 21 调到 26,间距反而从 18.7vp **涨到** 20.0vp。
  内缩量是字形自带的比例,只能用**负边距**抵消,不能靠改尺寸。
- **解法**:①视觉盒贴紧内容,间距只由 `Row space` 决定;②触摸区用 `responseRegion` 单独外扩
  (只影响命中测试、不参与布局);③按真机像素实测给偏窄的字形加负边距。
  极差:27/8(差 19vp)→ 3.7 → 5.0(走错那次)→ **1.7vp**。
- **教训 / 规律**:
  1. **"间距不齐"要先分清量的是盒边还是墨迹**。有背景色的元素盒边即可见边,纯图标的可见边是墨迹 ——
     同一个 `space` 在两者之间产生不同观感;
  2. **触摸区和视觉尺寸要分开表达**。用透明 padding 撑触摸区会污染布局节奏;平台一般都有
     只改命中测试的入口(鸿蒙 `responseRegion`);
  3. **像素实测比肉眼调参可靠得多**。这一节四轮里有一轮是反向的,靠"看着差不多"根本发现不了,
     是逐轮量出 17.3/15.0/15.0/18.7 这类数字才定位到字形墨迹这一层。

### H38. 横滑换页时 chips 高亮慢一拍:`Swiper.onChange` 在动画**结束后**才回调

- **现象**(用户报告):音阁分段、发现页分类横滑时页面确实切了,但上方 chips 要等**页面完全滑到位**
  才跟着变,手感总慢一拍。
- **原因**:两处都只挂了 `.onChange((i) => this.seg = i)`。ArkUI 的 `Swiper.onChange`
  是**翻页动画结束**才触发的;动画期间(约 300–400ms)选中态还停在原页。
  Android 侧 Compose 的 `pagerState.currentPage` 过半即更新,所以那边不会有这个滞后。
- **解法**:加 `.onAnimationStart((_i, target) => this.seg = target)` —— 它在动画**开始**时给出
  `targetIndex`,正是手势被确认的时刻。`onChange` 保留(程序化改 index、以及落位后的兜底)。
  **网络加载仍留在 `onChange` 里**:那是"真的停在这一页"之后才该做的事,
  移到 animationStart 会让快速连滑时每划过一页都发一次请求。
- **验证方法(这类瞬态的通用办法)**:把滑动放到后台、隔约 0.28s 再截图,一次调用内完成以避开
  hdc 往返延迟:`uinput -T -m x1 y1 x2 y2 & sleep 0.28; snapshot_display -f ...`。
  拿到的帧里 chips 已切到新页、而内容还在滑动中 —— 这才算证到了时机,
  只在滑完后截图是分辨不出修没修的。
- **教训 / 规律**:
  1. **"XX 回调"要先问它在动作的哪个阶段触发**。同一个手势有 开始 / 进行中 / 结束 三类钩子,
     驱动"选中态"该用开始或过半、驱动"加载数据"该用结束 —— 混用就会一头滞后、一头过度触发;
  2. **验收瞬态问题必须能截到那个瞬间**。否则"修了"和"没修"看到的是同一张图。

### H39. 换了 `startIcon.png` 却不生效:改错了层级 + 资源编译走缓存(两个坑叠在一起)

- **现象**(用户报告):冷启动那一屏一直是 DevEco 模板默认的**蓝底四方块**。检查 `module.json5`,
  `startWindowIcon: "$media:startIcon"` 配置本身没问题。
- **坑一:资源编译走了缓存**。把 `entry/src/main/resources/base/media/startIcon.png` 换掉后
  照常 `assembleHap`,`BUILD SUCCESSFUL` —— 但**解包 HAP 发现里面还是旧图**
  (md5 与源文件不同,尺寸仍是 144×144)。之前几次构建日志里 `CompileResource` 一直是
  `UP-TO-DATE`,替换 PNG 没能让它失效。必须 `rm -rf entry/build .hvigor/cache` 才真正重编。
- **坑二(真正的原因):改错了层级**。清缓存重编后包里**依旧**是旧图。
  逐个算 md5 才定位到:工程里有**两张** `startIcon.png` ——
  `AppScope/resources/base/media/`(应用级)和 `entry/src/main/resources/base/media/`(模块级),
  而 `module.json5` 里的 `$media:startIcon` 实际取的是**应用级那张**。我一直在改模块级的那张。
- **解法**:两处都换(保持一致),重点是 AppScope 那张;然后清缓存重编,**解包验证**包内 md5
  与源文件一致再安装。
- **教训 / 规律**:
  1. **改了资源要解包验证,不能只看 "BUILD SUCCESSFUL"**。资源类改动不会引起编译错误,
     缓存命中时构建照样成功、包里却是旧内容 —— `unzip` + `md5` 三十秒就能证伪;
  2. **同名资源存在多个层级时,先确认"到底取的是哪一个"**。鸿蒙的 AppScope(应用级)会覆盖
     模块级同名资源;Android 的 flavor/主源集、Gradle 资源合并也是同一类问题。
     判据很简单:算包内那张的 md5,拿去和各层级源文件比对,一次就定位;
  3. 这一条我连续错了两次(先怀疑缓存、清了缓存还不行才想到层级),说明**"配置对不对"和
     "取的是哪份文件"是两个独立问题**,要分开验。

### H40. 首次发布开混淆:不要照抄 SDK 模板,并且**必须真机冒烟**

- **背景**:release 构建会 WARN「若需要混淆请在本次构建启用,否则将来可能无法混淆」——
  首版必须开。但 DevEco 模板的 `obfuscation-rules.txt` 默认把四项全开
  (property / toplevel / filename / export),对本工程风险不对等。
- **逐项判断(为什么只开两项)**:
  - ✗ `-enable-property-obfuscation`:ArkUI 的 `@Observed / @ObjectLink / @State` **靠属性名**
    做变更追踪(本工程刚把全部 store 改成 @ObjectLink,见 H26/H27)。属性名一改,最坏是
    「界面不刷新」这类**静默失效** —— 恰好是出包前最难发现的一类。另外直接交给系统 API 的
    对象字面量必须保原名:`SharedData({utd,uri,title})`、`setAVMetadata({assetId,...})`、
    `notificationManager.publish({content:{normal:{title,text}}})`、`WorkInfo({workId,...})`。
  - ✗ `-enable-filename-obfuscation`:路由/入口按**路径**引用(`srcEntry`、`main_pages.json`、
    `loadContent('pages/Index')`),改名出错即启动白屏。
  - ✗ `-enable-export-obfuscation`:单 HAP 收益有限,而 `EntryAbility` / `FeedUpdateExtension`
    由配置按名拉起。
  - ✓ `-enable-toplevel-obfuscation` + `-compact`:不改变任何"按名字找东西"的运行时行为。
- **namecache 要入库**:开 `-print-namecache`,把 `obfuscation-namecache.json` 一并提交;
  后续版本 `-apply-namecache` 复用同一映射,崩溃栈才能还原、增量更新不会因改名全量替换。
- **必须真机冒烟,且要挑"依赖名字"的路径验**:启动 → 榜单加载 → 继续收听(读历史) →
  起播与续播位置 → 音阁五分段 → 历史列表 → 设置页各项读出。本次逐项通过。
- **教训 / 规律**:
  1. **混淆是"改代码"**,编译通过不代表功能没坏 —— 它坏的方式通常是静默的(读不到、不刷新),
     所以验收要**专挑按名字寻址的路径**:序列化字段、响应式属性、按名拉起的入口、传给系统 API 的字面量;
  2. **模板给的默认值是给"典型工程"的**,不是给你的工程的。开每一项前先问:本工程有没有
     依赖这个名字的地方?答不上来就先别开;
  3. **发布前一天不是开激进选项的时候**。要开 property/filename,应当留到有完整回归的版本。

### H41. 榜单快照生成器的两个静默陷阱:抓空即覆盖、"连不上"被判成"死链"

- **背景**:给三端做「内置精选清单」(无网时发现页的兜底内容),用脚本抓 Apple 榜单
  快照打进包(`shared/seed/gen-seed.py`)。
- **陷阱一:某个榜单抓空,脚本照样"成功"**。首跑 12 个榜单齐全,再跑一次
  `us:0`(美区综合榜)返回空,产出的清单**少了一整个分类**,而脚本打印的是
  `✓ 12 个榜单 / 132 条` 这种正常输出 —— 数字变小了,但不看前后对比根本发现不了。
  修法:抓取前读入上一版,**某榜单抓空则保留旧数据**,并在榜单数少于预期时显式告警。
- **陷阱二:把"我这边连不上"当成"源已失效"**。写了个 `--check` 校验 129 个 feedUrl,
  报 13 条失效,差点直接从清单里删掉。实际是**当前环境的出网白名单**把
  audioboom / acast / megaphone 这些 CDN 域名挡了 403(响应体是"域名不在安全策略默认允许"),
  用 curl 手验才发现 —— 真正失效的只有 1 条(podbean 的 404)。
  修法:校验结果分三类 —— `ok`(2xx/3xx)/ `limited`(连不上或被代理拦,**无法判定**)/
  `dead`(明确 404/410);`--prune` 只删 dead,limited 一律保留。
- **教训 / 规律**:
  1. **"数据变少"是最难发现的一类回归** —— 它不报错、不崩溃,输出还是绿色的。凡是"抓取后
     覆盖"的生成器,都要能与上一版比较,并对缩水显式告警;
  2. **探测失败 ≠ 目标失效**。判定别人死活之前,先确认自己这条链路是通的。区分
     "确认失败"与"无法判定",是让自动化不至于误删数据的最小设计;
  3. 同理适用于任何"清理型"脚本:只对**确认成立**的判断动手,不确定的一律保留。

### H42. `HOME=...` 不能给 macOS App 做数据隔离(Application Support 不看环境变量)

- **背景**:要验证「热榜缓存为空时回退到内置清单」这条路径,又不想动用户的真实数据,
  于是用 `HOME=/tmp/xxx ./Reverb.app/Contents/MacOS/Reverb` 想做一次"全新安装"。
- **现象**:日志打出 `订阅=7 历史=22` —— 读的还是真实数据,`/tmp/xxx` 下什么都没生成。
- **原因**:`FileManager.default.urls(for: .applicationSupportDirectory, in: .userDomainMask)`
  走的是 `NSHomeDirectory()`,而非沙箱应用的 `NSHomeDirectory()` 由 **getpwuid(passwd 数据库)**
  解析,**不读 `HOME` 环境变量**。UserDefaults 更是按 bundle id 走 `cfprefsd`,与 HOME 无关。
- **可行做法**:改成"备份 → 移开 → 验证 → 还原 → 逐文件 md5 比对"。本次移开 12 个
  `popular_*.json`,验完还原,md5 全部一致。
- **教训 / 规律**:
  1. 想做隔离验证,**先确认隔离手段真的生效**(看目标目录有没有新文件),再看被测行为 ——
     否则你以为在测"首次安装",其实是在拿用户的真实数据跑;
  2. 只读的验证也可能有写副作用:这次那一趟就把 `popular_cn_default.json` 刷新重写了
     (是一次性缓存,无害,但必须说明);
  3. Android 侧同类验证有更干净的路子:debug 包的 applicationId 带 `.debug` 后缀,
     天然是独立包名 + 空数据,直接就是"全新安装"。

### H43. 一次外部复核判不通过四连:一个 @Builder 值参数 + 一处渲染路径解析,牵出卡死/高 CPU/"点击无响应"

- **反馈原文(鸿蒙)**:① AppFreeze `THREAD_BLOCK_6S`;② 播放常提示"加载失败"偶尔可播、
  收藏按钮点击无响应、长按单集不能加入队列;③ 单线程负载持续 1 分钟超过 70%。
- **「收藏按钮点击无响应」= H29 的漏网之鱼**。`PlayerPage.iconAction` 是 `@Builder`,
  而 `symbol`/`color` 是**值参数** —— ArkUI 的 @Builder 值参数只求值一次,状态变化不重新求值。
  点收藏后 store 确实变了、页面也重渲了,但心形图标冻结在初始值,颜色永不变化。
  **"点击无响应"其实是"视觉无反馈"**,功能一直是好的。队列图标高亮同理失效。
  改法:把 symbol/color 换成闭包 `() => Resource`,一路传到 `Glyph()` 那一层。
- **顺带一个命中区错误**:图标 21 宽、`Row({space:14})`,而 `responseRegion` 给了 43 宽,
  相邻两个的命中区互相压 8vp,重叠处被**后一个兄弟节点**吃掉点击。改成 35(= 21 + 14),
  即向两侧各外扩 7、刚好填满半个间距、互不重叠。
- **卡死与高 CPU 同源:解析跑在渲染路径里**。`PlayerPage.noteText()` 直接调 `htmlToText()`,
  而本页观察 `player`,播放中 500ms 一次 tick 就重渲一遍 —— 于是整段 shownotes
  (有的几十 KB、十道正则)每秒被解析两次。macOS 早先已做过「解析移出渲染路径」,鸿蒙漏了。
  改法:按 episode id 记忆化,只在换集时解析。**缓存字段不能是 `@State`** ——
  在 build 里赋值会再触发一次重渲。
- **高 CPU 的第二个来源:`@Prop` 没有 `@Watch`**。`InkWave.animating` 变化只让 build 重跑,
  而启停定时器是**副作用**,build 不会去调 `applyAnimating()`。原先只在 aboutToAppear /
  onReady / onVisibleAreaChange 里同步,于是**起播过一次,30fps 定时器就永久在跑**:
  暂停不停,离开播放页(组件在导航栈里不销毁)也不停。补 `@Watch` 即可。
- **卡死的第二个来源:主线程同步 IO**。`JsonFile.writeText` 用 `fs.writeSync`,而
  历史每 5s 整份写回、feed 缓存每次解析整份写回、热榜每次刷新整份写回。新增
  `writeJsonDebounced`(400ms 去抖 + fs Promise 异步写),并在 `onBackground`/`onDestroy`
  调 `flushPending()` —— 否则进程被回收会丢最后一次写入(表现是续播位置退回几秒)。
  小而关键的数据(订阅/收藏/印记/下载)**仍走同步**:宁可稳。
- **「长按不能加入队列」是真缺功能**:鸿蒙 `EpisodeListItem` 压根没有长按手势。
  补 `bindContextMenu(..., ResponseType.LongPress)`,并对齐 Android 在全部单集列表接好回调。
- **教训 / 规律**:
  1. **"点击无响应"要先分清是"没执行"还是"没反馈"**。这次代码执行得好好的,只是图标没变色;
     若一开始就去查点击链路会完全找错方向。判断方法:看那次操作有没有**持久化副作用**
     (收藏是否真的写进了 favorites.json);
  2. **同一个坑会在同一个项目里复发**。H29 记的是"@Builder 值参数会冻结",但只修了当时那处;
     这次的正确收尾是**扫一遍全部带参 @Builder**,而不是只修被投诉的那一个;
  3. **外部反馈的三条常常是同一个根因的三种表现**。主线程被占满 → 帧率掉 →
     watchdog 报 THREAD_BLOCK、CPU 报高位、输入被丢弃报"无响应"。先找共因,别急着分头修。

### H44. 渠道报「获取 SSID」不是自己的代码:AndroidX 库调 getActiveNetworkInfo() 也算

- **反馈原文(Android)**:应用获取用户信息 SSID,未在隐私政策说明;且在用户同意隐私政策前获取。
- **先定位到底是谁在调**。自有代码 grep `WifiManager|getSSID|getConnectionInfo` 一处没有,
  也没声明 `ACCESS_WIFI_STATE`。于是直接扫产物 dex(`aapt2` 同目录的 `dexdump -d`),
  只找到一个相关 API:
  ```
  Landroid/net/ConnectivityManager;.getActiveNetworkInfo
  ```
  再按前一行的 `Class descriptor` 反查调用方,得三个,**全是 AndroidX**:
  `media3.common.util.NetworkTypeObserver`、`media3.exoplayer.scheduler.Requirements`、
  `androidx.work.impl.constraints.trackers.NetworkStateTrackerKt`(混淆名 `L1.j`,
  用 release 的 mapping.txt 反查得到)。
  它返回的 `NetworkInfo` 带 `extraInfo`,WiFi 下内容即 SSID —— 厂商扫描按 API 家族判定,
  不看你有没有真去读那个字段。
- **"同意前获取"的具体路径**:`MainActivity.onCreate` 里 `PlayerController.init` 会连
  `PlaybackService` → 创建 ExoPlayer → media3 初始化 `NetworkTypeObserver`;
  `Application.onCreate` 又排了带网络约束的 WorkManager 周期任务。两处都早于同意。
- **改法**:持久化一个 `privacyAccepted`,未同意时界面树**只有同意页**,
  被门控的组件一个都不启动;同意后才 init 播放器与排任务。连 `cancelFeedUpdates` 也要门控
  —— `WorkManager.getInstance()` 本身就会初始化 WorkManager,其 `ForceStopRunnable`
  重排既有任务时会挂约束监听、进而读网络状态。
- **披露而非删除**:这三处都在第三方库里,删不掉(除非自己 fork)。因此在隐私政策里
  如实写明:该字段由系统接口顺带返回、本应用不读取/不保存/不传输、仅用于判断网络类型。
- **教训 / 规律**:
  1. **合规扫描扫的是 API 调用,不是你的意图**。判断"有没有采集"要以**产物里有没有这个调用**
     为准,`grep` 自己的源码会得出错误的"我们没有"结论;
  2. **dex + mapping 是最直接的证据链**:`dexdump -d` 找调用点 → 前一条 `Class descriptor`
     找调用方 → 混淆名用 mapping.txt 还原。比猜依赖快得多;
  3. 第三方库带来的合规项,**能门控就门控、不能删除就披露**,两者都要做:这次同时提了
     "未说明"和"同意前获取",只做一样过不了。

### H45. Android 字符串资源里的裸撇号会让资源编译失败,而报错信息完全不指向它

- **现象**:新增一段英文隐私政策文案后,`values-en/es/fr` 三个文件资源编译失败:
  `java.lang.IllegalStateException: Can not extract resource from ...ParsedResource@xxx`。
  XML 本身用 `ElementTree` 校验是**合法**的,zh 那份也照常通过。
- **真因**:文案里有 `app's` 和 `publishers'` —— Android 资源里裸 `'` 非法,必须写 `\'`。
  gradle 报的那句话与撇号毫无关系;**直接调 `aapt2 compile` 才给出真话**:
  `error: unescaped apostrophe in string`。
- **教训 / 规律**:
  1. 资源编译失败时,**别在 gradle 的输出里找答案**,把那一个文件单独喂给 `aapt2 compile`,
     它会指出行号与具体原因;
  2. 这是 H30 的反方向:H30 是"Android 转义被原样搬进 JSON",这次是"往 Android 搬文案时忘了转义"。
     跨端搬文案,**两个方向都要过一遍转义规则**;
  3. 只有 en/es/fr 失败而 zh 通过,本身就是提示 —— 差异一定在**文案内容**里,不在结构里。

### H46. 合规删减要做到"包里没有",而不是"界面上点不到"

- **背景**:合规口径把「内置内容目录 / 分类浏览 / 内容推荐」判为提供视听节目服务(需前置审批),
  当时于是给大陆商店渠道去掉分类榜、电台、内置精选清单,搜索只收 RSS 地址。
  **这是历史方案;H70 后首版恢复了在线目录与电台。**
- **第一版只做了界面门控**(不渲染分类页、不显示电台按钮)。看着没问题,直到解包一验:
  ```
  dexdump -d classes.dex | grep -c marketingtools.apple.com   # 1
  grep -c itunes.apple.com / api.fyyd.de / gpodder.net        # 各 1
  ```
  **复核时解压安装包就能看到目录接口的地址**,而申报写的是"仅作为 RSS 订阅解析工具"。
- **两个漏得更隐蔽的地方**:
  - 鸿蒙 `aboutToAppear` 里仍无条件 `loadCategory(0)` —— 界面不展示榜单了,**请求照样在发**,抓包即露;
  - `searchEpisodes` 把 RSS 地址当关键词丢给 iTunes(Android 早跳过、鸿蒙没有)——
    既拿不到结果,又平白多一次目录请求。
- **正确做法:用编译期常量在数据层加门**。`BuildConfig.CATALOG` / `Features.CATALOG` 是
  `static final boolean`,R8 能折叠 `if (!CATALOG) return ...` 并把后续整段判死,
  于是 iTunes / fyyd / gpodder / AppleCharts 四个源被整体剔除,四个地址字符串**各 0 次**。
  界面层的门控保留,但它只负责"不显示",不负责"不存在"。
- **教训 / 规律**:
  1. **"功能删掉了"要以产物为准,不以界面为准**。凡是合规性删减,验收方式是解包 grep,
     不是点点看;
  2. 编译期常量比运行时开关值钱:前者能让优化器**删代码**,后者只是不执行;
  3. 顺着这条思路要把"顺带发出的请求"也找一遍 —— 页面不展示的数据,初始化代码可能还在拉。

### H47. 写死在安装包里的 URL:域名没定就别打包

- **现象**:两端的 `privacy_url` / `recommended_opml_url` 是字符串资源,**编译进包**。
  域名从 `cxyxl.eu.org` 换到 `cxyxl.cn` 时,这就意味着改代码 + 重打包 + **重走一轮平台复核**。
- **差点做错的决定**:"先用 eu.org 顶一下,等 `.cn` 的站点登记下来再改"。代价是多一个版本、
  多一轮平台复核,而且登记申报写的域名与 App 实际连的域名**不一致**。
- **正解**:先把域名定下来再打最终包 —— 登记流程要等的那些天足够部署网站,时间上并不冲突。
- **同类的坑**:`.cn` 指向大陆服务器时,站点登记没通过会被直接拦掉(80/443 不通),
  所以"域名买了、站建好了"也不等于 App 能用。
  (登记主体、号段与两套序列这些运营事实见本地 `docs/STORE-OPS.md` 第八节。)
- **教训 / 规律**:
  1. 凡是**编译进包**的外部地址(域名、后端 URL、外链),都属于"改一次就要重发一版"的东西,
     必须在打包前定死;
  2. 判断"能不能先凑合"的标准不是"功能能不能跑",而是"事后修正要付几轮平台复核";
  3. 顺带:静态站的根目录**必须有首页**。内容全放在 `/reverb/` 下会让 `https://域名/` 返回 404,
     而登记平台复核看的就是域名首页,404 容易被判"空壳网站"。

### H48. 鸿蒙资源占位符 `%s` 传 number 会抛异常,后果是**界面上直接显示键名**

- **现象**(真机第一次把「导入推荐订阅」跑通时):导入明明成功了(日志 `导入推荐订阅 15/15`),
  首屏那两行提示却原样显示 **`import_done`** 和 **`starter_have_subs`** 两个资源键名。
- **原因**:`resourceManager.getStringByNameSync(name, ...args)` 对**占位符与实参类型**极其严格:
  文案写 `%s` 而传进去的是 number → **直接抛异常**;而它抛出的错与"压根没这条文案"无法区分,
  于是 `L.f` 走进 catch 分支、按设计返回键名。
  这两条文案是从 Android 移过来的,Android 侧写的是 `%1$d`(Java 的 `String.format`
  对 `%s` 传 int 照常输出,所以那边没事),移植时误写成 `%s`,5 个语言全错。
- **为什么这么久没发现**:这个首屏是"无内容目录渠道"才有的新界面,而导入这条路
  **在真机上从没成功过** —— 域名登记没下来,`cxyxl.cn` 在设备上打不开(见 H47)。
  用 `hdc rport tcp:8099 tcp:8099` + 本机 `python3 -m http.server` 把清单发在本地,
  才第一次走通,一走通就露了。
- **解法**:两条文案 `%s` → `%d`(五个语言);并把 `L.f` 的失败兜底从"返回键名"改成
  **自己填一遍占位符**(支持 `%1$s` 带序号与裸 `%s`/`%d`)。
- **教训 / 规律**:
  1. **"取不到就显示键名"这种自曝式守卫,只有在有人恰好走过那条路时才生效** ——
     否则它就是把键名发给用户。默认行为应当是"降级但可读",错误留在日志里;
  2. 跨端移植文案要**连占位符一起核**:Java/Kotlin 的格式化宽容,ArkTS 的严格,
     同一份文案照抄会在鸿蒙侧炸;
  3. 凡是"依赖外部地址才走得通"的路径,别等外部条件齐了再验 ——
     `hdc rport` / `adb reverse` 把服务端搬到本机,代码路径与线上完全一致。

### H49. 鸿蒙默认放行明文 http(与 Android 相反),但仍要真机验一遍

- **背景**:Android 侧为了让推荐清单里 3 条 `http://` 源能用,必须显式开
  `usesCleartextTraffic="true"`(Android 9+ 默认禁明文)。鸿蒙侧一直不确定对应开关是什么,
  是发布前的已知风险项。
- **实测结论**(BRA-AL00 / HarmonyOS 6.1、API 22 编译):**不需要任何配置**,
  `module.json5` 里没有 network 相关 profile,明文照常放行 ——
  - `@ohos.net.http` 拉 `http://` 的 RSS:3 条源全部解析成功(636 / 384 / 243 集);
  - `AVPlayer` 播 `http://` 音频:`initialized → prepared → playing`,
    服务器侧确认收到设备的音频 GET。
- **验证方法**(不依赖任何线上资源):本机起 `python3 -m http.server`,
  `hdc rport tcp:<port> tcp:<port>` 反向映射,再造一个 enclosure 指向
  `http://127.0.0.1:<port>/x.m4a` 的最小 feed,从搜索框粘地址订阅即可。
- **教训 / 规律**:平台默认策略"猜起来都很像",**但两端相反的情况真实存在**。
  这类"默认值风险"用一个 5 分钟的本地闭环就能验掉,不要留到发布后由用户替你发现。

### H50. ArkUI 里 `width('100%')` 配横向 `margin`,右侧留白会整个丢掉

- **现象**:发现页的搜索框左边有 16vp 留白,**右边圆角直接顶在屏幕边缘**。
  实测左 16.1vp / 右 0。
- **原因**:那个 Row 同时写了 `.width('100%')` 与 `.margin({ left: 16, right: 16 })`。
  ArkUI 的百分比宽度按父容器**内容宽**算出 100%,margin 再加在**外面** ——
  左 margin 把它整块往右推,右 margin 没有东西可顶,于是溢出右缘(被裁掉)。
  两侧留白"看起来只丢了一边",实际是整块偏移。
- **解法**:横向留白交给**外层容器的 padding**,内层保持 `width('100%')` ——
  这样百分比按"父内容宽 − padding"算,两侧自然对称。
- **同类隐患**:同一写法在引导卡上也有一处,而引导卡**只有零订阅的新用户看得到**,
  所以一直没人发现。已 grep 全仓确认只此两处。
- **教训 / 规律**:
  1. **`width('100%')` 与横向 margin 是互斥的两种表达**,凡是同时出现就要怀疑;
  2. 这类"只在某个用户状态下才可见"的界面(新用户引导、空态、错误态)最容易积累版式问题,
     排查时要专门把状态造出来看一遍,不能只看自己日常用得到的那几屏。

### H51. 跨端对齐要分清「可读性常量」与「平台外壳」,两者判据相反

- **背景**:并排比对两端界面时,连着改了好几轮,期间过度矫正了一次 —— 把 Android 的
  Material 规范值(底栏 80、药丸 64×32、搜索图标 24/间距 16)直接抄进鸿蒙,真机上明显笨重。
- **两类东西的判据是相反的**:
  - **字号 / 行高 / 字距 = 可读性常量**,按**绝对物理尺寸对齐**。16sp 的字在两台机器上就该
    一样大,与屏幕宽窄无关。鸿蒙那张 TypeScale 原先逐项比 Android 大 1~2fp,该改;
    Material 每档自带的 letterSpacing 鸿蒙压根没搬(ArkUI 默认字距 0),该补。
  - **栏高 / 图标尺寸 / 内边距 = 平台外壳**,**不照抄像素**,按各自平台规范取值。
    底部页签 Material 是 80、鸿蒙规范是 56;而且本机逻辑宽度 376vp、Android 那台 427dp,
    **同一个绝对值在鸿蒙上占屏比例大 14%**,抄过来必然显大。最后取 64 折中。
  - **图标形状 = 品牌一致性**,取一致。Symbol 字体里没有与 Material 罗盘/唱片盒对得上的
    对等件,索性把 Material 那两枚 SVG 搬进鸿蒙包(并在许可页登记)。
- **另一条反直觉的教训**:「图标看着太大」不一定是尺寸问题。实测鸿蒙字形占药丸比例
  **本来就比 Android 小**(57% vs 62%),真因是**描边空心环 vs 实心块** ——
  同样直径,空心环被眼睛读成"更大"。缩尺寸治不了,换实心才对。
- **教训 / 规律**:
  1. 跨端"对齐"之前先分类:这一项是可读性常量,还是平台外壳,还是品牌标识?判据不同;
  2. **观感问题要先量再改**。本轮几处结论都与直觉相反(字亮度两端相同、字形占比鸿蒙更小),
    靠眼睛猜会改错方向;
  3. 用户说"更精细"未必是"更粗" —— 先确认对方指的是哪个维度,别把形容词直接翻译成参数。

### H52. 长按菜单弹在屏幕边上而不是手指上:两端各有一个"锚点不是手指"的默认行为

- **现象**:同一份长按菜单,Android 一律贴**屏幕最左**弹出,鸿蒙一律在**横向正中**弹出 ——
  按在哪一行、按在行的哪一侧,都不影响它出现的位置,看着像是"跟点击无关的一个面板"。
- **两边的成因不同,但都是「锚点被解释成整行」**:
  - **Android**:`DropdownMenu` 挂在包住整行的 `Box` 上,而 `DropdownMenuPositionProvider`
    的规则是"菜单左缘对齐锚点左缘、菜单顶缘接锚点底缘"。锚点是整行宽,于是永远从最左开始。
    修法**不是**去算 offset:在按下点放一个**零尺寸锚点**(`Box(Modifier.offset { 按下点 })`),
    菜单挂在它上面,向下/向上、向右/向左的翻转全部由 Compose 自己按剩余空间决定。
    按下点用 `PointerEventPass.Initial` 的 `awaitFirstDown` 偷看得到 —— **不能消费事件**,
    否则会和 `combinedClickable` 抢同一个指针,点击和长按一起失效。
  - **鸿蒙**:`bindContextMenu(..., ResponseType.LongPress, { enableArrow: true })`。
    **`enableArrow: true` 是元凶** —— 带箭头时 ArkUI 要把菜单锚到组件上(placement 未给就退化成
    组件正上方),而这一行是整屏宽,结果就是横向居中。改成 `enableArrow: false` 后才走
    LongPress 的默认定位:**在按下点弹出**,贴边自动翻转。
- **教训**:菜单"位置不对"先问**锚点是谁**。锚点是一个整行宽的容器时,任何对齐规则都会
  把它解释成"贴某条边",跟手指无关;把锚点缩成按下点上的一个零尺寸元素,平台自带的
  避让逻辑就能直接用,一行 offset 都不用手算。

### H53. ArkUI 的 `bindContextMenu`:点外部关菜单时,那一下点击**会同时派发给下面的组件**

- **现象**:长按弹出菜单后,点菜单外部区域,菜单消失的同时下面的东西也被点了 ——
  顺手把另一条单集播起来、切了分段、跳进了播放页。Android 的 `DropdownMenu` 自带一层
  透明 Popup 吃掉这一下,鸿蒙没有这层。
- **两种修法,选了后者**:
  1. 每个 `onClick` 开头判一个"刚关过菜单"的时间戳。**实测会漏** —— 菜单是弹在列表上的,
     底下可能是单集行、频道行/宫格、分段 chips、「继续收听」卡、页头图标、搜索框、
     底部页签、迷你播放条……第一版就漏了「继续收听」卡,点一下真把节目播了。
  2. **整屏一层「误触盾」**(`util/TapGuard.ets`):菜单 `aboutToAppear` 升盾、
     `aboutToDisappear` 延时 220ms 撤盾;盾是个全透明 `Row` + `hitTestBehavior(HitTestMode.Block)`,
     挂在 `Index.build()` 最外层 `Stack` 里、盖在 `Navigation` 之上,**连 NavDestination 一起罩住**。
     只有一处,不会漏。
- **两个设计细节**:
  - 盾在菜单**弹出时**就已经在了,所以不依赖"消失回调早于点击派发"这个不确定的时序;
  - 盾自己的 `onClick` 会立刻把自己撤掉 —— 万一某条路径漏了撤盾回调,最坏也只是吃掉一次点击,
    不会把界面永久点不动。**故意不记录「菜单是否打开」**,那种写法一旦漏回调就是全应用点不动。
- **教训**:平台的浮层如果不吃掉"点外部关闭"那一下,不要在业务侧逐个 `onClick` 挡
  (清单永远列不全);挡在**一层之上**,一处就够,并且让这层自己有兜底撤除的能力。

### H54. 编译期常量在鸿蒙上**删不掉代码**:同一套合规门控,Android 达标、鸿蒙不达标

- **背景**:H46 定下的验收标准是「包里没有」而不是「界面上点不到」,当时两端都在数据层
  加了 `if (!CATALOG) return ...`,Android 解包复验四个目录接口地址各 0 次,就此收工。
  **鸿蒙那一侧当时只验了 Android 的 dex,没解 hap**。
- **这次解包一验**(`strings modules.abc | grep -i itunes`),鸿蒙 release 包里躺着:
  `ITunesSource` / `AppleChartsSource` / `FyydSource` / `GpodderSource` 四个类,以及
  `https://itunes.apple.com/search…`、`https://rss.marketingtools.apple.com/…`、
  `https://api.fyyd.de/…`、`https://gpodder.net/search.json?q=` 四个地址。
- **原因**:`Features.CATALOG = false` 只是**运行时不走**。R8 能把 `static final boolean`
  折叠、把整段判死后删掉,**ArkTS / hvigor 没有等价的 dead code elimination** ——
  常量为 false 也照样编进 `modules.abc`。混淆只改名字,不删分支。
- **修法**:把那四个类**整个移出编译树**(`entry/src/main/ets` → `harmony/shelved/net/`,
  见该目录 README),`PodcastRepository` 的三条降级链改成直接返回空并留 `TODO(catalog)`。
- **同一个坑的第二处**:`const SOURCES = Features.CATALOG ? ['…iTunes…','fyyd.de','gpodder.net'] : [...]`
  —— **三元的两支都会被编进产物**,于是许可页那三个名字还在。凡是"按渠道二选一"的字面量,
  在没有 DCE 的平台上都等于两份都打进去了。
- **教训 / 规律**:
  1. **合规删减的验收要按平台各做一遍**,别把 Android 的解包结论套到鸿蒙上 ——
     同一份写法在两个工具链下的结果可以完全相反;
  2. 判断"这段代码会不会进包",标准不是"会不会执行",而是**这条工具链有没有 DCE**。
     没有的话,唯一可靠的办法是**不让文件参与编译**;
  3. 三元 / `?:` 里的另一支也是代码。要"某渠道里根本不存在"的字面量,不能靠分支表达。

### H55. 手机上跑 whisper 到底多快:先量,再决定内置哪个模型

- **背景**:Android 端要自带离线语音识别(默认渠道),模型随包内置。选 tiny 还是 base
  不能拍脑袋 —— 一个 31 MB / 一个 57 MB,速度差一倍,中文质量差得更多。
- **量法**(不必先写 JNI,这一步纯命令行):用 NDK 交叉编译 whisper.cpp 的 `whisper-cli`
  为 arm64,连模型和一段**真实中文播客**的 16k 单声道 WAV 一起 `adb push` 到
  `/data/local/tmp`,`adb shell time ./whisper-cli …` 直接读墙钟。
- **实测**(OnePlus / SM8845 / 4 线程 / 真实中文播客):

  | 模型 | 5 分钟切片 | 整集 33.5 分钟 | 推算 1 小时 |
  | --- | --- | --- | --- |
  | tiny-q5_1(31 MB) | 35.1 s(8.5× 实时) | — | ≈ 7 分钟 |
  | base-q5_1(57 MB) | 65.3 s(4.6× 实时) | 8 分 17 秒(4.0× 实时) | ≈ 15 分钟 |

  **短切片会高估速度**:同一模型 5 分钟时 4.6×、跑满 33 分钟只有 4.0×,差的 12% 是降频。
  所以"1 小时要多久"这类结论必须用**长音频**量,拿 30 秒的样本乘出来会偏乐观。
- **质量差别比速度更值得看**。同一段话:tiny 出「明明忽悔的汽床」「包子满头白揉机担」
  「并米排骨汤」,还混进繁体字;base 出「你迷迷糊糊的起床」「包子馒头白州鸡蛋」
  ——剩下的错基本只是同音词。**选了 base**:多 26 MB 换来"能读"。
- **两个必须在业务侧挡掉的模型行为**(都是真实数据里撞上的,不是理论风险):
  1. **复读**:片头音乐/口号处会把同一句吐十几遍(实测「原来是这样」连出 6 次)。
     连续相同的句子丢掉;分块识别时 `no_context = true` 也能少一部分;
  2. **幻觉署名**:片尾静音处凭空出一句 `(字幕:J Chong)`。括号类标记整句丢掉,
     长度阈值要放宽到 20 字以上 —— 按 10 字设会漏掉这一条。
- **教训 / 规律**:
  1. 模型选型是**实测题**,不是查表题。而且要量在**目标机器 + 目标语言 + 真实素材**上;
  2. 拿短样本外推长任务会偏乐观,降频只有跑够时间才出现;
  3. 端上模型的输出**必须过一道业务侧的清洗**:复读与幻觉是常态,不是异常。

### H56. whisper 的 `detect_language` 不是「顺便自动判断语言」,是「只判断、不转写」

- **现象**:真机上点「生成逐字稿」,一句都没有,界面显示「转写失败」,而**日志里一个错误都没有**
  —— 不是 `whisper_full` 返回非 0,也没有 native abort / OOM / UnsatisfiedLinkError,
  `.so` 与模型都确认加载成功。
- **定位靠一行日志**:把每块的「样本数 → 句数 / 耗时」打出来,立刻看出问题:

  ```
  块 startMs=0 样本=1931840 → 0 句,耗时 1607ms
  ```

  **120 秒的音频 1.6 秒就"跑完"了** —— 75 倍实时,而同机同模型实测只有 4~8 倍。
  快到不可能,就说明它压根没干活。**"没报错但快得离谱"比报错更值得警觉。**
- **根因**:`whisper_full_params.detect_language` 的语义是
  **「检测出语言就返回」**(exit after detecting language),不是"顺便自动判断"。
  我按字面理解写了 `wp.detect_language = lang.empty()`,而界面语言是「跟随系统」时
  上层传的正是空串 —— 于是每块都只做语言检测就返回,0 句,不报错。
- **正确写法**:`detect_language` **恒为 false**;要自动判断就把 `language` 传字符串
  `"auto"`(**不能传 nullptr**)。
- **顺带一个反直觉的实测**:同机同模型,**应用内比命令行快近一倍**(8 倍实时 vs 4.6 倍)。
  差别来自分块识别必须开的 `no_context = true` —— 少了跨块上下文提示,质量略降、速度大涨。
  所以"官方 benchmark 的倍率"不能直接套到自己的参数组合上。
- **教训 / 规律**:
  1. 端上模型的参数名**别按字面猜语义**,拿不准就去看实现里那几行怎么用它;
  2. **给每一步打上"输入量 → 输出量 / 耗时"**。这类"静默不干活"的故障,靠错误日志永远看不出来,
     靠吞吐量一眼就看出来;
  3. 换了参数组合,**速度结论要重新量**。

### H57. whisper 转中文默认出**繁体**,而且给了提示词之后句子会变得很长

- **现象一**:简体界面下转出来整屏繁体字(「原來是怎樣」「我們假設今天晚上的12點開始」)。
  这不是模型坏了,是 whisper 对中文的既有倾向 —— 不给任何提示时它偏向繁体。
- **修法**:给一句**同字体的提示词**(`initial_prompt = "以下是普通话的句子。"`),
  繁体界面反过来给繁体提示。注意两点:
  - `initial_prompt` 与 `no_context = true` **不冲突** —— 后者清的是跨块上下文,
    提示词是每块都重新给的;
  - 顺带要把「跟随系统」在业务层**解析成真实语言**再传下去。传空串让引擎自己猜,
    既容易猜成繁体,又会让缓存 key 退化成 `auto`(换了系统语言还命中旧稿)。
- **现象二(修完现象一之后才出现)**:句子突然变得很长 —— 3 分钟音频只切出 21 句,
  一句两三百字。因为提示词带了标点,模型跟着输出整段带标点的长句。
  一段三百字会**整段高亮二十多秒**,跟读效果等于没有。
- **修法**:业务侧再切一刀。这条规则**与官方逐字稿的长 cue 切分是同一个问题**,
  所以抽成了共用的 `util/TranscriptLines.kt`(中文一行 24 字、西文 42 字符 ——
  汉字宽得多,42 个汉字在手机上要占三行;时间按字符占比线性插值)。切完 42 句。
- **教训 / 规律**:
  1. 端上模型的**字体/风格倾向**要当成需求处理,不是"模型的事";
  2. **修一个行为常会换出另一个行为**(给了标点提示 → 句子变长)。改完要把整条链再看一遍,
     别只验刚改的那一处;
  3. 两处都在做"把长文本切成能读的一行",那就该是一份实现。发现第二处时正是抽公共的时机。

### H58. whisper 的 token 会把一个汉字劈成两半,半个字符交给 `NewStringUTF` 会**直接 abort 进程**

- **现象**:用户报「播一半应用会自动退出」。系统退出记录(`dumpsys activity exit-info`)显示
  `reason=5 (APP CRASH(NATIVE))`,崩溃缓冲里是:

  ```
  Fatal signal 6 (SIGABRT) … DefaultDispatch
  Abort message: 'JNI DETECTED ERROR IN APPLICATION:
    input is not valid Modified UTF-8: illegal continuation byte 0
    from java.lang.String …WhisperEngine.nativeTokenText(long, int, int)'
  ```
- **根因**:whisper 用**字节级 BPE**,一个汉字 3 个 UTF-8 字节,**可能被劈到两个 token 里**。
  把这半个字符的 `char*` 交给 `env->NewStringUTF()`,JVM 判定为非法 Modified UTF-8 并
  **abort 整个进程**(debug 包开着 CheckJNI 必崩;release 下不崩,但会得到一段坏字符串 ——
  那更难查)。
- **修法**:token 的拼接与校验都放 C++ 侧,**攒够字节形成完整字符才交出去**
  (`nativePrepareWords` + `nativeWordText`);JNI 边界上所有字符串统一走一个
  `safeString()`,验不过就给空串,**绝不让它 abort**。
- **教训 / 规律**:
  1. **凡是把模型/解析器产出的字节直接 `NewStringUTF` 的地方,都是一颗雷**。
     字节级 tokenizer 天然会产出不完整字符;
  2. `NewStringUTF` 的失败方式是**杀进程**,不是抛异常 —— 上层 `try/catch` 一点用都没有;
  3. 用户说「应用自动退出」时,先看 `dumpsys activity exit-info`:它会直接告诉你是崩溃、
     被系统回收、还是**被一次覆盖安装打断**(reason=16 PACKAGE UPDATED)。这次三种都出现了,
     而其中一种是我自己在用户使用期间 `adb install` 造成的 —— 别把那个也算成 bug。

### H59. `flash_attn` 默认开着,会**静默关掉** whisper 的词级时间戳

- **现象**:开了 `dtw_token_timestamps` 之后,`whisper_token_data.t_dtw` 与 `t0` **全是 -1**,
  界面上逐字高亮完全不动;但一切正常,不报错。
- **根因**:`whisper_context_default_params()` 里 **`flash_attn` 默认是 `true`**,而库里有一句

  ```
  dtw_token_timestamps is not supported with flash_attn - disabling
  ```

  于是 DTW 被悄悄关掉。**这句 WARN 库是打了的**,但它默认写 stderr —— 在 Android 上等于扔掉。
- **修法**:开 DTW 就必须 `cp.flash_attn = false`;并且**把库的日志接到 logcat**
  (`whisper_log_set` → `__android_log_write`)。后者不是锦上添花:装上之后
  `flash attn = 0 / dtw = 1` 这两行自述直接可见,这类"库已经告诉你了而你没听见"的坑就没了。
- **顺带修正一个我自己下错的结论**:此前测出"DTW 几乎不花时间"是**错的** ——
  那几次 DTW 根本没生效。真实代价见 H55 表格下方与 TRANSCRIPT.md:**多约 70% 时间**。
- **教训 / 规律**:
  1. **接第三方库的第一件事就是把它的日志接出来**。没接日志的排查等于蒙眼;
  2. 参数之间可能互相排斥,而库往往选择"静默降级"而不是报错。开了某个开关之后,
     要**验证它真的生效**(这里就是打印库的自述行),不能只看"没报错";
  3. 性能结论必须绑定配置。"开着某功能测出来一样快"的第一嫌疑是**那个功能没开**。

### H60. 逐字高亮"跟语音完全对不上,而且根本不跟着走" —— 三个独立缺陷叠在一起

- **现象**(用户报的):点「生成逐字稿」后要等很久才出字;出字之后高亮的位置跟语音对不上,
  而且高亮**不会随播放推进而切换**。
- **根因**:三件事,彼此无关,凑在一起就是上面那个观感。**一个一个查,不要指望一个根因解释全部**:

  1. **自动滚动把自己判成了"用户在滚"**。`TranscriptList` 里原本是
     `LaunchedEffect(listState.isScrollInProgress) { if (…) userScrolledAt = now }`,
     用来实现"手指一碰就停止跟随、4 秒后恢复"。但 `animateScrollToItem` **自己也会**把
     `isScrollInProgress` 置真 —— 于是自动滚动触发了抑制,4 秒内不再跟随;4 秒后滚一次、
     又把自己禁言 4 秒。净效果是**每 4 秒才跳一下**,看上去就是"压根不跟着念"。
     修法:只认真正的手指拖动 —— 收 `listState.interactionSource.interactions` 里的
     `DragInteraction`,程序化滚动不产生这种事件。
  2. **词级时刻用错了来源**。当时取 whisper 的 DTW 结果(`t_dtw`),实测**整体偏晚 0.4~0.9 秒**;
     而且库里那段赋值有**一格错位**:`if (v != last_v)` 里 `tok_i` 比 `v` 慢一步,
     写进 token k 的其实是"token k+1 开口的时刻",原样当起点用等于整体晚一格,
     末尾那个 token 还永远拿不到值(留 -1)。改用 whisper 自带的 `token_timestamps`(`t0/t1`):
     准到 ±150 ms、**快 43%**,还能让 flash attention 常开(于是逐字高亮不再有额外耗时)。
  3. **首块 120 秒 ⇒ 首字要等二十多秒,而且那段等待是一片空白**。
     `State.Running` 分支直接渲染 `TranscriptList`,句子还没有时那就是个空 `LazyColumn` ——
     用户看不出是在算还是坏了。修法:块长改成 30 → 60 → 120 秒逐块放大(30 秒是下限,
     whisper 内部按 30 秒窗处理,喂更少只是浪费),并且"Running 且还没有句子"时显示进度。

- **另一处埋着的同类地雷(顺手拆了)**:渲染判断"读到哪个词/哪句"用的是
  `indexOfLast { it.startMs <= nowMs }`。这个写法**只在起点单调不减时才正确** ——
  队尾只要混进一个异常小的值(比如某个 token 没算出时刻、退化成 -1 → `-10ms`),
  它就永远满足条件,`indexOfLast` 恒定命中那一条,**高亮钉死不动**。
  与其在渲染侧每帧兜底,不如在数据出口处保证不变式:C++ 侧 `tidyWords` 出口保证
  "时刻全部 ≥ 0、起点单调不减",并给缺失值做前后补齐。
- **缓存必须带版本号**。时刻算法改了,而用户手机上**已经生成的稿是按旧口径存的**,
  界面无从分辨、只会照着显示 —— 修完装上去仍然"对不上",而且用户没有清缓存的入口自救。
  `TranscriptStore.CACHE_VERSION` 一变,旧稿自动丢弃重转。
- **教训 / 规律**:
  1. **一个现象可能是多个缺陷的和**。"完全对不上"是时间轴的错,"不跟着走"是滚动逻辑的错 ——
     只修一个,用户仍然会说"还是不行";
  2. **别用"程序化操作也会触发的信号"去识别用户操作**。`isScrollInProgress`、
     `onValueChange` 这类信号分不清是谁干的;要用只有人能产生的事件(拖拽、按压);
  3. **算法换口径就得给持久化数据加版本号**,否则修复被旧数据挡在门外;
  4. **这一条的结论全部是量出来的,不是读代码猜的**。为此专门写了主机端探针
     `android/tools/asr-probe/`(与 JNI 同一套参数,把每个 token 的时刻打出来),
     真相则用**切片法**定:把音频截到 0→1.0 / 0→1.3 秒分别识别,看第几个字还在里面。
     这类"时间轴对不对"的问题在真机上完全看不见中间值,**必须先造出能看见的工具**。

### H61. 鸿蒙接 native 模块(NAPI)的四个卡点

做逐字稿时鸿蒙端必须写 native(ArkTS 层没有解封装/解码 API),接线上连撞四处,逐条记下:

- **`napi_module` 找不到**。`#include <js_native_api.h>` 里没有它,报
  `unknown type name 'napi_module'`。它在 **`napi/native_api.h`** 里。
- **`LOG_TAG` 重定义警告**。hilog 的 `log.h` 自己先 `#define LOG_TAG NULL`,
  所以自定义之前要 `#undef LOG_TAG`。不致命,但会淹掉真正的警告。
- **ArkTS 不能 `requireNapi`**,报 `Cannot find name 'requireNapi'`。
  正路是把 .so 声明成一个**类型包**:`cpp/types/<libname>/` 下放 `index.d.ts` +
  `oh-package.json5`(包名就叫 `libxxx.so`),在模块的 `oh-package.json5` 里
  `"libxxx.so": "file:./src/main/cpp/types/libxxx"`,然后 `import x from 'libxxx.so'`。
- **声明完还是报 `arkts-no-any-unknown`**。因为 `file:` 依赖**要跑一次 `ohpm install`**
  才会在 `oh_modules/` 里建好软链;没跑之前类型解析成 `any`。
  症状很误导 —— 看着像 `index.d.ts` 写错了,其实是没装。
- 另外 ArkTS **不允许无类型对象字面量**(`arkts-no-untyped-obj-literals`):
  想把几个 native 函数包成一个对象存起来是不行的,直接调 `import` 进来的函数即可。

**教训**:鸿蒙的 native 接线错误信息普遍指向"下游症状"而不是根因(缺 install → 报 any;
缺头文件 → 报 unknown type)。**遇到类型解析成 any 先想依赖装没装**,再怀疑 d.ts 写法。

### H62. 鸿蒙系统语音识别(Core Speech Kit)真机实测:**不足以做播客转写**

装到真机上逐个修完接线问题之后,结论是这条路本身不够用。按顺序记下四个坑与最终结论:

1. **同步编解码模式必须显式打开**。以为"不注册回调即同步"是错的 ——
   每次 `OH_AudioCodec_QueryInputBuffer` 都返回 `{QueryInputBuffer} not in sync mode`。
   正解:配置阶段 `OH_AVFormat_SetIntValue(fmt, OH_MD_KEY_ENABLE_SYNC_MODE, 1)`(默认 0)。
   **顺带暴露了一个自己的错**:外层"攒够就返回"的循环没有失败闸,取不到数据就空转,
   几千行错误日志刷屏、调用线程再也回不来。**任何 pump 循环都要有"连续 N 轮无进展就放弃"**。
2. **别自己拼解码器配置,把轨道格式原样交给它**。自己只填采样率/声道数,缺了
   `aac_is_adts` 与 `OH_MD_KEY_CODEC_CONFIG`(MP4 里的 AudioSpecificConfig),
   于是 `CheckAdts: aac_is_adts parameter is missing` + 每帧 `Invalid data found when
   processing input`,一个采样都出不来。用 `OH_AVSource_GetTrackFormat` 的结果去 Configure,
   只补一个同步模式开关即可。
3. **监听器只能绑一次,而且 `startListening` 之后必须等 `onStart` 才能喂。**
   每窗重新 `setListener`,会在上一窗 `onComplete` 还在派发时换掉监听器 ——
   **进程直接崩**在系统的 `libspeechrecognizer.z.so`(`AsrEngine::WritePcm`)。
   不等 `onStart` 就喂,则每帧报 `1002200010 Write audio failed because the start
   listening is failed`,整窗 0 句。改成"绑一次 + 当前窗指针 + 等 onStart"之后不再崩。
4. **然而识别质量不够用**。默认(短语音)档一次会话只认**第一句**,检测到句末静音就收工:
   10 分钟的中文单集 → **14 行**,内容多是「。」「能力。」「有八。」这类碎片。
   试着走"长语音"档(库里有 `SpeechRecognitionLong` / `ParseAsrLongEngineOptions`,
   `strings` 能抓到 `recognizerMode` / `maxAudioDuration` / `vadBegin` / `vadEnd` 这些**参数名**,
   但抓不到**取值字符串**),传 `recognizerMode: 'long'` 之后变成 **0 行**。
   拿不到官方取值口径就不该继续瞎猜,已回退默认档。

**结论**:Core Speech Kit 的离线档是给"短语音输入/命令词"设计的,不是给长音频转写的。
鸿蒙端要真正可用的本机转写,得走 Android 那条路(把 whisper.cpp 链进已经建好的
native 模块,见 TRANSCRIPT.md 的迁移路径);官方逐字稿那条路不受影响,已经可用。

**教训 / 规律**:
1. **"系统有这个 API"不等于"这个 API 能干这件事"。** 接口形状对得上(喂 PCM、出文本)
   不代表适用场景对得上 —— 短语音引擎的 VAD 会在第一句结束就收工。
   **这种判断只能靠真机上跑真实素材**,读文档和读头文件都看不出来。
2. **不要靠 `strings` 猜出来的参数名去传值。** 名字能抓到、取值抓不到时,传了往往比不传更糟
   (这里从 14 行变成 0 行)。
3. 前三个坑的错误信息都指向下游症状(not in sync mode / Invalid data / write failed),
   根因分别在"没开开关""配置不全""时序不对"。**逐个二分,不要指望一次改对。**

### H63. 签名口令进了 43 个历史提交 —— 而泄露它的是**构建缓存**,不是配置文件本身

- **现象**:准备开源前扫全历史,`harmony/build-profile.json5` 在 **43 个提交**里带着
  release 签名的 `storePassword` / `keyPassword` / `keyAlias`。
  该文件后来已加进 `.gitignore`,但**加之前的提交永久留在历史里**。
- **更隐蔽的一处**:清掉那个文件之后再扫,口令串**仍有 42 处命中** ——
  来自 `harmony/.hvigor/outputs/sync/output.json` 与 `harmony/.hvigor/cache/task-cache.json`。
  **hvigor 的构建缓存把整份签名配置(含口令)内嵌进了缓存文件。**
  `.gitignore` 里只有 `harmony/.hvigor`,而根目录、`android/`、`entry/src/main/ets/` 下
  还各留过一个 `build.log` —— 忽略规则不是全层级的。
- **严重程度要说准**:`.p12` 私钥本体**从未入库**,所以光有口令签不出包。
  但口令的作用就是保护私钥,一旦私钥从别处泄露,这层保护已经不存在。
  DevEco 存的是加密形式,**不要假设它安全** —— 行业惯例是等同明文对待。
- **修法**:`git filter-repo --invert-paths` 清理路径,分三类:
  1. 口令载体:`harmony/build-profile.json5`、`harmony/.hvigor`、`*.hvigor/*`;
  2. 个人数据:发布截图(48 张真实订阅与收听记录);
  3. 误提交的二进制:`store-android.zip`、`entry-default-*.hap`、`harmony/entry/build`。
  再用 `--replace-text` 擦掉历史里的本机绝对路径与分发平台的证书标识。
  结果:`.git` 从 **145 MB → 3.7 MB**,提交数 203 → 198(5 个只碰被删路径的提交变空被剪掉)。
- **教训 / 规律**:
  1. **扫历史不能只扫「敏感文件名」,要扫「敏感字符串」。** 按文件名扫只会找到
     `build-profile.json5`;按口令串扫才会发现构建缓存也带着它。
     决定性的一步是**先看本地那份未入库的文件里口令长什么样,再拿那个串去搜全历史**。
  2. **构建缓存 / 日志 / 同步产物是二等泄露源。** 它们会把配置内容复制一份进去,
     而人只会去 gitignore「配置文件」。忽略规则要写成全层级(`.hvigor/` 而不是 `/.hvigor`)。
  3. **`.gitignore` 是从现在开始生效的,不追溯。** 加规则那一刻之前的提交不会被清理。
  4. **不可逆操作前先做 bundle 备份**(`git bundle create ... --all`),
     并把仍需保留的未追踪文件(这里是发布截图)另拷一份 —— 历史重写会把工作区重置到新 HEAD。
  5. **别在文档里写会自动漂的计数。** 这次清理让文档里的「199 次提交」直接失效,
     当时的处理是「一并改」—— 但那治不了根:提交数每提交一次就过期一次,
     靠人维护等于给自己派一个永久任务。后来把 README / AGENTS / HISTORY 里的提交数
     **删掉**了。判据是**「它会不会自己变」**:提交数会,所以不写;
     踩坑条数与语种数由人显式增加、增加时本来就要动文档,所以可以写。

### H64. 「下拉刷新的 loading 很卡」之一:**高频状态挂在被观察对象上 = 整页重建**

- **现象**:鸿蒙端下拉刷新时转圈动画非常卡。用户描述是"loading 非常卡",
  但真正的范围比这句话大 —— 只要在播放,**任何**页面都在掉帧,下拉刷新只是最看得出来的那一刻
  (转圈动画和刷新手势要的正是那条被占满的 UI 线程)。
- **量化基线**(用系统自带的两把尺,不靠手感):
  ```
  hdc shell hilog -x | grep -c ProcessJank                     # 系统 jank 事件
  hdc shell hilog -x | grep -c "AceTextField.*SetIsEnable"     # 整页重建次数(搜索框每次重建都打一行)
  ```
  | 场景 | jank | 整页重建 |
  |---|---|---|
  | 播放中静置 10 秒 | 62 | 45 |
  | **暂停后**静置 10 秒 | 0 | 0 |
  | 边播边下拉刷新(14 秒) | 124 | 131 |
- **根因**:`PlayerController` 上加了 `@Observed`,而 **ArkUI V1 的观察粒度是整个对象** ——
  它任何一个字段被赋值,所有 `@ObjectLink` 持有者都会重跑 `build()`。
  而 AVPlayer 的 `timeUpdate` **约每 100ms 一次**,回调里就一句 `this.positionMs = t`。
  于是播放中发现页每秒重建约 10 次,连搜索框 `TextInput` 与两个列表的 `ForEach` 一起重建。
- **还叠了两处同源问题**:
  1. 500ms 的 ticker 每跳都 `notify()`,把根组件 `Index` 的 `@State tick` +1(第二条重建通道),
     并顺带每半秒往 AVSession 推一次状态(日志里伴随 `SetAVPlaybackState in syncExecutor timeout`);
  2. 挪走 `positionMs` 之后重建只降到 2Hz,剩下的是 ticker 里两行**不起眼的记账**:
     `tickCount += 1`、`lastCountedPosMs = …`,以及 `ListenStatsStore.pendingMs += delta`。
     **ArkUI V1 不区分 private** —— 私有字段赋值一样触发通知。
- **修法**:高频可变量一律搬进**普通对象**(嵌套的非观察对象不参与依赖收集):
  新增 `playback/PlaybackClock.ets` 承载 `positionMs` / `ticks` / 收听计数基线,
  `ListenStatsStore` 的未落盘累计量同理;`positionMs` 保留为 **getter**(getter 不是自有属性,
  读它不建立依赖),既不破坏调用方也不再触发重建。
  然后让需要连续进度的界面**各自按自己的频率轮询**:
  进度条拆成独立组件 `SeekBar`(250ms,只重渲自己)、迷你条细线 1s 且按整数百分比去重、
  逐字稿沿用原有的 80ms 外推心跳。ticker 不再 notify;AVSession 改为
  「状态签名变了 or 实际位置与系统外推值差 >1.5s」才推(seek/续集/缓冲都落在后一条里)。
- **复测**:播放中静置 10 秒 = **0 jank / 1 次重建**;边播边下拉刷新 = **0 jank / 4 次重建**;
  AVSession 推送 20 次 → 0 次,`syncExecutor timeout` 4 次 → 0 次。
  锁屏/控制中心的进度仍会自己走(20 秒后 09:26 → 09:47),证明系统外推是可靠的。
- **教训 / 规律**:
  1. **判断一个字段能不能留在 `@Observed` 类上,看的不是"界面用不用它",而是"它多久变一次"。**
     一秒变十次的东西挂上去,等于把整棵树按 10Hz 重建。
  2. **ArkUI V1 的观察粒度是对象,不是字段,而且不区分 private。** 与 Compose 的
     `mutableStateOf`(字段级)不是一回事,移植时不能照搬"反正它是私有的"这种直觉。
  3. **高频刷新要下沉到最小的组件**:把进度条拆出来之后,进度更新只重渲那一小块,
     而不是包含轮播三页 + 水墨画布 + shownotes 长文的整个播放页。
  4. 一处代价要记住:离屏常驻的剪藏卡原本靠"整页高频重建"顺带刷新时间戳,
     重建停掉之后必须在按下剪藏时显式取值并让出一帧 —— 否则截出来的图停在旧时刻。
     (顺带让语义更对:剪藏此刻应该是**按下的那一秒**,不是渲染发生的那一秒。)

### H65. 「下拉刷新的 loading 很卡」之二:**RSS 解析占住 UI 线程近两秒**,而 jank 计数看不出来

- **现象**:修完 H64 之后,**暂停播放**再下拉刷新,转圈依然卡。
  而 `ProcessJank` 计数只有 5 —— 差点据此得出"刷新本身不卡"的错误结论。
- **为什么计数会骗人**:`ProcessJank` 记的是**jank 事件**,不是掉帧数。
  一次 1.8 秒的停顿和一次 100ms 的停顿都只记 1 条。**用它比较相对量可以,用它判断"卡不卡"不行。**
- **定位手段**:在 `RssParser.parse` 里把耗时打进已有那行日志(`解析耗时=Xms 字节=N`)。
  一量就清楚了:
  ```
  集数=1026  解析耗时=1833ms  字节=8550145   ← 8.5 MB 的 RSS
  集数=623   解析耗时=707ms
  集数=261   解析耗时=488ms
  ```
  一轮 15 源刷新里 **约 4.5 秒是纯解析**。
- **根因**:ArkTS 没有协程。`Http` 的等待是异步的没错,但
  **`XmlPullParser` 的逐 token JS 回调、每集一遍的 `htmlToText`(十来道正则)、
  上千个对象的构造全是同步 JS —— 谁调用就占谁的线程**,而调用方是 UI 线程。
  另有一处同类:`FeedCacheStore.put` 每次都把整份缓存(20 频道 × 50 集,约 600KB)
  重建成 JSON 对象再 `stringify`,**一轮刷新做 15 遍**;去抖只去掉了写盘,没去掉序列化。
- **修法**:
  1. 新增 `net/FeedTask.ets`,用 `@Concurrent` + `taskpool` 把**取源与解析整段**放进子线程。
     连网络一起搬(而不是只搬解析):这样 8.5 MB 的 XML 字符串压根不出现在 UI 线程的堆上,
     跨线程只传 url 进去、传结果出来。子线程不可用时**回落本线程解析**,宁可卡一下也不失效。
  2. `JsonFile.writeJsonDebouncedLazy(name, () => Object)`:传"怎么取值"而不是值,
     把序列化也推迟到去抖到期,同一文件连续 N 次写只做一次。
     `feed_cache` / `history` / `inbox` 三处大对象改用它。
- **复测**:暂停下拉刷新 **jank 0**;边播边刷新 **jank 0**;解析日志的线程号不再是主线程。
  单源解析耗时反而变长(1833ms → 2606ms,多个子线程抢核),但**不占 UI 线程**,
  整轮刷新的墙钟时间基本不变。
- **教训 / 规律**:
  1. **"异步"只保证等待不阻塞,不保证计算不阻塞。** `await` 回来之后的那段同步解析
     照样占满调用线程 —— 这是 ArkTS 与 Kotlin 协程(可以 `withContext(Dispatchers.IO)`)
     最容易踩错的差别。
  2. **别信粗计数器,要量绝对耗时。** 先造能看见的东西(这里就是往已有日志加一个 `Date.now()` 差),
     再谈结论 —— 同 H60 的教训。
  3. **去抖要连"生成数据"一起去抖。** 只去抖 IO 而每次都序列化,等于没解决 UI 线程上的那部分。
  4. 一处已知代价:子线程里的 `Log` 走 hilog 照常可见,但 `Log` 的内存环形缓冲是每线程一份,
     **设置页「分享日志」拿不到子线程那些行**。

### H66. 三端扫一遍「UI 线程上的耗时操作」——同一类毛病,三端各犯一种

- **起因**:H64/H65 修完鸿蒙的下拉刷新之后,顺着问「**还有没有别的**」,
  按五类扫了三端:同步文件 IO / 大对象序列化 / 解析与正则 / 图像编解码 / 渲染路径里的重循环。
  结论:**有,而且分四族**。这条记的是扫查方法与各族结论,具体修法见对应提交。
- **族一(鸿蒙独有,最重)**:
  1. `DownloadManager` 用 `expectDataType: ARRAY_BUFFER` 把一集**几十 MB 整块读进 JS 堆**,
     再 `fs.writeSync` 一次写完 —— 内存尖峰 + UI 线程上的大写。
     Android 侧本来就是 `Dispatchers.IO` + `byteStream()` 流式,macOS 是
     `URLSession.downloadTask` 由系统托管落盘,**只有这一端是整块同步写**。
     改用 `requestInStream` + `dataReceive` 分片 + Promise 串行链序列化写。
  2. 逐字稿缓存(**本应用最大的一份 JSON**,词级稿约 1 万条条目 / 600 KB)
     `readTextSync` + `JSON.parse` / `stringify` + `writeSync` 全在 UI 线程;
     官方稿的解析与断行合并同样。→ 各自搬进 `@Concurrent` + taskpool,带回落本线程的降级。
  3. 设置页 `recomputeSizes()` 一进页面就 `listFileSync` + 逐文件 `statSync`(O(N) 同步 IO)。
  4. 备份的 `JSON.stringify(root, null, 2)` / `JSON.parse` 在 UI 线程,
     且导入流程把同一个大 JSON **解析了两遍**(探测分区一遍、应用一遍)。
- **族二(三端共有)**:播放中**每约 5 秒整份写回** history / listen_stats。
  Android 的 ticker 用 `Handler(Looper.getMainLooper())`;macOS 的 store 是 `@MainActor`
  且 `AppSupport.save` 同步 encode + write。本机实测 history.json **270 KB**、inbox.json **747 KB**。
- **族三(macOS)**:逐字稿缓存在主 actor 上同步解码(实测 192 KB)。
- **族四(冷启动,三端共有)**:Android 有 **8 个 store 在构造函数里读盘**
  (`MutableStateFlow(load())`),而容器在 `Application.onCreate` 构造;macOS 各 store 的
  `init` 同步读;鸿蒙 `boot()` 同步读。→ **实测后决定不改**:`am start -W` 冷启动
  **219 ms**、macOS 各 store 合计约 53 ms。并行化要动装配顺序,风险大于收益。
- **量化工具(两端不同,都别只看一个数)**:
  ```bash
  # 鸿蒙:jank 事件数 + 整页重建次数(搜索框每次重建都打一行)
  hdc shell hilog -x | grep -c ProcessJank
  hdc shell hilog -x | grep -c "AceTextField.*SetIsEnable"
  # Android:掉帧分布(比鸿蒙那个计数准得多)
  adb shell dumpsys gfxinfo <pkg> reset && …交互… && adb shell dumpsys gfxinfo <pkg>
  #   看 Janky frames / 99th percentile / Number Slow UI thread
  ```
- **教训 / 规律**:
  1. **同一个毛病在三端的表现不一样,不能只查报障的那一端。** 这次是鸿蒙报"下拉刷新卡",
     但同族问题 Android 与 macOS 各有一份;反过来,鸿蒙最重的那处(下载写盘)
     另两端压根不存在 —— 因为那两端的框架天然把它放在后台。
  2. **先量再改,量完可能是"不改"。** 族四看起来最像问题(8 个 store 同步读盘),
     实测冷启动 219 ms,改它是白担风险。**"扫出来"不等于"该修"。**
  3. **`ProcessJank` 只能比相对量。** 它记的是 jank 事件不是掉帧数,
     一次 1.8 秒停顿也只记一条(H65 差点因此下错结论)。Android 的 `gfxinfo` 才给分布。
  4. **可变容器的遍历不能推迟到别的线程。** 把"生成 JSON"挪到 IO 线程时,
     若直接遍历 `mem` / `table` 这类可变 Map,就会与主线程的写入撞车 ——
     要先取一次浅拷贝快照,贵的是后面的 JSON 构造,不是拷贝。
  5. **数据安全路径上只搬纯运算。** 备份只把 `stringify`/`parse` 挪进子线程,
     合并规则(G-Counter 取 max、历史按 updatedAt 取新)一字不动。

- **现象**:发布前把两端的包解开逐项核对,发现当时的商店渠道(Android `store` + 只走商店的鸿蒙)
  设置页的「清除缓存」行显示 **「热门榜与图片缓存 · 3.0 MB」**、确认弹窗写

  后来 H70 恢复目录后,这条现状已翻转。
- **为什么要紧**:与 `docs/HISTORY.md` 阶段七同一类 —— **砍掉内容目录正是为了不被判定为提供
  视听节目服务,而界面上却写着「热门榜」,等于自己推翻合规口径**。而且这是**用户与复核方
  都看得见的可见文案**(不是注释、不是孤立字符串)。
- **顺带发现两处不准**:
  1. 鸿蒙那句还写着「图片」,但它的「清除缓存」**并不清图片**(只清频道缓存与逐字稿),
     统计的字节数里也没算图片;
  2. Android 主 res 那句只提「热门榜与图片」,却**漏了实际也计入的频道缓存与逐字稿缓存**。
     也就是说:同一条副标题在两个渠道各错一种。
- **修法**:按「实际清了什么、实际算了什么」重写,并用**渠道覆盖**区分:
  - Android `main`(自分发,有榜单):「榜单、频道、图片与逐字稿缓存 · %s」
  - Android `store` 覆盖(无榜单):「频道、图片与逐字稿缓存 · %s」
  - 鸿蒙(无榜单、不清图片):「频道与逐字稿缓存 · %s」
  五语种各一份;繁体用字过了一遍体检(注意 **`榜` 繁简同形**,别被"简体字检查"误报)。
- **验收**:重打包后 `aapt2 dump resources` 查 —— 商店渠道包里 **「热门榜」= 0 处**;
  鸿蒙 hap 的 resources 同样 0 处。设置页真机复看,显示「频道与逐字稿缓存 · 3.6 MB」。
- **一个留下不改的**:商店渠道包里仍有 6 条**孤立字符串**(「每日热门」×2、「情境电台」、
  「随机电台」、「电台模式」、「…检索接口…」)。它们**没有任何代码引用**(dex 里目录与电台代码
  已被 R8 删净,解包 grep 为 0),因此**永远不会显示**;根因是引用它们的代码在 `main`
  且是编译期删除,字符串却留在共享的 `strings.xml` 里。要彻底去掉得把那部分界面代码
  也移进 `default` source set —— 发布前不做这种重构,**记在这里以免以后被当成新发现**。
- **教训 / 规律**:
  1. **渠道审计要查"包里的可见文案",不能只查代码与权限。** 代码、权限、域名三项全为 0
     并不代表界面上没有自相矛盾的话 —— 用 `aapt2 dump resources` 把字符串过一遍。
  2. **"这个渠道没有 X" 要连 X 的名字一起清出可见文案**,不然验收报告与界面对不上。
  3. **副标题这类"说明性文案"最容易腐坏**:它描述的是行为细节(清了什么、算了什么),
     而行为改过好几轮(加了逐字稿缓存、鸿蒙又不清图片),文案没跟上。
     `AGENTS.md` 硬规矩 5 的清单里"设置项副标题"这一条就是为此存在的。
  4. 简繁体检的字表要准:`榜`、`才`、`不` 这类繁简同形字混进"简体独有"表会误报,
     反而掩盖真问题。

### H68. 第二次历史清理:**个人身份信息**,以及「指纹不是机密」这个论证的边界

- **起因**:准备公开仓库时复查,分发登记材料(`docs/BEIAN.md`,现仅本地)里有三类东西 ——
  ① 证书 MD5/SHA-1/SHA-256 指纹;② 登记主体信息(**真名**);
  ③ 分发平台的证书标识 `CN=…(20 位 id)`。文件开头原本写着
  **「本文件只记录公开信息。证书指纹与公钥可从任何已发布的安装包中提取,不是机密」** ——
  这句话对 ① **完全成立**,但它被当成了整份文件的通行证,而 ② ③ 并不满足:
  Android 证书主体是 `CN=Yuyin Reverb`,**真名只出现在鸿蒙/分发平台那一侧**,
  从 APK 里提不出来。
- **修法**:`git rm --cached` + `.gitignore`(文件留在本地,发布要照着填),
  六处引用改指向别处;然后一次 `git filter-repo` 把它从**全部历史**里删掉
  (它在 9 个提交里,今天的目录整理还让它有 `BEIAN.md` 与 `docs/BEIAN.md` 两个路径,
  两个都要传给 `--path`)。
- **顺带同一次做掉的**:把全历史的作者/提交者邮箱从公司邮箱换成个人邮箱 ——
  `git filter-repo --invert-paths --path … --mailmap <file>` **一次跑完两件事**,
  少一次全仓 hash 变更。mailmap 一行的格式是
  `新名字 <新邮箱> <旧邮箱>`。改完别忘了 `git config --local user.email`,
  否则下一次提交又写回旧邮箱。
- **结果**:私人字符串(真名 / 分发平台id / 三种指纹 / 公司邮箱)全历史各 **0 处**;
  提交数 204 → 203(有一个只碰被删文件的提交变空被剪掉);`.git` 4.5 MB → 3.8 MB。
- **刻意保留的**:**备案号本身**留在若干字符串资源与官网页脚里 ——
  它必须在 App 关于页显示,属公开信息。需要如实说清一点:公开备案号等于公开了
  一条到登记主体真名的查询链(登记公示可查主体名称),
  **但装了 App 的人本来就能看到这个号,不是仓库特有的暴露面。**
  (号与具体文件处数、主体信息都在本地 `docs/STORE-OPS.md`。)
- **知识与文件分开处理**:被删那份里真正值钱的是"为什么大陆商店渠道必须去掉内容目录"
  (当时的大陆分发口径把内置目录判定为提供视听节目服务,需《相应内容分发许可资质》,个人主体拿不到)。
  这一段本来就同时写在 `docs/HISTORY.md` 阶段五与 `docs/FEATURES.md` ——
  **删文件之前先确认知识有别的落点**,否则清理会顺手清掉判断依据。
- **教训 / 规律**:
  1. **"这类信息不是机密"的论证要逐项过,不能整份文件套用一个理由。**
     同一份文档里往往混着"可从产物提取的"与"只存在于账号体系里的"两类。
  2. **判断标准换个问法更准**:不是"它算不算机密",而是
     **"公开它以后,能不能反查到一个具体的人"**。指纹不能,真名与账号标识能。
  3. **`.gitignore` 只管未来**(同 H63)。要让公开仓库真的看不到,必须重写历史;
     而重写前先 `git bundle create … --all` 备份,并把仍需保留的文件另拷一份 ——
     它已经不在工作区受保护的范围里了。
  4. 一次 filter-repo 能同时做路径删除与邮箱重写,**攒着一起做**:
     每次重写都会让所有 commit hash 变化,次数越少越好。

### H69. 鸿蒙播放页的频道名点不动 —— 缺的不是一个跳转,是**订阅这件事的唯一入口**

- **现象**:鸿蒙端在播放详情页点频道名没反应。Android 点了会进频道主页。
- **为什么这不是小事**:频道主页是**订阅/取消订阅按钮所在的唯一页面**。
  从「最新」聚合、从收件箱、从别人分享的链接播起来的单集,它所属的频道很可能还没订阅,
  音阁的订阅列表里自然也找不到 —— 于是"听到喜欢的节目"和"订阅它"之间**没有任何一条路**。
  一个看起来是「少一个跳转」的缺陷,实际封死的是产品的主干动作。
- **根因**:**这个回调在鸿蒙端从来没实现过。** `PlayerPage.ets` 只声明了
  `onBack` / `onOpenQueue`,频道名就是一个裸 `Text`,没有 `.onClick`;
  Android 的 `PlayerScreen.kt` 与 macOS 的 `PlayerView.swift` 都一直有 `onOpenChannel`
  (还按 `feedUrl` 是否为空切主题色来暗示可点,macOS 同样是用 `feedUrl` 拼一个 `Podcast` 种子)。
  不是回归,是**从未对齐**。
  而 `docs/FEATURES.md` 这一行的「两端一致」指的是 **Android 与 macOS** —— 它没说错,
  但鸿蒙的能力只在文档开头用一段散文概括(「鸿蒙端已具备……播放页 + 后台播放 + ……」)。
  **矩阵逐项、鸿蒙成段,漏项就漏在这个不对称里**:成段的自述没有可勾选的粒度。
- **修法**:
  1. `PlayerPage.ets` 加 `onOpenPodcast: (feedUrl: string) => void`,
     频道名挂 `.onClick`,并按 `feedUrl` 是否为空串切 `scheme.primary` / `onSurfaceVariant`
     ——**颜色本身就是"能不能点"的说明**,照抄 Android 的处理。
     引导音频这类没有 `feedUrl` 的单集因此天然不可点,不需要额外判断。
  2. `Index.ets` 里 `openPodcastByFeed()`:**先在订阅里找现成的 `Podcast`**,
     找得到就能立刻显示作者与简介、不必等 RSS;找不到再用单集信息拼一个最小种子
     (`feedUrl` / `id` / `title` / `artworkUrl`)。详情页只依赖 `seed.feedUrl` 去取 RSS,
     其余字段回来后会被 `loaded` 整体覆盖,**种子只需要够撑住第一帧不空白**。
- **验收**:真机(BRA-AL00)分别跑了两条路径:
  1. 已订阅频道:播一集 → 展开播放页 → 频道名已是主题色 → 点它 → 频道主页打开,
     显示「已订阅」按钮与共 73 集,迷你条继续播放;
  2. 未订阅频道:随机电台播到 `Morbid` → 点播放页频道名 → 用最小种子进入频道主页,
     RSS 拉取完成后显示作者、简介、共 882 集与「订阅」按钮。
  两条路径均实际装机点击,不只是代码走查。
- **教训 / 规律**:
  1. **文档的粒度决定它能不能当检查表。** 逐项的矩阵能勾,成段的「已具备……」勾不了 ——
     哪一端是散文写的,漏项就攒在那一端。跨端对齐要按**交互**逐个点过:
     "字段都在、页面都有"不代表点得动(同 H67:文档说的和包里有的是两件事)。
  2. **判断一个缺陷的分量,看它封死了什么,而不是看改动有多大。** 这次改动约 30 行,
     但在它之前,鸿蒙端"发现新节目 → 订阅"这条链是断的。
  3. **可点性要有视觉暗示。** 一段和正文同色的文字,用户不会去点它 ——
     即便实现了跳转,不换色也等于没有入口。

### H70. 商店渠道恢复内容目录:**合规删减不是一个整体,期望值也会翻转**

- **决策**:首版先按完整版目录能力提交复核,被拒再降级。只恢复 `CATALOG`:
  分类热门榜、节目 + 单集关键词搜索、随机 / 情境电台重新启用;
  `SPECTRUM` 与 `LOCAL_ASR` 继续关闭,因为当初关闭它们分别是敏感权限与识别质量 / 包体问题,
  和目录的合规口径不是同一个理由。商店渠道仍不打包 `seed_podcasts.json`。
- **做法**:
  1. 鸿蒙把 `Sources.ets` 从 `harmony/shelved/` 移回编译树,并接回 Apple → fyyd →
     gpodder 三处降级链。ArkTS 没有 DCE,将来若回退,仍必须把实现移出编译树;
  2. Android 只需打开 flavor 的编译期 `CATALOG` 开关让 R8 保留目录代码,
     但字符串 source set 必须重排,不能把「改开关」误当成全部工作;
  3. `privacy_consent_catalog` 在 `main` 原本**没有本体**,只有 `default` 正文与 `store` 空覆盖。
     若只删商店渠道的空覆盖,资源不会自动回落,而是直接缺资源,轻则编译失败、重则运行时崩;
     必须把目录正文提升到 `main` 供两个渠道共用;
  4. `about_p_features` 在 `main` 虽然**有本体**,但其中声称「本机离线转写」。商店渠道
     不能直接删覆盖回落到 main,否则会向复核方和用户宣称一个包里没有的能力;
     必须保留「有目录,但只读发布方逐字稿、无真实频谱」的渠道覆盖;
  5. 鸿蒙的节目搜索与单集搜索是两个独立请求,同时发出而不是串行等待;
     用递增的请求代次挡住慢旧请求与取消后的请求回写,否则连续搜 A、B 时 A 可能最后覆盖 B;
  6. `Sources.ets` 挂起期间,`Episode` 新增了 `transcriptUrl` / `transcriptType` 两个必填字段。
     搬回编译树的第一次构建因此直接失败;Apple 单集搜索没有这两项元数据,显式填空串。
     **挂起代码不是冷冻代码**,主模型继续演进时它会漂,恢复的第一步必须是严格编译。
- **验收**:重打 Android 商店渠道 APK 与 HarmonyOS 商店包后,目录 URL 的解包 grep
  从 **0 变为非 0**;商店渠道 APK 的 `lib/|whisper-model` 仍为 **0**,
  `RECORD_AUDIO` 仍为 **0**。真机首页显示在线分类榜;关键词 `history` 的节目搜索 47 条、
  单集搜索 32 条;随机电台从在线榜单开台并播放 `Morbid`。
- **教训与可复用规律**:
  1. **方法论与期望值要分开。** 解包 grep 永远要做,但某个关键词该为 0 还是非 0
     取决于当前产品决策;翻转时必须同步 `FEATURES.md`。
  2. **声明加回来也要解包验证。** 「界面能点」不证明 release 包真的含接口实现,
     与「界面点不到不证明包里没有」是同一条规律的两面。
  3. **合规删减不是一个整体。** 目录、频谱、转写的关闭理由不同,恢复其中一个时不能
     顺手恢复另外两个;source set 中每条覆盖也要按它实际声明的能力逐项判断。

### H71. 鸿蒙「自动地区」写死成美国:**设置显示自动,不等于代码真的读了设备**

- **现象**:中国区设备安装后第一次进入发现页,热门榜不是中国区内容;设置页地区明明显示「自动」。
- **根因**:`SettingsStore.regionOverride` 的空串确实表示自动,但 `AppContainer.region()` 遇到空串
  直接返回了 `us`。`DiscoverPage`、榜单缓存键、Apple Charts 与电台全都忠实使用这个结果,
  所以错的不是目录接口,而是唯一的地区出口。Android 同一路径一直读 `Locale.getDefault().country`。
- **修法**:显式覆盖仍优先;自动模式改读
  `i18n.System.getSystemLocaleInstance().toString()`,从 locale tag 最后一段提取两位国家码并转小写,
  只有系统不给地区或 API 失败时才回落 `us`。推断值不落盘,用户切换设备地区后仍能真正「自动」。
- **验收**:BRA-AL00 保持地区「自动」覆盖安装后,发现页「每日热门」显示声动早咖啡、岩中花述、
  凹凸电波等中国区榜单;未清设备数据。真正的空数据首装仍需在不伤真实数据的隔离包上另验。
- **教训与可复用规律**:**带「自动 / 跟随系统」的枚举值必须一路追到最终出口。**
  设置页文案、存储空值、业务默认值三者任何一个写死,界面都会给出一个看似正确的假承诺。

### H72. 鸿蒙播放卡顿与错误提示闪烁:**失败处理本身形成了 AVPlayer 重试风暴**

- **现象**:迷你播放条点播放后很卡、经常失败;播放页「加载失败,请检查网络后重试」反复出现又消失,
  页面持续闪动。相同音源在 Android / macOS 流畅。
- **根因**:不是先假设 CDN 或缓冲参数。真机 `hilog` 直接看到约 200ms 一轮的
  `prepared → idle`:同一次失败会同时从 `prepare()` catch 与 AVPlayer `error` 进入重试;
  每次重试都留下一枚未取消 timer,而「重试耗尽」又把计数归零。更致命的是上一轮 50ms 淡入
  timer 仍在 reset 后调用 `setVolume`,随后 `setPlaybackRate` 也撞上 idle —— 两个
  `Operate Not Permit` 又被 AVPlayer 当成新错误,最终自己喂自己,无限 reset / setMediaSource。
- **修法**:
  1. 所有换源进入一条 Promise 串行链,每次装载分配递增代次;每个 await、状态回调、错误回调和
     retry timer 都核对代次,旧工作不能再碰新音源;
  2. 同一代次只处理第一条失败信号,自动重试始终只有一个可取消 timer,三次耗尽后保持终止错误,
     直到用户明确重试或换集;
  3. 合并并发 `createAVPlayer`,装载期间给 UI 明确 loading 并拒绝重复播放点击;
  4. 换源 / 失败立即停旧淡入;音量与倍速只在 AVPlayer 允许的状态执行,`play()` 失败也统一进
     失败状态机,不再记一行日志后继续跑后续操作。
- **验收**:修复前日志连续数十轮 `unsupport volume/rate operation`、重复 setMediaSource 与
  1/3→3/3→1/3;修复后真机随机电台连续播放两条网络单集,每条都只有一次
  `initialized → prepared → playing`,从「播放」日志到 playing 分别约 0.89s / 1.05s,
  无重试、无非法状态错误;暂停、继续与下一首都正常。失败三次后的终止态还需用可控坏 URL 补验。
- **教训与可复用规律**:
  1. **播放器报网络失败不等于网络失败。** 先看状态机日志;同一音源别端正常、且本端出现
     idle 状态操作错误时,应先修本端并发与生命周期。
  2. **重试必须具备身份、唯一 timer 和终止态。** 只按 episode id 判断不够,同一集的旧尝试
     仍会复活;耗尽后把计数清零更等于给旧回调重新发了一本预算。
  3. **定时器也是异步任务。** 换源时只 reset AVPlayer、不取消 fade / retry,就是让上一代任务
     在下一代状态机上继续写。

### H73. 鸿蒙迷你播放条头像点不动:**回调接好了,命中区仍可能只覆盖一小块**

- **现象**:迷你播放条的标题文字能进入播放页,点击频道头像没有反应;Android 除播放与下一首外,
  点击整条都会展开。
- **根因**:`Index.ets` 在主 Tab 与频道详情两处都正确传了 `onExpand`,但 Harmony 把 `.onClick`
  只挂在标题 / 频道的 `Column` 上。封面是它的兄弟节点,信息区空白也不属于这块命中区。
  Android 则把展开点击挂在外层 Row,两个 IconButton 消费自己的事件。
- **修法**:把封面、两行文字与剩余宽度组成独立信息 Row,由它占满控制按钮左侧并统一 `onExpand`;
  播放 / 暂停与下一首留在信息区外,不依赖父子事件冒泡。
- **验收**:BRA-AL00 真机点击封面和信息区空白均进入播放页;播放键只暂停并留在发现页;
  下一首只切到新单集并起播,不误跳播放页。主 Tab 路径已实点,频道详情页复用同一组件与回调。
- **教训与可复用规律**:**跨端交互对齐要比较命中区域,不能只比较有没有 onClick。**
  「回调存在」「文字能点」都不能证明整块卡片可点;至少要分别实点封面、文字、空白与内嵌按钮。

### H74. 首页是中国榜、电台仍会跨区:**地区快照与无来源缓存是两条独立泄漏路径**

- **现象**:H71 修完后发现页已经显示中国区榜单,点随机电台仍可能抽到其它商店地区的节目。
- **根因**有两层:
  1. `AppContainer.startGated()` 只在启动时把地区交给 `RadioStation.configure()`,电台把它保存成
     永久快照;发现页每次加载却现场读 `app.region()`,于是同一页面能同时存在两个地区;
  2. 电台候选池读取 `cn:default` 综合榜,而发现页的综合榜为了不空会按 cn → us → fyyd
     回退,并把结果写在目标键 `cn:default` 下。这个键记录的是「用户想看的地区」,不是
     「内容实际来自哪里」,一旦回退过就无法从缓存本身辨别来源。
- **修法**:
  1. 电台 configure 只注入依赖;每次开台 / 下一首都由发现页现场传 `app.region()`,自动续播使用
     本次活动地区。活动电台切区时清空电台前后导航,不让旧地区单集从历史里被下一首重放;
  2. 电台改成严格商店地区:只用当前地区的 `genreId > 0` 分类榜缓存/种子,不足时只刷新当前地区
     分类榜;完全不读 provenance 不明的综合榜缓存,也不走美国 / fyyd 回退。无候选时宁可停台;
  3. 不清 `popular_cache.json`:旧 `cn:default` 仍供发现页容灾,但电台不再读取,无需破坏用户缓存。
- **验收**:BRA-AL00 保留设备原缓存(含已被污染的 `cn:default`)覆盖安装。自动地区下开台日志
  `开台 region=cn` → `电台候选 region=cn count=240` → 选中资讯早7点;连点四次「下一首」被单飞
  收敛成两次顺序抓取(历史学人、K-Pop Radio),无并发、无误停台,候选池始终 `region=cn`,
  日志中综合榜刷新 / 美国 / fyyd 回退均为 0。每首起播都是单次 `initialized → prepared → playing`
  (约 0.9s),播放错误 0。活动电台把地区改成美国后切歌,日志 `地区切换 cn → us,清空电台导航历史`
  → `电台候选 region=us count=28` → 选中 Today, Explained;切回自动再切歌 `地区切换 us → cn`
  → 候选回到 `region=cn count=240`。发现页「每日热门」仍显示旧综合榜(Crime Junkie / The Daily 等),
  证明电台严格策略未波及展示型容灾。业主选择「仅按商店地区」,因此不再按 RSS 语言过滤,
  中国区榜内的英文节目允许出现。
- **教训与可复用规律**:
  1. **参数叫 region 不代表返回内容有地区来源保证。** 要追到回退链与缓存写入点;
  2. **展示型容灾与筛选型候选池不能盲目共用。** 页面宁可跨区兜底,电台要求严格地区时应
     fail closed;否则同一份「好心的回退」会成为另一功能的数据污染;
  3. **地区与语言是两个维度。** 商店地区只限定榜单 storefront,不保证节目语言;
     若以后要做中文电台,应解析 RSS `<language>` 后另立规则,不能靠标题猜语言。

### H76. 没有开发者后端,不等于隐私标签可以全否

- **现象**:商店指出应用存在个人信息处理,但后台未勾选对应隐私标签;旧政策还写着
  “不收集任何个人信息”“数据只存在本机”。

- **修法**:政策、官网、商店文案、同意页与关于页五语统一改为“无开发者数据后端、本地数据不自动

- **验收**:商店用途勾“应用功能”,流向勾“向第三方披露”“跨境传输”;关联数据汇总写明搜索输入、
  网络信息与本地应用活动。五语资源、Markdown 与 HTML 口径一致,代码扫描不再找到上述敏感日志。
- **教训与可复用规律**:**“收集”要按平台规则理解,不能按有没有自建后端理解。** 直连第三方、
  IP 暴露、本地处理和用户主动导出各自有不同流向,都应如实描述,不能用一句“零后端”全部覆盖。

### H77. 鸿蒙设置开关点完立即回弹:**ArkUI Builder 的布尔入参是快照**

- **现象**:“仅在 Wi-Fi 下载”“逐字高亮”“订阅更新提示”点按后无法稳定切换;存储 setter 实际执行,
  重新渲染却仍显示旧值。
- **根因**:`switchRow(..., on: boolean, ...)` 把观察对象字段在 `@Builder` 调用边界求值成普通布尔值。
  ArkUI V1 后续重建拿到的仍是这次调用的快照,与 `SettingsStore` 已变化的字段脱节。这和
  `choiceRow(selectedOf)` / `rowText(subOf)` 已经规避过的是同一类问题。
- **修法**:参数改为 `onOf: () => boolean`,在 `Toggle.isOn` 渲染处调用 getter;所有动态开关都传闭包。
  通知授权拒绝时显式写回 `updatesEnabled=false` 并展示专用提示,不再复用“备份失败”。
- **验收**:开关开→关→开后视觉状态与存储一致,离开页面、返回和强杀冷启后仍保持;通知允许与拒绝
  两条路径分别验证。静态编译只能证明类型正确,最终仍需真机点击。
- **教训与可复用规律**:**ArkUI Builder 的 primitive 参数不要承载可变真相。** 如果值来自
  `@Observed` 对象且要随重建刷新,传 getter 或最小观察组件,不要再复制一份镜像状态。

### H78. “仅在 Wi-Fi 下载”能保存却不生效:**设置项必须接到执行入口**

- **现象**:鸿蒙设置页能保存 Wi-Fi-only 偏好,但频道详情下载和备份恢复重下仍会在蜂窝网络执行。

- **修法**:向 `DownloadManager` 注入 `SettingsStore`,所有下载统一在入口查询默认网络 bearer。

- **教训与可复用规律**:**设置必须在副作用边界执行。** 验收不能停在“开关可切、值能落盘”,还要
  追到真正发起网络、写文件或调度任务的唯一入口。

### H79. 鸿蒙目录里的 RSS 真机不可达:**线下全量探测后按精确 feed 剔除**

- **现象**:复核样本中的 Anchor 与 BBC 频道从目录能搜到,进入详情后却长时间转圈或失败;桌面读取
  同一批 feed 均能得到合法 XML,容易误判为 ArkTS 大 XML 解析问题。
- **根因**:真机日志显示 worker 与主线程请求都在连接阶段 `Operation timeout`;设备上
  `anchor.fm` 与 `podcasts.files.bbci.co.uk` 能解析到 IP,但无法建立连接,同时 `gpodder.net`
  可正常连接。把 RSS 专用超时放宽至 30 秒、再放宽至 120 秒仍失败,后者还被系统网络栈约 65 秒
  硬截断。因此根因是设备网络出口到发布方不可达,不是语言、XML 大小或解析器。
- **修法**:先补齐 worker 返回 `null` 时的主线程降级、按 host 记录阶段与耗时、详情页代次和终态;
  再线下抓取中国区 19 个分类前 30 名,得到 535 个去重 feed / 59 个 host,从鸿蒙真机对每个 host
  连续探测三次。最终把 10 个持续不可达 host 上命中的 30 条**精确 feed 路径**写入
  `CatalogFeedFilter`,在榜单缓存、联网榜单、节目/单集搜索和随机电台候选进入 UI 前统一剔除。
  不按语言或整个 host 永久封禁,不删除用户已有订阅;无效的加长超时试验已撤回。
- **验收**:四个复核 feed 全部命中静态过滤;旧缓存与新榜单都不再展示它们,粘贴这些 URL 后也不会
  通过目录降级重新出现。可达 feed 仍能正常展示;未知新源仍走详情页的明确失败态。日志只含
  scheme/host,不含完整 feed 路径或 query。
- **教训与可复用规律**:**“桌面能下载”不能证明手机使用的是同一网络出口。** 对复核可见的有限榜单,
  发布前可以在目标设备网络上全量探测并固化精确过滤结果;不要因两个域名不可达就按语言或托管商
  整站屏蔽。静态清单只能覆盖当次榜单快照,关键词搜索的长尾来源还需运行时有界校验(见 H81)。

### H80. 已设 `SHARE_MODE` 仍被判停止后台音乐:**进程内中断单元不等于跨应用 AudioSession 策略**

- **现象**:复检工具在余音起播约两秒的短音场景记录 `The audio session of pid ... is not found`,
  并判定焦点策略为 stop。后台音乐被打断后,余音暂停或播放结束也不能自动恢复。
- **根因**:`AVPlayer.audioInterruptMode = SHARE_MODE` 只表示本应用不同音频流共享同一个 interrupt unit,
  不会声明与其他应用并发时应混音、压低还是暂停。播放器又使用 `STREAM_USAGE_MUSIC`,没有显式
  AudioSession 时系统只能按默认音乐冲突策略处理。
- **修法**:`PlayerController` 在每次真正 `play()` 前激活
  `AudioSession(CONCURRENCY_PAUSE_OTHERS)`,暂停、真正播完、睡眠到时、电台无下一首、重试耗尽和
  release 时撤销。换集、自动续集和前三次加载重试保持会话。activate/deactivate 与明确播放动作各自
  串行并带代次校验,防快速暂停/继续时旧异步结果覆盖新意图;AVSession 的 play/pause 也从 toggle 改为
  幂等 resume/pause。
- **验收**:先让另一媒体应用播放音乐,再起播余音;对方应暂停而非停止。余音通过页面、控制中心或耳机
  暂停后对方自动恢复;换集不闪断,自然结束与失败终态会恢复。hilog 不再出现本应用 pid 没有 audio
  session,并能看到 pause-others 会话的激活/撤销。
- **教训与可复用规律**:**同名的“中断模式”和“会话并发策略”不能凭字面类推。** 音频焦点必须在用户
  真正听得到声音的生命周期内申请,并在所有终态释放;只设置 renderer usage 或进程内 SHARE_MODE 不够。

### H81. 搜索结果仍能进入 84 秒转圈:**榜单黑名单覆盖不了长尾,`null` 回落还把超时请求了两遍**

- **现象**:补完 H79 的 30 条静态规则后,复检仍能从 Apple 关键词搜索进入新的节目并持续加载约 84 秒。
  `Daily Easy English Expression`、`The Beijing Hour`、`Learn Mandarin Chinese` 的 feed 都不在
  当时 535 条榜单样本中,桌面网络又都能返回 200。
- **根因**:Apple/fyyd/gpodder 搜索可返回榜单快照之外的任意长尾 feed,静态 denylist 不可能穷举。
  同时 `PodcastRepository.feed()` 把 worker 正常返回 `null` 也当成子线程故障,又在主线程请求一次;
  复核网络下单次约 40 秒的系统连接超时因此被串成约 80 秒。外层 `Promise.race` 只丢结果、不销毁
  请求,也不能解决后台任务堆积。
- **修法**:`Http.text` 增加到点主动 `destroy()` 的物理硬截止;RSS 详情 12 秒、搜索预检 8 秒。
  worker 返回 `null` 作为正常失败终态,只有 taskpool 真正抛异常才回落一次;相同超时策略的同一 feed
  共享一条 in-flight Promise,预检成功的完整解析结果写缓存供详情直接复用。搜索目录结果先展示,
  仅以前两路全局并发检查首屏前四条;失败项保留但标记“当前网络不可访问”并禁入,第 5 条以后仍可
  直接进入且受详情硬截止保护。
  直接粘贴 RSS 和已有订阅始终真实尝试,不按语言、整个 host 或静态白名单封禁。
- **验收**:三个复核 feed 都必须在单次 8/12 秒上限内得到可用或明确不可达终态,hilog 对同一 feed
  只能看到一次网络链;检测中禁止进入,检测成功后详情直接复用缓存。可达的大 RSS 仍由 worker 解析成功,
  没有单集的空 feed 不能被误标为可用;取消搜索或离开详情后旧 generation 不得覆盖新页面。
- **教训与可复用规律**:**有限快照适合快速拒绝已知坏源,不适合作为开放搜索的完整可用性证明。**
  对无限长尾要把成本限定在首屏小批量,并把超时落实到底层资源释放;“超时返回了”不等于请求停了。

### H82. 商店反复标「风险应用」:**代码特征收敛做完仍报,根因在签名证书的引擎信誉 —— 但换证书只有一次机会**

- **现象**:安卓商店渠道提交复核多次被标「风险应用」。先做了包表面收敛(去掉未用依赖、WorkManager
  按需初始化、`allowBackup=false`、排除 `DebugProbesKt.bin`),重新提交复核**仍报**;
  用真机系统自带的安全扫描(某安全引擎)直接扫 APK 同样报「风险」。
- **根因**:安全扫描引擎对**签名证书的信誉**权重远高于包内容特征。旧证书虽然是字段完整的自签专属
  证书(非 debug、非公用测试证书),但换全新 RSA-4096 专属证书后,两台不同厂商定制
  ROM 真机的系统安全扫描都**不再报**——触发点是旧证书本身落在引擎的灰名单口径里,与代码行为无关。
- **修法**:`keytool -genkeypair` 生成新 jks(RSA 4096,有效期 10000 天,DN 字段完整),重写
  `keystore.properties` 为新随机口令,双渠道重打包;旧证书与旧包按决策**全部销毁,无备份**。
- **前提 —— 这条路的入口只有一次**:两个 Android 渠道**同包名**,而应用身份绑定签名证书。
  同包名换签名之后:系统侧覆盖安装签名校验不过,商店侧也不认为新签名的包是同一应用的升级,

### H83. 熄屏静置十几分钟后自动开播:**AVSession 的 play/pause 都接了 toggle,重发的系统命令会翻转状态**

- **现象**:用户反馈(1.0.0 发布版):熄屏无操作,停播十几分钟后播客自己开始播放,先后两次;
  未设置睡眠定时。场景里没有任何用户动作,入口只能在系统侧。
- **根因**:`AvSessionBridge` 把系统 `'play'` 与 `'pause'` 两条命令**都接到 `togglePlayPause()`**。
  toggle 不幂等 —— 锁屏/媒体控制中心/蓝牙设备状态重同步会把**已派发过的命令重发一遍**,
  应用早已暂停时,一条重发的 pause(或 play)经 toggle 翻转成播放。系统重发不需要用户在场,
  于是表现为「熄屏静置自播」。对照全部入口:启动路径无自动续播、睡眠定时只会暂停、
  加载重试只在装载失败链上、电台续播只在 `completed` —— 会话命令是 1.0.0 里唯一能
  无操作起播的入口。
- **修法**:1.0.1(6cacf80)把会话命令改为**幂等的明确动作**:`'play'→resumePlayback()`、
  `'pause'→pausePlayback()`,重复调用只确认目标态、不翻转;配合 `playbackDesiredPlaying` +
  代际号 + 串行动作队列收敛快速暂停/恢复。
- **验收**:用户场景(暂停态下重发 pause 命令)在 1.0.1 语义下确认暂停、不起播;
  6cacf80 已在 Pura 90 模拟器回归媒体键与跨应用焦点闭环。1.0.1 发布后用户升级即愈。
- **教训与可复用规律**:①系统回调命令必须接「幂等的明确动作」,toggle 只适合无重复风险的
  界面点击 —— 呼应硬规矩 9:程序化操作也会触发的信号,不能当用户操作处理;②媒体命令的
  重复派发是常态不是异常,蓝牙 AVRCP、锁屏、控制中心都会重发;③「灵异现象」先枚举全部
  能触达该行为的入口逐一排除,再对照版本差异 —— 本例 1.0.1 已修,用户报告就是修复必要性的
  独立佐证。

### H85. 解包 grep 中文报 0 但串明明在:**macOS 自带的 BSD grep 对二进制内容的多字节匹配会漏报**

- **现象**:验证商店包时用 `LC_ALL=C grep -a '余音' resources.arsc | wc -l`
  想确认应用名字符串在包里 —— 报 0。换 Python 按字节统计同一个模式,非 0;
  把同一文件拷到 Linux 机器用 GNU grep,也非 0。**结论依赖了 grep 的实现语义,
  差点把「在」验成「不在」。**
- **根因**:macOS 的 `grep` 是 BSD 实现,不是 GNU。`LC_ALL=C` 在 GNU grep 里
  等于「逐字节透明匹配」,而 BSD grep 在同一环境下对含 NUL / 非法 UTF-8 序列的
  大二进制文件,多字节模式的行为不可信 —— 按行切分与编码判定都可能提前放弃。
  本仓库的解包期望值(`grep -ac …` 非 0 / 为 0)恰好都是围绕 GNU grep 语义写的。
- **解法**:二进制内容统计不信任系统 grep,两种可靠做法任选:
  `python3 -c "import sys; print(open(sys.argv[1],'rb').read().count('余音'.encode()))" f`,
  或 `rg -a '余音' f | wc -l`(ripgrep 逐字节扫描)。本次 1.0.2 系统备份解包验收
  就是用这两种方法复核的。
- **教训与可复用规律**:①**验证工具本身要先自校验**:拿一个已知存在的串跑一遍,
  得到非 0 再相信后面的 0 —— 否则你验证的是工具,不是包;②跨机器语义差异
  (BSD vs GNU、locale)是「同一命令换台机器结论翻转」的常见来源,仓库里写
  验证命令时注明动机,换环境的人才不会盲跑。

### H86. 恢复备份「没任何效果」:**Swift 合成解码里默认值≠可选键,一个缺键毒死整份备份;时间戳单位三端分叉**

- **现象**:把 Android 导出的 `reverb-backup.json` 导入 macOS 端,选完文件后
  **什么都没发生** —— 没有恢复弹窗、没有报错,像没点过一样。
- **根因**是三件事叠加,每件都值得单独记:
  ①**Swift 合成 Codable 的陷阱**:属性写了默认值(`var played: Bool = false`)
  并**不会**让解码变成「键可缺省」,合成实现仍然要求键存在。Android 导出的
  history 没有 `played` 键,第一条历史就让 `JSONDecoder` 抛 `keyNotFound`,
  而备份是**整包一个 Payload 解码** —— 一个分区坏,全份作废。
  ②**时间戳单位三端分叉**:history 的 `updatedAt` Android/鸿蒙存毫秒、macOS 存秒,
  谁也没归一。即便①修好,macOS 备份恢复到 Android/鸿蒙会被整批判「当前更新」跳过,
  一条历史都进不来;反过来则全部落成 1970 年。
  ③**失败静默**:UI 在 `sectionsIn` 探测为空时 `return`,用户视角就是「没任何效果」,
  连错在哪都无从查起 —— 日志里也只有一行探测失败。
- **修法**(数据出口保证,各修一层):
  - macOS `HistoryEntry` 改自定义解码逐键 `decodeIfPresent`,并在解码口把
    >1e11 的时间戳按毫秒÷1000 归一;`SettingsPayload` 全字段可选(三端 settings
    schema 各有增删,恢复时缺键保持现值),任何分区缺键都不再毒死整份备份;
  - Android 导出补 `played`、恢复补秒→毫秒归一与 played 补回;鸿蒙 `mergeAll`
    同样补秒→毫秒归一(其 played 链路本来就通);
  - 两端恢复在 `record()` 之后补 `markPlayed` —— record 会把 played 重置为 false;
  - macOS 恢复探测为空时弹窗「无法识别的备份」,不再静默。
- **验收**:用真实模型编译探针解码真实备份文件:修前 `keyNotFound: played`,
  修后 7 个分区全部解码(31 订阅/100 历史/88 统计),毫秒归一后时间戳语义正确
  (2026-09-14 20:27);实机导入由用户手动复核。
  另留一条过程教训:**这轮修复的第一版曾被「假绿」掩盖** —— macOS 编译失败
  (`init(from:)` 写在类型体内吞掉了成员初始化器,`Stores.record()` 的逐参构造
  全部失配)、鸿蒙构建跑错目录,而验收命令用了 `构建 | tail` 的管道,退出码被
  `tail` 吞掉,三端被误报成全绿。**构建验收必须看真实退出码
  (`set -o pipefail` 或不带管道),产物要看 mtime。**
- **教训与可复用规律**:①「字段有默认值」只影响**构造**,不影响**合成解码** ——
  想要键可缺省必须 `decodeIfPresent` 或声明 Optional;②跨端交换的 JSON 是系统
  边界,单位与 schema 的分叉要**在解码口归一**,不能指望对端和你口径一致 ——
  这个仓库三端「同一格式互通」的承诺,指的是解码端互相容忍,不是编码端永不漂移;
  ③任何「选完文件就没下文」的路径都该有可见反馈,静默失败是最贵的失败:
  用户不报障,你永远不知道。

### H87. 恢复备份弹窗选项区首开整块空白:**`isPresented` 弹窗首帧拿到的是旧状态快照,数据要随 item 走**

### H88. 顶部分类胶囊拖动不联动:**Swiper `currentOffset` 实测是带符号位移,方向按 d.ts 字面理解会被边缘保护整个吞掉**
- **现象**:发现页/曲库页做「分类胶囊随 Swiper 手势 1:1 平移」联动,真机上
  拖动页面时胶囊纹丝不动(冷启动后第一次拖动必现,而那恰恰是最常见场景),
  切换完成后胶囊才整体弹到新位置 —— 等于联动代码从未生效。
- **排查**:在 `onGestureSwipe` 里加 hilog 探针逐帧打 `index/currentOffset`,
  拖动前先开流式落盘(环形缓冲会被一次拖动的 300+ 帧冲掉)。310 帧证据:
  从第 0 页向左拖(去第 1 页)时 `currentOffset = -302`(页宽 1216)——
  **向左滑为负**。而代码按「负 = 往前一页」理解,算出 `to = -1`,
  被 `to < 0` 边缘保护静默吞掉。既有 `dragTarget` 的
  `offset < 0 ? index+1 : index-1` 正是正确语义的旁证。
- **根因**:d.ts 把 `currentOffset` 注释成「距 Swiper 主轴起点的偏移」,
  实测是**当前页相对其锚点的带符号位移**。第一版按绝对偏移公式
  (`|off - index*W|/W`)算,开局就被钳到 1.0,胶囊「瞬移到目标位不动」;
  第二版改对位移语义但符号方向仍反,同样全线失效。
- **修法**:`to = index + (off < 0 ? 1 : -1)`,与 `dragTarget` 同一套方向约定;
  进度 `p = |off| / pageW`,帧数据经回调总线推给胶囊组件(见 Components.ets
  `ChipsSwipeSync`)。
- **验收**:装机后冷启动直接首拖,35% 处胶囊已离位插值、60% 处明确位于
  两 chip 之间且宽度同步插值 —— 不再依赖「先切过一次」。
- **教训与可复用规律**:①「看不见中间值的交互」先造探针(逐帧落盘)再定位,
  靠现象猜方向连错两次;②**事件参数语义与 d.ts 字面不符时,同仓库已有的
  消费方往往是对的** —— 先找同类代码对照,别按注释直译;③带符号位移配
  边缘保护是危险的组合:方向反了不会崩、不会报错,只会让整条路径静默失效。

### H89. 点击切页胶囊不动而拖动正常:**ArkTS `@Watch` 的回调参数是属性名字符串,不是新值**
- **现象**:拖动联动修好后(H88),**点击** chip 切页:页面切过去了、chip
  高亮也切过去了,唯独胶囊留在原 tab 位置。

  onAnimationStart/End(否则 endSink 会兜住胶囊),程序化切页的收尾要在
  改 index 的调用点自己驱动;③真机自动化验证交互时,后台残留的 uitest
  手势可能在新会话里延迟生效,造成「点了 A 却选中远处 B」的假象 ——
  下结论前先 `uitest dumpLayout` 确认当前状态与截图一致。

### H90. 玻璃分类条下缘透出半个静止圆:**m3 1.2 的 PullToRefresh 指示器静止态也画,给它挪位置等于把它挪进视野**
- **现象**:Android 玻璃分类条(悬浮)装机后,分类条玻璃容器下缘中央
  常驻半透明圆,下半截露在容器外、上半截透过玻璃可见;发现页与音阁
  收件箱都有,冷启动静止态就有,不是下拉残留。
- **根因**:material3 1.2.1 的 `PullToRefreshContainer` 静止态也会画
  指示器圆盘。玻璃移植前它贴在 Box 顶缘,被 `clipToBounds` 裁在视野外;
  玻璃移植时为了「转圈不被玻璃罩着看不清」给它加了
  `padding(top = topPad)` 下移 —— 等于把常驻圆盘挪进了玻璃条视野。
  之前 cd05eb8 的「下移 + 裁边」组合里,「下移」本身已经引入了这个
  隐患,只是当时容器上沿紧贴分类条没显形。
- **修法**:指示器按需组合 —— `if (pullState.isRefreshing ||
  pullState.verticalOffset > 0f)` 才参与组合(1.2.1 的 State 公开面
  只有 progress/isRefreshing/verticalOffset 可用,无 1.3 的
  distanceFromTop)。不拉不转时圆盘根本不存在;下拉/刷新时出现在
  玻璃条下方。`clipToBounds` 保留作纵深防御。
- **验收**:该国产定制 ROM 真机冷启动静止态发现页/音阁页均无圆;拖拽 Pager、
  点切 tab、下拉刷新后静止态复查仍无圆。
- **教训与可复用规律**:①「给常驻元素挪位置」前先确认它**该不该
  常驻** —— 修视野问题的正解有时是让元素按需存在,而不是继续调
  位置;②material3 1.2→1.3 的 PullToRefresh API 断代很大(容器+
  State 拆成 PullToRefreshBox),搜到的 1.3 解法不能照搬到 1.2;
  ③悬浮玻璃栏这类半透明覆盖层会把「内容层的小瑕疵」半透出来,
  验收要点因此变多 —— 任何新增的常驻绘制都要在玻璃下看一眼。

### H91. 玻璃移植装机验收的六处修正:**两处坐标/归属语义坑 + 四处间距几何**
用户上手验出六个问题,按发现顺序:①胶囊偏左;②点已选中的发现 tab 跳音阁;
③标题栏顶进状态栏;④音阁排列按钮偏下;⑤频道页顶距过大;⑥换页后选中 chip
留在屏幕外。前两个是「语义想当然」,后四个是纯几何,一并记录。
- **①胶囊偏左**:chip 用 `positionInParent()` 量测,那是**叶子布局坐标,
  不含父节点 modifier 链上的 padding**(Row 有 horizontal=8dp 内边距)。
  胶囊拿它减 scroll 去对齐玻璃条(视口)坐标,恒差一个 padding。修法:改用
  **窗口坐标差**(chip.positionInWindow - 玻璃条原点.positionInWindow)+ 补回
  scroll.value,得到「含 padding、滚动无关」的内容坐标 —— 窗口坐标天然实时
  随滚动刷新,连补偿逻辑都省了。
- **②点已选中的 tab 跳到隔壁**:`tabAt = (x + halfW/2)/halfW` 算的是
  「离 halfW 整数倍最近」,但两个 tab 的中心在**半个** halfW 处 —— 发现 tab
  的右半边全部被判成音阁:按下预览跳走、松手提交切页;而且连点两次会第二次
  才生效(第一次判成"已选中"被 no-op)。修法:均分槽位用 `floor(x/halfW)`。
- **③④⑤⑥**:MainShell 是 edge-to-edge 的,状态栏让位只有详情页的
  FullScreen 做了,tab 外壳漏了 → 补 `statusBarsPadding()`(③);
  音阁排列按钮(48dp)比玻璃条(44dp)高,top=5dp 起排中心差 7dp,负 offset
  才能真正对中(④);频道页返回行 24dp 顶距叠在 systemBarsPadding 上,
  对齐播放页的 12dp(⑤);分类条 reveal 原先只防「向后滚」
  (`scroll.value < target` 才滚),换到屏幕左侧的分类永远滚不回来,
  改为双向 `animateScrollTo((m.first - revealPad).coerceAtLeast(0))`(⑥)。
  ③第一版还连犯两错(用户复验抓出):**background 写在 statusBarsPadding
  之后**,状态栏区域露黑底、沉浸式失效 —— 让位 modifier 必须垫在 background
  之内(`background().statusBarsPadding()`);ScreenHeader 顶距 28dp 矫枉过正,
  收成 12dp。**两页标题动作键不同高**:动作键在含副标题的左列里垂直居中,
  有无副标题的页面差出半个副标题 —— 副标题移出居中行、动作键只对齐标题行;
  顺手踩了 `weight(fill=false)` 的坑:全 fill=false 的加权行会退成包裹宽度,
  动作键悬在半路,标题要 `weight(1f)`(fill 默认 true)撑满才行。
- **验收**:该国产定制 ROM 真机逐项复测 —— 胶囊在 scroll=0 与滚动后均与 chip 对中;
  点发现右半边不再跳音阁;状态栏透明、标题离状态栏一指宽;dumpLayout 量得
  发现页随机电台与音阁页设置键 bounds 逐像素一致([1129,213][1200,284]);
  频道页顶距与播放页一致;从远处分类一路滑回文化,chip 行全程跟随滚回。
- **教训与可复用规律**:①`positionInParent()` 不含父节点自身 modifier 的
  padding —— 要「相对某个可见容器」的坐标,用 `positionInWindow()` 差值,
  不要手补常量;②「最近邻」公式先画数轴再写:中心锚点在半格处时,+half/2
  会把边界判反;③凡是「浮层叠在系统栏上」的布局,让位只做一次、做在最外层,
  且 background 必须在 inset modifier **之前**(否则让位区露底色,沉浸式失效),
  内层各页自查有没有再叠一层;④「标题 + 动作键」的头部,动作键的垂直参照物
  必须是与副标题无关的行(标题行),否则有无副标题的页面必然错位;
  ⑤验收移动端交互,用 dumpLayout 拿真实槽位边界再点 —— 槽位的几何直觉
  ( label 居中 ≠ 槽位对半)经常是错的。

### H92. 玻璃条纵向中央的白线:**半透明材质会把身后的渲染缺陷显形 —— 这次是高程阴影的网格化接缝**

**现象**:浅色模式下,发现/音阁页顶部玻璃分类条与底部玻璃导航条的纵向中央
有一条隐约的水平白线(用户:「胶囊 tab 纵向中央似乎有个白条」)。暗色模式下
同一缺陷也在,只是对比度低于肉眼阈值。

**根因**:玻璃条 = 85% 不透明表面 + 高程投影(`Modifier.shadow`)。投影画在
条身后,透过 15% 的透明度显形——这正是玻璃「厚度感」的来源,但也把投影自身
的渲染缺陷透了出来:RenderNode 高程阴影对「圆角半径接近半高」的圆角矩形做
网格化时,上下两条直边投影在形状正中央留下一条**未覆盖的接缝**——别处被压暗、
唯独这条缝漏光,亮背景从缝里透出来就是一条白线。实测缝宽随圆角半径递减:
44dp 高的条用 21dp 圆角 → 6px;降到 19dp → **17px(更糟)**;半径恰好半高
(56dp 高的底部条用 28dp)→ ≈1px。规律:半径越接近半高,上下直边越短,
上下两段投影越贴合,真胶囊(percent=50)时归零。

**修法**:两根玻璃条的 `shadow(shape=…)` 改用 `RoundedCornerShape(percent = 50)`,
外观的 clip/background/border 维持原圆角。阴影是一团模糊斑,外形圆角差 1dp
肉眼不可辨,观感零变化。`shadow` 的 shape 参数与外观 shape 本就可以分开指定,
这是本修法成立的前提。

**教训与可复用的规律**:
① **半透明材质是「身后的显影液」**:前景怎么查都对不上时,先问它背后有什么
(本例第一反应是逐层排查前景元素——胶囊指示器、chips、描边——全错;把表面
摘掉做成完全无背景的对照版,白线原形毕露是身后的投影,方向立刻就对了)。
② **多包并存时,装机验证先验包名**:手机上同时装着旧包 `com.yuyin.reverb`
(9 月 5 日 v1.0.0)与新包 `com.yuyin.reverb.android`(应用 ID 迁移后的现行包),
用旧组件名启动了旧包,量出「玻璃面根本没画」——其实那版还没有玻璃条。启动前
`pm list packages` + `dumpsys package` 确认包名与版本,`resolve-activity`
拿真实入口(应用 ID 迁移后 Activity 类名仍留旧命名空间,按包名拼组件名会报
`Activity class does not exist`)。
③ 手势判别实验要防误触:想「微微滚动列表」的小幅 swipe 会被识别成下拉刷新
甚至翻页/切 tab,截到的帧不是你以为的状态——对照实验前后都要 dumpLayout
确认页面身份。

### H93. 横滑换页后选中 chip 留在屏幕外:**reveal 的触发点挂在布局回调上,而横滑根本不产生布局变化**

**现象**:顶部分类玻璃条,横滑切到屏幕外的分类:页面切了、胶囊也过去了,
但条身不滚 —— 选中 chip 留在屏幕外,高亮看见了却不知道是哪个分类
(用户:「tab 整体没有移动,导致看不到当前所在的 tab 了」,与 Android
H91 轮修过的「换页后 tab 不可见」同症)。

**根因**:把选中项滚进可视区的 `revealSelected()` 从初版(8a373bf)起就只挂在
内层 chips Row 的 `onAreaChange()` 上。这个回调只在**组件面积/位置变化**时触发
(首次布局、字号变化),而横滑换页只更新 `selected` 状态,整条没有任何面积变化
—— `onAreaChange` 在首次布局之后永远不会再触发。`@Watch(onSelectedChange)`
那条链只推了胶囊弹簧(`springTo`),没推条身滚动。也就是说 reveal 入库起就
没有过真实的触发路径;此前测试都滑在前几个可见分类上(可见时 reveal 本来
无事可做),一直暴露不了。

**修法**:reveal 挂到业务事件上 —— `onSelectedChange`(@Watch 桥)里同时调
`revealSelected()` 与 `springTo()`。横滑落位(`onChange`)与点按(`onSelect`)
两条换页路径都汇聚到 `selected` 状态,一处挂接全覆盖;reveal 自带
`scrolledTo` 幂等阀,重复触发无害。

**教训与可复用的规律**:
① **挂生命周期/布局回调的逻辑,要审计它的真实触发路径**。回调名看着相关
(`onAreaChange` ≈「布局变了」,reveal ≈「位置该动了」)不等于业务事件会经过
它 —— 换页不改变布局,reveal 就永远不会被叫到。写「A 发生时做 B」的代码,
先问一句:B 的触发点在 A 的路径上吗?
② 同一用户操作常有两条代码路径(手势逐帧/落位 onChange,或按下预览/松手
提交),状态订阅必须两条都覆盖 —— Android 侧同功能当时就修对了
(LaunchedEffect(selected) 直接挂选中态),两端对照是最便宜的回归测试。
③ 收尾弹簧参数与落位动画的时长相配:胶囊 `springMotion(0.3, 0.75)` 约
150ms 冲到终点,Swiper 落位约 400ms,胶囊早早到位、页面还在路上,观感
「急促」(用户对照 Android 的跟页平移反馈)。放宽到 (0.45, 0.95) 与落位
同步到位,读起来才是「跟着页面滑过去」。

### H94. 底部导航横滑换 tab,两个方向的松手阈值不对称:**槽位判定用了胶囊左缘,左缘与中心差半个胶囊宽**

**现象**:底部导航,从左往右拖(发现→音阁)超过一半松手,弹回发现不切;
从右往左拖(音阁→发现)超过一半松手,正常切过去。同一个「过半」,两个方向
一个切一个不切。

**根因**:拖拽的落槽判定 `tabAt(dragStartX + dragAccum)` 用的是**胶囊左缘**
坐标(pillXFor 系列全是左缘),而槽位分界在条的中线。左缘到胶囊中心差半个
胶囊宽(84dp 胶囊 ≈ 115px):发现→音阁方向,左缘要越过中线,实际要拖满
行程的 69% 才判过半;音阁→发现方向,左缘 31% 就过了中线,早早判回发现。
两个方向阈值差了一倍多,用户按「拖过半就该切」的直觉操作,向右必失败。
(点按路径不受影响:手指坐标本来就是命中点。)

**修法**:拖拽的落槽判定(松手提交 target 与途经高亮 nearIdx)改用胶囊
**中心** `tabAt(dragStartX + dragAccum + pillW / 2)` —— 中心过中线 =
行程恰好过半,两向对称;途经高亮与松手提交用同一判定,预览与结果一致。

**教训**:① 坐标系要成对检查:一组坐标(这里 pillX)全是「左缘」,而判定
基准(槽位分界)是「中线/中心」,两套基准混用就会在某个方向上差半个身位 ——
凡是「A 越过 B 判定」的代码,先确认 A 和 B 是不是同一个锚点。② 不对称的
bug 最容易暴露:同一操作两个方向行为不同,几乎必然是某个偏移量在起作用,
直接比较两个方向的差值就能把偏移量钉出来。

### H95. 批量重写提交历史的三处**静默失败**:规则自我追加、量词只管最后一个字符、以及一次超限的 `git grep`

- **现象**:给历史做词表重写(提交信息 + 各版本文件内容)时,三个错都不表现为报错,
  只让结果悄悄不对:
  1. 有一条**追加型**规则 —— 命中锚点句后在句尾补一句「这条路只有一次」。它的替换文本里
     仍然包含那个锚点,于是**每跑一遍就多补一份**:第二遍补一份、第三遍又补一份,
     同一条提交信息里出现三份,而整个流程每遍都打印「Completely finished」。
  2. 想把连续 N 份折叠回 1 份,写成 `re.compile(re.escape(TAIL) + "{2,}")`。**量词只作用于
     模式的最后一个字符**,不是整段字面量 —— 折叠等于没做,同样不报错。
  3. 验收用 `git grep -c <词> $(git rev-list --all)`。258 个 ref 一次性当参数**超出系统参数
     上限**,命令根本没跑起来,但 stderr 被 `2>/dev/null` 吃掉,stdout 为空 ——
     而「stdout 为空」正是我想看到的「0 命中」。差一点就把没扫当成扫过了。
- **根因**:三者共同点是**失败与成功在输出上不可区分**。①是规则集不幂等(产物能再次被
  规则匹配);②是正则语义与直觉相反;③是进程层失败被重定向掩盖。
- **修法**:①追加改成**折叠式后处理**,而且尾串**从规则表里反取**
  (`next(new[len(old):] for old, new in RULES if old == ANCHOR)`)而不是手抄 ——
  手抄的那份与规则里那份标点差一个字符就永远匹配不上;模式写成 `(?:TAIL){2,}`,整段包进组。
  ②重写前先跑**幂等自测**:对 HEAD 每个文件与每条提交信息跑两遍规则,两遍结果必须相同,
  并断言「HEAD 是规则表的定点」(0 处会被再改)—— 这一步同时保证 HEAD 文案与历史文案用同一张词表。
  ③验收改成逐对象扫并**先打印处理量**:`git log --all --format=%B`(提交信息)、
  `git log --all -p -- <所有文本后缀>`(每个版本的每一行)、
  `git rev-list --all --objects`(路径名),看到「扫了 N 个提交 / M 字节 diff」之后再读命中数。
- **教训与可复用规律**:
  1. **批处理重写必须自带「跑两遍等于跑一遍」的断言**,否则每一遍都在累积污染,而且污染是
     单调的 —— 第二遍看起来"更干净",实际多了一份重复。
  2. **`0 命中` 必须先证明扫描本身有效**。报告处理量(对象数、字节数)是最低成本的做法;
     否则"没有"和"没跑成"是同一个输出。这与硬规矩 1 同源:声明"包里没有"也要可验证。
  3. 规则表要**按长度降序**应用(第一遍就踩过:短规则先吃掉长规则的输入,产出乱语),
     且需要保护的字面量(法定展示号、必须可用的官方链接)先进占位符、后还原,
     不要指望规则顺序天然正确。

### H96. 底部玻璃「放大镜」装机三连改:**折射带画不成折射、倍率被胶囊高度卡死、以及把「太弱」误判成「坏了」**

**现象**:对底部玻璃导航提三条手感要求 —— ①按住任一 tab 时**整条栏**一起放大
(当时只有被按的那个图标放大);②镜片经过/离开文字图标时内容要**明显**放大,
像放大镜;③胶囊停在文字图标**边缘**时要有明显的拖影(折射拉伸感)。
改前的代码已经是「基础内容 + 折射带 + 镜片」三层,装机一看:整栏放大看不见、
折射带那圈不是折射而是**一整圈提亮的浅色光晕**、镜片里的字与底下原尺寸的字叠成
重影、慢拖胶囊时副本跑得比镜片快(读作掉帧)。

**根因**:四件事,全都只有真机看得出来:
1. **折射带**:那一层是「比胶囊大一圈 + `clipShape` 裁剪 + 内容绕胶囊中心放大」。
   带 `clipShape` 的子节点在 ArkUI 里被**单独合成**,而玻璃质感靠 `.backgroundEffect`
   对**身后实时内容**做区域模糊 —— 单独合成的那一圈把 backgroundEffect 重算了一遍,
   于是它表达的是「这一圈背景更亮」,不是「边缘内容被拉伸」。
2. **倍率没有对账**:`LENS_MAG` 1.45 与 `PILL_H` 44 各自凭观感取值。内容块高 =
   图标 22 + 间距 2 + 文案 ≈13 = **37vp**,放大后 37×1.45 ≈ 53.7 > 44,副本上下各溢出
   约 5vp,「发现」下沿被胶囊圆角**削掉** —— 表现酷似「缩放轴心跑偏、字往下掉」。
3. **底板盖不住**:镜片里的放大副本要靠一块表面色底板盖住下层原尺寸内容(不挖孔,
   理由见 `GlassTabBar.ets` 类注释),α 0.82 盖不住,两层字叠读。
4. **「看不见」不等于「没生效」**:整栏放大 1.07 在 56vp 高的栏上只有 4vp 变化,
   截图与肉眼都察觉不到,一度被判成状态链路断了、差点去重写正确的代码。

**修法**:① **删掉折射带**,收敛成两层(基础内容 + 镜片);拖影改由镜片层自己表达 ——
副本绕胶囊中心放大,并沿拖拽方向做**负向**滞后平移(副本落后于镜片;正向会读作掉帧),
同时**横向单独加一档**倍率(`lensMagX = LENS_MAG + |拽动量| × LENS_STRETCH`)。只平移
得到的是「整块字挪了位子」,不加横向拉伸就不像折射。② 倍率与胶囊高**一起定**:
先量内容块 37vp,取 37×1.35 ≈ 50,于是 `PILL_H` 44→50、`LENS_MAG` 1.45→1.35 ——
上限由「放大后不超出裁剪框」倒推。③ 底板 α 提到 **0.93**(宁可实一点也不留重影)。
④ 放大率提到可察觉:**BAR_PRESS 1.10 / PILL_PRESS 1.15**。鸿蒙定稿后 Android 以同一组
数值、同一套两层结构移植(`GlassNavBar.kt`:倍率/胶囊高/底板 α/拖影三参数一一对齐),
双 flavor 编译通过。

**教训与可复用的规律**:
① **观感参数要「先算账再取值」**:凡「放大 + 裁剪 + 叠加」三者共存,先把内容块实际
尺寸与容器尺寸写成不等式(37×M ≤ H_胶囊),M 与 H 就是**一对**联动值 —— 只调其中一个,
必然以另一种方式失败(倍率大了切字、胶囊高了发胖)。
② **几何结论用 bounds 算,别目测截图**。本例先目测副本「偏下 15vp」、怀疑
`.scale({centerX, centerY})` 的语义,拿 `hdc shell uitest dumpLayout` 的实测 bounds
一算:2508 + (2547−2508)×1.45 = 2564.6,与实测 2564.5 吻合 —— 轴心正确,错的是倍率
超了裁剪框。**凡是能算的观感问题,先去找那个给出数字的工具。**(同一回路里抓屏用
`hdc shell snapshot_display` + `hdc file recv`,不是 `hdc recv`。)
③ 判「没生效」之前先跑一遍**夸张值**(本例 1.25/1.30):链路通不通一眼分明,
把「太弱」和「坏了」分开,再谈调参。
④ **系统手势区会吃掉注入事件**:在底部导航区做 `uitest` 长按/慢滑会触发小艺提示气泡
(bounds [172,2405][1044,2568],正好压住栏),该气泡**吞点击**,于是「点按不切页」被
误判成代码回归。真机自动化之前先 dumpLayout 看有没有非本应用的节点压在目标区域上。
⑤ 「区域级实时背景模糊」与「带裁剪的独立合成层」互斥:想让某一圈看着更玻璃,不要在
带 `clipShape` 的子层上叠 `backgroundEffect`,它只会把那圈背景提亮。
