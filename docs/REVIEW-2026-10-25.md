## 0. 一句话结论

虫子不在 happy path 上——三端的防御密度、并发口径、坑位回写在独立应用里属罕见水准;

**唯一被打穿的红线是日志承诺**(见高危 1)。

## 1. 高危(3 条 —— 建议 1.0.6 出包前修,合计小时级工作量)

### 高-1 macOS 日志写搜索词与设备标识,违反已发布的隐私承诺 【主线复核 ✅】

- **位置**:`macos/Sources/Reverb/Data/ITunesSource.swift:10,13,17,26,29,53`、`FyydSource.swift:8,19,22`、`GpodgerSource.swift:9,11,25`(共 10 处 `term="..."`);`ListenStatsStore.swift:43`(`device=\(deviceId.prefix(8))`)。
- **现象**:原始搜索词与安装随机标识前 8 位写进 `reverb.log`(Log.debug 也落文件),而日志有「导出 / 分享 / 发邮箱」三条出口离机。
- **违反的承诺**:`docs/PRIVACY.md`「日志」一节明文——「日志不记录搜索词、完整 URL 或安装随机标识」,点名 Android 与 macOS 都受约束。
- **根因**:H131(2026-10-05)定的修法「搜索词一律换词数」只落在了 macOS 的 `PodcastRepository.swift:30`(注释还引了政策),三个 Source 层调用点漏扫——正是 H131 自己总结的「规矩落在调用点上必漏」的复发。
- **修法**:三处源日志照 Repository 改词数;`deviceId.prefix(8)` 删掉。

### 高-2 macOS 备份三格初值与两端相反,会把手机的合规开关静默打开 【主线复核 ✅】

- **位置**:`macos/Sources/Reverb/Data/Stores.swift:338-339`(`allowCellularDownload ?? true`、`updatesEnabled ?? true`)。
- **现象**:注释声称「初值与另两端同口径……要和手机默认一致才不篡改备份」,实测**两端默认均为 false**:Android `SettingsStore.kt:17`(`cellular_dl` false)与 `:20`(`updates_enabled` false)、鸿蒙 `SettingsStore.ets:121` 两格同 false。注释动机与代码效果正好相反。
- **后果**:从未恢复过手机备份的 Mac 原生导出备份(ExportSheet 默认全勾含 settings),Android 恢复时无条件应用存在的键(`BackupManager.kt:248-249`)——手机的「仅 Wi-Fi 下载」在蜂窝网络下直接产生流量消耗;更重的是 `updates_enabled` 默认关有**合规理由**:Android 代码注释写明隐私政策承诺「仅在你主动开启『订阅更新提醒』时征求同意」,被备份静默打开等于绕过该承诺。
- **来源**:M3 提交(`9983b72`)引入,机制(逐键 optional 对称往返)本身正确,唯初值两处一行修掉即可。`categoryOrder` 的 `[]` 初值无问题(Android `loadOrder()` 默认也是空表)。

### 高-3 Android 与鸿蒙全部 JSON store 非原子写 + 读失败整份清零

- **位置**:Android `data/local/JsonWriter.kt:56,76` 及各 store 直写点;鸿蒙 `store/JsonFile.ets:34-35,192-193`、`TranscriptTask.ets:108-109`、`TranscriptStore.ets:369-370`。
- **现象**:「截断原文件 → 直接写」,无临时文件、无 rename、无 fsync;进程死在写入窗口内(电池耗尽 / 系统回收 / 崩溃)→ 文件截断 → 下次启动解析失败 → 读侧 `catch { emptyList() }` 整份当空 → 任何一次后续操作把空态永久落盘。订阅 / 收藏 / 批注(用户手写的字)/ 历史全部同型,无自救入口。
- **暴露面**:播放中每约 5 秒写一次 history(几百 KB),窗口持续存在;鸿蒙播放中 history 写 + 每次用户动作一次同步写。
- **修法在本仓库已有三份正确范式,只是没推广**:Android `AudioCacheManager.fetch` 的 `.part → rename`、macOS `FeedCacheStore` 的 `.atomic`。统一「临时文件 + rename + 读失败跳坏条目而非弃整份」。
- **附带**:Android `HistoryStore.kt:88` 单条坏元素(`episode` 缺键)会毒死整份文件,同修。

## 4. bug 背后的四个模式(比虫本身更值钱)

1. **故障方向欠账。** Android 与鸿蒙两路审查独立得出同一结论:happy path 防御到位,「坏方向」——播放器出错之后、备份值类型不对、进程死在写盘中途——普遍缺一道收尾。高危 3 条 + 中危 1/2/6/9 全是这一族。
2. **靠调用点自律的规矩必漏。** H131 搜索词(macOS 漏 10 处)、蜂窝闸门(三端各有闸,转写路径全没接)、备份初值口径(注释意图与代码相反)。结构性解法只有一个:把规矩变成一处集中闸或一张可执行断言表,不是「下次记得」。
3. **非原子写盘是三端共有的底座病。** 三份正确范式躺在仓库里(`.part→rename`、`.atomic`),推广即可,应一次性收口而非零碎修。
4. **互通协议主体咬合好,缺口全在 macOS 键集滞后。** 三端备份的分区、合并语义、时间戳归一(1e11 阈值)、CRDT 分账、PlayMode ordinal 逐字段核对全部对齐;真正的洞只有 macOS 少写的键(中危 8)与两格初值(高危 2)。

## 5. 方向建议(对 ROADMAP §四 的五条增量,不重复其已有规划)

1. **1.0.6 出包前收口四件事**:高危-2 两行改 `false`;高危-1 十处日志改词数;中危-9 判 hvigor 退出码;中危-10 补 CHANGELOG。合计小时级。
2. **把 REVIEW-2026-10-18 的 P1-9「规则级测试」提前,本文就是立项理由。** 上述虫里约一半(备份对称性、初值口径、时间轴单调、hash 碰撞、实体解码顺序)是纯函数级可测的。最优先两张表:三端 settings 默认值一致性表(直接拦住高危-2 这类)、备份键集三端对照表(拦住中危 8)。
3. **持久化原子化做成一次独立收口**(高危-3):三端 JSON 底座统一「临时文件 + rename + 读失败跳坏条目」。这是「每加一个新功能就多一处实例」的地基问题,值得专门一个提交批次。
4. **重拍「macOS 运行验收固定在另一台机器」这条 2026-09-29 的边界。** 10-24 出包门已全绿,「这台机器就是自己的构建机」已成事实;本文 macOS 虫最多恰因为它从未跑起来过。哪怕只做一条脚本判据(启动→播 15 秒→退出→验 history.json 的 mtime 与进度值,ROADMAP 三-A 已列),也能拦住高危-1/2 这类「看起来对」。
5. **隐私承诺做成反向 grep 断言**:发版前扫日志代码不得出现 `term=` 插值、完整 URL 插值、`deviceId` 插值(对齐硬规矩 1 的解包 grep 方法论)。高危-1 的本质是文本承诺与代码行为的漂移,仓库自己的方法论正好能管住它。

次级两条:鸿蒙接 whisper.cpp(ROADMAP「如果只做一件事」)**翻开关前必修中危-3 的蜂窝闸门**,现在是潜伏的,开关一翻就在计费网络上拉几十 MB;iOS 扩展(ROADMAP 判断性价比最高)的前置条件应是 **macOS 互通键集补齐**(中危 8),否则会把第三套半成品互通面复制过去。
