## 0. 一句话结论

**这是一个把"克制"写进架构、而不是写进文案的项目** —— 零后端、不接三方 SDK、按渠道裁剪功能,
三条都不是口号,每条都有可执行的解包判据在守。工程纪律在同类个人项目里属于少见的水平。

**但它把全部质量保障押在了"人肉装机验收 + 文档"上,而这套体系正在被自己的文档体积压垮。**
排错手册(条目数用 `grep -cE '^#+ *H[0-9]+' docs/TROUBLESHOOTING.md` 现算)、88 万字节的排错记录、
33 万字节的路线图 —— 这些是资产,也已经是负债:
它们已经长到没人(包括编码代理)能在一次会话里读完,而它们承载的规则会互相矛盾。
**复校后的现状**:本文列出的五条硬矛盾已全部修完,但**复校又抓到同类的两处**(写死数字、行号自指),

## 2. 做对了什么

### 2.1 约束是"可验证的",不是"声明的"

"零后端"这类承诺最容易变成 README 里的一句好话。这里把它做成了命令:

```bash
unzip -l dist/reverb.apk | grep -icE 'lib/|whisper-model'                # 合并 flavor 后期望**非 0**(曾期望 0,H205)
LC_ALL=C cat classes*.dex | grep -ac 'itunes.apple.com\|fyyd\|gpodder'   # 期望非 0
```

> 这一组判据**在本文写完之后当场翻转过一次**:10-18 之前它是拿 `dist/reverb-store.apk` 量的、
> 期望 `lib/` 与模型为 **0**;合并 flavor 之后商店那份不复存在,同一句"包里有没有离线识别"
> 的期望值变成非 0。**这就是下面 2.1 自己那条方法论的活样本** —— 期望值跟着产品决策走,不是仪式。

而且方法论写的是"**声明加回来也要验、声明删掉也要验**",不是把一组期望值永久写死 ——
这条差别很关键:它把"验收"从"仪式"变成了"跟着产品决策一起翻转的量"。

### 2.2 渠道隔离做在编译期,不在运行期

`app/src/default/` 与 `app/src/store/` 两个 source set(⚠️ **2026-10-18 合并 flavor 后这两个目录已删除**,
`ls android/app/src/` 只剩 `main`;降级档改由 `src/main` 里三个编译期常量承担 —— H205)、
`harmony/shelved/` 把代码移出编译树(这一条不变)。
`AGENTS.md` 硬规矩 2 明确写了"ArkTS 没有 DCE,`Features.X ? A : B` 两支都会进包"——
这是一个**用工具链事实推翻常识类推**的判断,而且是被事故教出来的。这类知识买不到。

### 2.3 踩坑记录是本仓库最值钱的东西

每条固定四段:**现象 / 根因 / 修法 / 教训与可复用的规律**(条目数别写死,
`grep -cE '^#+ *H[0-9]+' docs/TROUBLESHOOTING.md` 现算;`^##? *H` 那种写法会数到 0)。抽样几条就能看出密度:

- H63:`.hvigor/sync` 缓存内嵌整份签名配置(含口令),导致口令进了 43 个历史提交 ——
  并由此得出"扫泄露要拿真实口令串搜全历史,不是按文件名扫"。
- H156:`aapt2` 不在开发机 PATH 时 `grep -c` 对着空 stdin 报 **0**,两个渠道都被读成"没有录音权限"——
  由此得出"期望 0 的判据必须先看命令自己的退出码"。
- H70:渠道口径翻转后,解包 grep 的期望值也要跟着翻 —— 文档同步不是可选项。

这三条的共同点:**它们都是"看起来通过了,其实是假的"**。这类失败模式靠读代码发现不了,只能靠记录。

### 2.4 单一发布物 + 时间戳判据

`AGENTS.md` 硬规矩 20 要求"报'包已就绪'要带出处:字节数 + `ls -lT` 时间戳",
并用 `find ... -newer` 断言产物晚于最后一次源码改动,还专门写了"**括号不能省**,
省了 `-newer` 只作用在第一个 `-name` 上"。

这是在防一个非常具体、而且**真的发生过**的失败:"代码改了、包没重打",而 `dist/` 里躺着旧包时
它看起来是完全就绪的。大多数项目在这一步靠"我记得我重新打过"。

### 2.5 合规是设计输入

隐私同意门、按渠道裁剪功能、**应用内更新曾只在自分发版实现**(商店版是空实现桩,不检测、不下载、
不申请「安装未知应用」权限)—— 这些不是界面上加个开关,而是**三处口径同时翻**才能落地的架构决定。

> ⚠️ **本文写成当天(2026-10-18)这一节就失效了一半**:两个 flavor 合并成唯一一份包(H205),
> 于是离线识别、麦克风权限、内置精选清单与应用内更新**同时出现在交去商店的那份包里**,
> 上面那句"商店版是空实现桩"只作为合并前的史实保留。
> **不变的是这一节的方法论** —— 功能口径一动,要跟着翻的是**备案申报、解包 grep 期望值、隐私政策**三处,
> 这一次是它的第二次发作(第一次见 H70)。

### 2.6 注释写"为什么",而且写在事发地点

`AGENTS.md` 的代码风格要求"踩过的坑写在最近的代码旁边,不只写进文档 —— 后来者改这行时才看得见"。
这条在个人项目里几乎见不到,但它恰好是**唯一能对抗"文档和代码脱节"的写法**。

### 2.7 诚实的自述

`CHANGELOG.md` 的 1.0.5 一节开头就直接写:"缓存那一批的装机与断网实跑**一条都没走**",
"鸿蒙这一份 release 包本身仍没装过机"。**一个发布前夜的变更日志主动标注"核心卖点没有真机证据"**,
这需要的不只是诚实,还需要一套不奖励自我欺骗的记录习惯。

## 3. 不足

### 3.1 质量保障:零自动化,全部押在"人肉装机"

**证据**:无 `.github/`、无测试目录、无 lint 门。

**后果**:44 522 行、**三个编译单元**(⚠️ 本文写成当天从「四个」变来:合并 flavor 前是 Android `default` + `store`、鸿蒙、macOS,
现在只有 Android、鸿蒙、macOS 三份 —— H205;复校那轮订正过"3 端 × 2 渠道"这个口径,今天它又翻了一次),
唯一回归手段是"装到真机上点一遍"。
`CHANGELOG` 自己已经给出了这个体系的失效样本:**1.0.5 的核心功能(播放缓存)一条真机判据都没走**,
而它已经是"发布在即"的状态。这不是疏忽,是**体系容量到了上限**——
当"验收"的边际成本是"拿起手机点十分钟",它一定会在时间压力下被跳过。

**这一条是本文最重要的判断**:其他所有问题都可以慢慢修,这一条不修,下一个版本会以同样的方式发布。

### 3.2 三端一致性靠文档同步,不靠测试同步

同一套产品规则在三端各写一遍:缓存淘汰策略、时间轴单调性、渠道裁剪、备份格式互通。
同步机制是"`AGENTS.md` 硬规矩 5 的那张表 + 人的记性"。

`docs/MACOS-GAPS.md`(14 KB)的存在本身就是证据:**它是一份"三端不一致"的手工台账**。
台账能做到的事是"记录漂移",做不到"阻止漂移"。

### 3.6 仓库对外不完整

**⚠️ 复校更正了本节的前提 —— 原文把两个仓库当成一个:**

| 仓库 | 可见性(API 实测) | 内容 | 有无 LICENSE |
|---|---|---|---|
| `cxyxlxdm/reverb`(**本仓库 = git remote**) | **未认证访问返回 404 ⇒ 私有**(CHANGELOG 那句"公开仓 `revert-cast`,不是私有 git remote"指的是它;同一判据也记在 `docs/TROUBLESHOOTING.md` H144 的 2026-10-08 补记) | 全部源码与文档 | 无(但外部人看不到) |
| `cxyxlxdm/revert-cast`(**对用户公开**) | `visibility=public`、`private=false` | 根目录只有 `README.md` + `.gitignore` + `.gitattributes`;**实际用途是 Releases 分发**(1.0.5 的应用内更新就查它的 `releases/latest`) | **无 LICENSE** |

所以原来的说法要分两层重述:

1. **"代码仓库公开但没 LICENSE"这句不成立** —— 代码仓是私有的,"别人 fork / 修改 / 分发"这一层风险不存在。
   本文「对外完整性」那一行的扣分理由因此需要改写(见第 0 节评分表注)。
2. **但缺 LICENSE 这件事仍然成立,只是换了对象**:公开的是 `revert-cast` 和从这里发出去的**安装包**。
   用户拿到 apk / dmg,法律上没有任何许可证说明"可以安装、可以备份、可以转发"到什么程度;
   而 `revert-cast` 那个公开仓本身也没写"代码公开但不授权"。
   **要补的是对外许可声明(或显式的"保留所有权利"立场),不是给私有代码仓加开源证书。**

同时缺 `CONTRIBUTING.md`、Issue 模板。单人项目可以不要,但 `AGENTS.md` 既然是"给第一次接手的人看的",
就该说明"外部提 PR 怎么处理"—— 否则第一个 PR 会以最尴尬的方式出现。
**复校补一条**:代码仓私有 ⇒ 这一条的紧迫度低于原文评估;真正会先到的是**对安装包的问询**。

> ⚠️ **另有一条本文原先没写、复校时才发现的口径事实**:应用内更新的 URL 指向 `revert-cast`,
> 与 git remote `reverb` **是两个不同仓库**。这是**有意的**(公开分发 vs 私有开发),
> `SelfUpdate.kt:55` 与 `ROADMAP` A19 都写明。但它意味着**发版有第四条"必须一致"的东西**:
> 包要传到 `revert-cast` 的 Releases,而版本号写在 `reverb` 里 —— 只推一边,应用内更新就查不到新包。
> **回滚预案(3.5②)缺的正是这一环的说明。**

### 3.8 产品面

2. **弱网首启体验差 —— 合并 flavor 后这一条只剩鸿蒙。** 原先写的是"商店渠道不打包 `seed_podcasts.json`";

   首次内容完全依赖在线榜单。
3. **崩溃可见性:原文"只能靠用户描述"说重了,复校收窄成一条具体缺口。**
   ✅ **已有**:设置页有「分享日志」(`values/strings.xml:226`)/「导出日志」(`:229`),
   副标题就写着"把运行日志发给开发者协助排查偶发问题"(`:232`)—— 也就是"本地日志导出 + 用户主动提交"**已经存在**;
   Android 崩溃还能从 `adb shell dumpsys activity exit-info` 读到退出原因(`reason=16` 是覆盖安装不是崩溃)。
   ❌ **真缺的**:**未捕获异常没有专门落盘**。判据(处理量先行):对 192 个源文件扫
   `Thread.setDefaultUncaughtExceptionHandler` / `UncaughtExceptionHandler` / `CrashHandler` —— **0 命中**。
   所以进程挂掉之前那几行不会进日志,用户导出的那份**恰好不含崩溃瞬间**;
   而鸿蒙/Android 两侧要拿到崩溃现场,现在得靠开发者主动连设备读系统日志(用户那边做不到)。
   **这仍然与"零后端"不冲突**(落盘 + 用户主动提交是本机动作),只是补一个 handler,不是加上报。
