# 项目评价 · 2026-10-18(1.0.5 发布前)

> 评价对象:`cxyxlxdm/reverb`,分支 `feat/offline-cache`,HEAD `64333d2`。
> 方法:通读 `AGENTS.md` / `README.md` / `docs/*` / `CHANGELOG.md`,统计三端源码与文档规模,
> 实际跑一次 Android 编译,核对发版要素(版本号、依赖、忽略规则、许可证)。
> 本文只写判断与证据;`docs/ROADMAP.md` 记的是"要做什么",本文记的是"现在处在什么位置"。

## 0. 一句话结论

**这是一个把"克制"写进架构、而不是写进文案的项目** —— 零后端、不接三方 SDK、按渠道裁剪功能,
三条都不是口号,每条都有可执行的解包判据在守。工程纪律在同类个人项目里属于少见的水平。

**但它把全部质量保障押在了"人肉装机验收 + 文档"上,而这套体系正在被自己的文档体积压垮。**
202 条踩坑记录、88 万字节的排错手册、33 万字节的路线图 —— 这些是资产,也已经是负债:
它们已经长到没人(包括编码代理)能在一次会话里读完,而它们承载的规则正在互相矛盾。

| 维度 | 评分 | 一句话 |
|---|---|---|
| 产品定位与取舍 | ★★★★★ | "安静的播客客户端"从头贯彻到尾,连缓存策略都在为这个语义让路 |
| 架构纪律 | ★★★★★ | 渠道隔离做在 source set / 编译树层面,不是运行时 `if` |
| 代码质量 | ★★★☆☆ | 注释质量极高,但巨型文件多、三端重复实现同一套规则 |
| 可验证性 | ★★☆☆☆ | 产物验收很强,产品行为验收为零自动化 |
| 文档 | ★★★☆☆ | 密度与诚实度罕见;但体积失控、彼此矛盾、不可检索 |
| 发版卫生 | ★★★★☆ | 单一发布物 + mtime/SHA 判据很硬;缺版本号单一来源与回滚预案 |
| 对外完整性 | ★★☆☆☆ | 仓库公开但**没有 LICENSE**,法律上默认"保留所有权利" |

## 2. 做对了什么

### 2.1 约束是"可验证的",不是"声明的"

"零后端"这类承诺最容易变成 README 里的一句好话。这里把它做成了命令:

```bash
unzip -l dist/reverb-store.apk | grep -icE 'lib/|whisper-model'          # 期望 0
LC_ALL=C cat classes*.dex | grep -ac 'itunes.apple.com\|fyyd\|gpodder'   # 期望非 0
```

而且方法论写的是"**声明加回来也要验、声明删掉也要验**",不是把一组期望值永久写死 ——
这条差别很关键:它把"验收"从"仪式"变成了"跟着产品决策一起翻转的量"。

### 2.2 渠道隔离做在编译期,不在运行期

`app/src/default/` 与 `app/src/store/` 两个 source set、`harmony/shelved/` 把代码移出编译树。
`AGENTS.md` 硬规矩 2 明确写了"ArkTS 没有 DCE,`Features.X ? A : B` 两支都会进包"——
这是一个**用工具链事实推翻常识类推**的判断,而且是被事故教出来的。这类知识买不到。

### 2.3 踩坑记录是本仓库最值钱的东西

202 条,每条固定四段:**现象 / 根因 / 修法 / 教训与可复用的规律**。抽样几条就能看出密度:

- H63:`.hvigor/sync` 缓存内嵌整份签名配置(含口令),导致口令进了 43 个历史提交 ——
  并由此得出"扫泄露要拿真实口令串搜全历史,不是按文件名扫"。
- H156:`aapt2` 不在开发机 PATH 时 `grep -c` 对着空 stdin 报 **0**,两个渠道都被读成"没有录音权限"——
  由此得出"期望 0 的判据必须先看命令自己的退出码"。
- H70:渠道口径翻转后,解包 grep 的期望值也要跟着翻 —— 文档同步不是可选项。

这三条的共同点:**它们都是"看起来通过了,其实是假的"**。这类失败模式靠读代码发现不了,只能靠记录。

### 2.4 单一发布物 + 时间戳判据

`AGENTS.md` 硬规矩 20 要求"报'包已就绪'要带出处:字节数 + `ls -lT` 时间戳",
并用 `find ... -newer` 断言产物晚于最后一次源码改动,还专门写了"**括号不能省**,
省了 `-newer` 只作用在第一个 `-name` 上"。

这是在防一个非常具体、而且**真的发生过**的失败:"代码改了、包没重打",而 `dist/` 里躺着旧包时
它看起来是完全就绪的。大多数项目在这一步靠"我记得我重新打过"。

### 2.5 合规是设计输入

隐私同意门、按渠道裁剪功能、应用内更新只在自分发版实现(商店版是空实现桩,不检测、不下载、
不申请「安装未知应用」权限)—— 这些不是界面上加个开关,而是**三处口径同时翻**才能落地的架构决定。

### 2.6 注释写"为什么",而且写在事发地点

`AGENTS.md` 的代码风格要求"踩过的坑写在最近的代码旁边,不只写进文档 —— 后来者改这行时才看得见"。
这条在个人项目里几乎见不到,但它恰好是**唯一能对抗"文档和代码脱节"的写法**。

### 2.7 诚实的自述

`CHANGELOG.md` 的 1.0.5 一节开头就直接写:"缓存那一批的装机与断网实跑**一条都没走**",
"鸿蒙这一份 release 包本身仍没装过机"。**一个发布前夜的变更日志主动标注"核心卖点没有真机证据"**,
这需要的不只是诚实,还需要一套不奖励自我欺骗的记录习惯。

## 3. 不足

### 3.1 质量保障:零自动化,全部押在"人肉装机"

**证据**:无 `.github/`、无测试目录、无 lint 门。

**后果**:44 522 行 × 3 端 × 2 渠道,唯一回归手段是"装到真机上点一遍"。
`CHANGELOG` 自己已经给出了这个体系的失效样本:**1.0.5 的核心功能(播放缓存)一条真机判据都没走**,
而它已经是"发布在即"的状态。这不是疏忽,是**体系容量到了上限**——
当"验收"的边际成本是"拿起手机点十分钟",它一定会在时间压力下被跳过。

**这一条是本文最重要的判断**:其他所有问题都可以慢慢修,这一条不修,下一个版本会以同样的方式发布。

### 3.2 三端一致性靠文档同步,不靠测试同步

同一套产品规则在三端各写一遍:缓存淘汰策略、时间轴单调性、渠道裁剪、备份格式互通。
同步机制是"`AGENTS.md` 硬规矩 5 的那张表 + 人的记性"。

`docs/MACOS-GAPS.md`(14 KB)的存在本身就是证据:**它是一份"三端不一致"的手工台账**。
台账能做到的事是"记录漂移",做不到"阻止漂移"。

### 3.3 文档已经过载

| 文件 | 体积 | 问题 |
|---|---|---|
| `TROUBLESHOOTING.md` | 880 KB / 9 869 行 | 单文件超过多数编辑器的舒适区;无法整体检索,只能 grep |
| `ROADMAP.md` | 335 KB / **1 002 行** | 平均每行 334 字节 —— 意味着大量单段数千字的"散文式状态汇报" |
| `CHANGELOG.md` | 133 KB | 1.0.5 一节的标题就是一句话 100+ 字;正文前 40 行是"验收状态"散文,**已经不能直接对外发布** |

**后果有三层**:
1. **人读不完** → 只能靠 grep,而 grep 只能找到你已知要搜的词;
2. **代理读不完** → 每次会话都要重新建立上下文,这正是"同一件事写在两处、改一处忘另一处"的温床;
3. **`CHANGELOG` 作为"对外版本说明的唯一上游"(硬规矩 19)已经失效** —— 它现在的读者是维护者自己,
   不是用户。而"上游失效"意味着对外文案又变回了一次手工翻译。

### 3.4 文档之间存在硬矛盾(这是当下最危险的一类问题)

| # | 矛盾 | 位置 | 后果 |
|---|---|---|---|
| 1 | "装机前**先问**" vs "用户 2026-10-16 明确授权代理**自己装,整个过程不问**" | `CLAUDE.md` 第 20 行 vs `AGENTS.md` 硬规矩 12 | 编码代理按 `CLAUDE.md` 行事会**该装的不装**,任务卡在"等确认" |
| 2 | "18 条硬规矩" vs 实际 20 条 | `CLAUDE.md` 第 6 行、`README.md` 第 82 行 | 计数漂移,读者会以为漏看了两条 |
| 3 | macOS 产物在 `macos/build/余音-Reverb.dmg` vs `macos/dist/余音-Reverb-<版本>-universal.dmg` | `README.md` 第 117 行 vs `AGENTS.md` 硬规矩 20 | 找错产物 |
| 4 | "共享记忆"指向 `~/.agent-memory/…` | `AGENTS.md` 第 435–442 行 | **该目录在本机不存在**,整节是死链 |
| 5 | `export JAVA_HOME=$(/usr/libexec/java_home -v 17)` | `README.md` 第 95 行 | 本机 `java_home -v 17` 返回空,实际要用 `/Users/liang/.java/jdk-17.0.12+7/Contents/Home`;**`AGENTS.md` 完全没写 JDK 路径** |

第 1 条尤其值得警惕:它不是笔误,而是**授权变更只改了一处**。
这恰好是硬规矩 5 想防的那类事故,只是这次发生在"给代理看的文档"上。

### 3.5 发版卫生:缺两个关键机制

**① 版本号没有单一来源。** 1.0.5 要在至少三处手改:

| 端 | 位置 | 当前值 |
|---|---|---|
| Android | `android/app/build.gradle:20-21` | `versionCode 6` / `1.0.5` |
| 鸿蒙 | `harmony/AppScope/app.json5:5-6` | `1000005` / `1.0.5` |
| macOS | `macos/Info.plist:29-32` | `1.0.4` / `2` |

macOS 停在 1.0.4 是**有意为之**(`CHANGELOG` 写明本轮桌面端零改动),但它暴露了机制缺失:
"三端共用一套版本号节奏"这句承诺,现在**没有任何东西在守**,只靠人记得。

**② 没有回滚预案。** 发出去一个坏包怎么办 —— 商店侧下架、GitHub Releases 撤包、
应用内更新指向哪里,`AGENTS.md` 与 `STORE-OPS.md` 都没写。对一个已经有"应用内更新"链路的产品,
这是缺的一环。

### 3.6 仓库对外不完整

**没有 `LICENSE`。** 仓库在 GitHub 上公开(`github.com/cxyxlxdm/reverb`),
但没有许可证意味着**默认保留所有权利** —— 别人不能合法地 fork、修改、分发,甚至"学习参考"都在灰色地带。
如果本意是"代码公开但不授权使用",那应该显式写出来(这本身是一种立场);
如果本意是开源,那现在缺的是法律基础,不是礼貌问题。

同时缺 `CONTRIBUTING.md`、Issue 模板。单人项目可以不要,但 `AGENTS.md` 既然是"给第一次接手的人看的",
就该说明"外部提 PR 怎么处理"—— 否则第一个 PR 会以最尴尬的方式出现。

### 3.7 代码结构:三个巨型文件 + 渲染与状态耦合

| 文件 | 行数 |
|---|---|
| `harmony/entry/src/main/ets/playback/PlayerController.ets` | 1 555 |
| `android/.../ui/components/Components.kt` | 1 444 |
| `harmony/entry/src/main/ets/view/Components.ets` | 1 438 |
| `harmony/entry/src/main/ets/view/DiscoverPage.ets` | 1 416 |
| `android/.../ui/screens/DiscoverScreen.kt` | 1 035 |

`AGENTS.md` 硬规矩 6 和 7 其实已经诊断出了根因("**每秒会跑两次的代码,要按每秒两次来估成本**"、
"高频状态不要挂在被整体观察的对象上"),但**解法只到了"下沉到最小组件"这一层**,
没有到"文件该拆开"这一层。1 400+ 行的 Compose/ArkUI 文件,改一个卡片就要在四个屏幕之间来回确认影响面。

### 3.8 产品面

1. **三端不对齐,但对外叙述是"三个原生端"。** macOS 缺一批功能(`MACOS-GAPS.md`),
   而 `README` 第一句是"三个原生端"。用户不会读缺口清单,只会觉得"Mac 版是残的"。
   要么把差异显式写进对外文案,要么把 macOS 标成 beta。
2. **商店渠道弱网首启体验差。** 不打包 `seed_podcasts.json`,首次内容完全依赖在线榜单 ——
   而这恰好是商店渠道(合规裁剪后功能更少)最需要"打开就有东西"的场景。
3. **无崩溃可见性。** 与"零后端"原则冲突,但至少可以做到"本地崩溃日志导出 + 用户主动提交"。
   现在出问题只能靠用户描述。
